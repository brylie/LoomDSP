## Goal

"I plug a cable into a running patch. The new path should join the sound that is playing, as it does on hardware. If it starts from reset, it sounds like a bug."

## Behaviour

Every edit that changes the graph compiles a new schedule on the control thread. The engine swaps it in at a buffer boundary (NFR-RT-05). The player hears the change at that boundary and nothing else.

| What the swap touches | Carried across | How |
|---|---|---|
| Module instances | Yes | They live in engine slots, not in the schedule. A module runs whether or not anything is patched to it. |
| Parameter smoothing, engine side | Yes | By fill key (`take_smooth_state_from`). A new fill starts from `Module::param_glide`. |
| Unit delays (user and inserted) | Yes, while the key stays | By key (`take_tap_state_from`). The key is the module ID, the delayed input, or the assignment ID. |
| A new unit delay, or one that moved | Its source's last value | Rule 5. |
| Transport, output safety, MIDI state | Yes | They live in the engine. |
| Port buffers | Not needed | Every buffer is written before it is read in each block. |
| Copy 1 of a module that turns stereo | **No: starts from reset** | Not built yet (#23). Rule 6 fixes it. |
| A module the player adds | No, by design | A new module is new hardware: it starts from reset. |
| A module that reaches nothing | Yes, paused | It is not run while nothing hears or shows it (rule 8). |
| An input whose cable changed, or an assignment added, removed, or moved | Its last value, then a 5 ms ramp | Rule 9. Gate, trigger, and phase inputs switch; what a changed phase drives fades. |
| An assignment turned on or off, or given a new depth or polarity (no swap; undo and redo blend the same way) | The live modulation, with the old setting blended into the new one over 5 ms | Rule 9. |

## Rules

1. **Module instances outlive schedules.** A swap never resets, rebuilds, or reorders a module's state. *Why:* plugging a running LFO into a new input must pick it up mid-cycle, as in hardware.

2. **Parameter smoothing carries across a swap.** Engine-side smoothing moves to the new schedule by key. *Why:* a recompile while a knob glides must not step the knob.

3. **A unit delay keeps its state while its key stays the same.** *Why:* a recompile must not touch a running feedback loop. A test checks that adding an unrelated module leaves a running loop bit-identical.

4. **A new module starts from reset.** *Why:* it has no history. This matches hardware, where a module is plugged in before it is patched.

5. **A unit delay with no state to carry starts with the last value its source output wrote before the swap.** This covers a delay the compiler inserts when a cable closes a new loop, a delay that moves to another cable when a loop changes, a new assignment delay, and a new Unit Delay module. If the source output did not run in the old schedule, the delay starts at 0. So does every new delay when two swaps land before one block runs, because the middle schedule never wrote its buffers. *Why:* measured in `hot_patch.rs`:

   | Case | Starting at 0 (before rule 5) | With rule 5 |
   |---|---|---|
   | New loop closed into an input that reads 0 when unplugged (Add B) | The cable acts as if plugged one sample later. No extra step. | Bit-identical to a delay that was already running. |
   | New loop closed into an input with another default or fallback (Multiply B reads 1) | The signal drops out for one sample: error -6 dB. | Bit-identical to a delay that was already running. |
   | A new cable moves the inserted delay to another cable of a running loop | The feedback drops out for one sample: error -17 dB. | Bit-identical to no move, because both placements give the same loop. |

   The value is what a delay that had always been on that cable would hold, so the new delay continues the signal instead of inventing a 0. *How:* the old schedule keeps a table of its output buffers, sorted by output. At the swap, each new delay looks up its source there and reads the last frame of the last block. The engine remembers that block's length. A binary search per new delay, no allocation.

6. **Copy 1 of a module that turns stereo takes copy 0's state.** The rules are in the [stereo spec](stereo.md), rules 13 and 25 to 27, and the decision in ADR-0022. *Why:* measured with the SVF and the same signal on both sides, a cold copy 1 is off by -2 to -24 dB and takes 1 to 20 ms to settle. A 5 ms crossfade scales that down but does not shorten it. Copied state is exact.

7. **A module made with non-default values starts at those values.** `reset()` snaps all smoothing to its targets (Constant already does this). After a module is built and its first parameter values are set, and before it is sent to the engine, the `Controller` calls `reset()` once. So the `Controller` keeps a new module until the next commit: values set before it go straight to the module, and the commit resets it and sends it in, before the new schedule. The `loom-test` harness does the same before it renders. *Why:* a factory builds the module with built-in values, then `set_param` sets the real ones. A smoothed parameter treats that as a new target and glides. A pasted filter at 200 Hz would sweep down from 1 kHz for 10 ms, with nothing to hide it (loading a patch has the output fade-in). *Why this option, not a flag per module or a factory that takes values:* the call is made in one place, so a module author cannot forget it, and `reset()` on a module that has just been built clears nothing that matters. Modules must keep this convention: **`reset()` snaps smoothing to the current targets.** A test in the harness checks it for every registered module: a module built with defaults, given a changed value and `reset()`, matches one that held the value for a long time, from the first sample.

8. **A module that reaches nothing the player hears or sees is not run, and keeps its state** (FR-GRAPH-09). The compiler leaves it out of the schedule and lists it in `CompileReport::skipped`. Its instance stays in its engine slot, so a cable that connects it again resumes it where it stopped: not reset, and not moved on by the time it was skipped. A module runs if a path of cables or modulation assignments leads from it to one of these:
   - the audio output;
   - a probed output, such as a meter or scope on screen ([telemetry](telemetry.md));
   - a module with display values, or with a light or meter on its panel ([panels](panels.md)), so its lights tell the truth with no cable. MIDI Note has a gate light, so it hears every note on and off while unplugged, and a cable added later finds no stuck gate;
   - a module with a modulated parameter, whose knob shows a moving live dot ([modulation](modulation.md)).

   A feedback loop that reaches nothing is still in the compile report with its inserted delays, so the canvas shows them, but it does not run. *Why:* the requirement saves CPU in large patches, and a module nobody hears or sees changes nothing the player can tell. *Why these roots:* the specs for telemetry and panels promise that what the screen shows is live, and the specs do not say a light may freeze. *Why pause and not reset:* a player who unplugs and replugs an LFO expects it to keep its settings and phase, not start cold. *Cost:* a paused module resumes with old state. A delay line unplugged at its output and plugged in again a minute later first plays the audio it held a minute ago, where hardware would play the last seconds of its input. A module that will one day have side effects (MIDI out) must count as a root.

9. **A cable change fades over 5 ms** (FR-GRAPH-05). When a schedule swap changes what feeds an input (a cable added, removed, or moved to another output), the input holds the last value it read before the swap and moves in a straight line to the new signal over 5 ms, sample by sample. A modulation assignment that is added or removed ramps its contribution in or out over 5 ms. One that is turned on or off, or given a new depth or polarity, blends its old setting into the new one over 5 ms. A phase input switches, and what it drives fades instead.
   - **Only audio, modulation, and pitch inputs fade** (by the port's `SignalType`). Gate, trigger, and phase inputs switch on the swap frame. *Why:* a ramped gate crosses 0.5 late and fires late, and a ramped phase passes through values that look like wraps.
   - **A phase cable change fades what the phase drives** ([#763](https://github.com/brylie/LoomDSP/issues/763), agreed on the plan for #762, 2026-11-15). When a module's phase input changes cable (plugged, pulled, or moved, including a change between a cable and the oscillator's own phase), the phase still switches on the swap frame, so the wave jumps to its new place at once. Every audio, modulation, and pitch input that module's outputs feed fades from its last value over 5 ms, as if its own cable had changed. That includes the Audio Out input, so an oscillator patched straight to the output fades there. An assignment whose source is that module, onto a continuous parameter, ramps from its held contribution as a moved assignment does.
     - **The fade follows phase cables onward.** A module fed through a phase input by one of those modules counts as changed too, and so on down the chain. So replugging the phase into a Phase Shift also fades the oscillator the Phase Shift drives. Every phase input on the way still switches.
     - Gate and trigger inputs downstream switch, as everywhere in this rule.
     - *Why fade downstream and not the phase:* the phase must stay exact, so modules that share it stay in lock, and a ramped phase looks like wraps. What clicks is the sound made from the phase, so that is what fades.
     - *Why follow phase cables:* phase modifiers often sit between a Phase and the oscillators it drives ([ADR-0042](../adr/0042-unpatched-phase-inputs-are-wired-for-the-player.md)). If only the module whose cable changed faded, a replug one step upstream would still click.
     - *Cost:* everything a replugged phase drives fades, not only audio. An LFO whose phase is replugged makes the cutoff it modulates glide for 5 ms, which is what keeps the cutoff from stepping. A phase cable change that does not move the phase still fades: a short dip in a signal that did not step, as for any moved cable. Two gestures meet this: moving a phase cable to a source with the same phase, and inserting a Phase Shift at offset 0 into a running oscillator's phase cable. Both make a 5 ms dip (accepted by the maintainer, 2026-11-15).
   - **Nothing fades on the first schedule** after a load or a new engine, nor on any schedule swapped in before the engine has played its first block. *Why:* a patch renders the same whether or not it was edited live first, and however many commits it took to load; nobody heard a step before the first block. The output fade-in covers the start ([output safety](output-safety.md)). (Widened on 2026-11-14 from "the first schedule", because a load in the editor can commit more than once before it plays.)
   - The fade state is a fixed slot per input, prepared on the control thread with the schedule. The engine adds no allocation, lock, or wait (AGENTS.md rule 1).
   - Fixed at 5 ms, with no setting. *Why:* long enough to soften the step, short enough that nobody hears it as a fade.
   - **A change between an input's normal and a signal** is a cable change, so it ramps too. That includes a slot swap into or out of an empty Sound source, Envelope, Modulator, or Voice slot, and Remove part on one, inside a stack or not. A swap into or out of an empty Filter or Effect slot is softened by the slot's swap fade instead, in every copy of a stack ([sub-patches](sub-patches.md#empty-slots-agreed-2026-11-14), [ADR-0043](../adr/0043-unpatched-means-normalled.md)). The exception is a removal (Remove part, undo of a swap-in, redo of Remove part) whose fades do not fit the module limit: it adds no swap fade and ramps here over 5 ms ([sub-patches, The module limit](sub-patches.md#empty-slot-swaps-inside-a-stack-agreed-on-the-plan-for-762-2026-11-15)).
   - *Why hold the last value, not crossfade from the old signal:* the old source may be gone, and keeping it running costs CPU for a sound that is leaving. Holding the last value keeps the input continuous, which is all a click needs. The rules above still make the new signal right from its first sample (rules 5 and 6); the fade only softens the step the cable itself makes.
   - **The ramp.** N = 5 ms of frames, rounded, at least 1 (240 at 48 kHz). On the first frame after the swap the input reads the held value exactly. On frame k it reads `held · (1 − k/N) + signal · k/N`. From frame N on, it reads exactly the same samples as the signal. The ramp never makes a value that is not finite on its own; a signal that is already NaN or infinite passes through, as it would with no fade. A held value that is NaN or infinite does not fade: the input switches, because holding it would only spread a broken value into a clean cable (settled 2026-11-14).
   - **What counts as a cable change** (settled 2026-11-14). The input's cable in the graph: plugged, pulled, or moved to another output. Every channel of that input fades: each copy, the right side of a stereo input, and each voice of a bundle input. These are **not** cable changes and do not fade, because rules 5 and 6 already keep the signal continuous, and a fade would put a short dip into a signal that did not step:
     - a delay the compiler inserts, or one that moves;
     - a downmix that appears, or a source that changes width with the same cable.
   - **New and paused modules.** A new module has nothing to hold, so its inputs read their signals from the first frame (rule 4). A new copy of a running module, such as the right side of a module that turns stereo, fades together with copy 0 on an input whose cable changed. A module that resumes after it was skipped (rule 8) read nothing while paused, so on a changed cable it fades from 0.
   - **Which inputs fade.** Audio, modulation, and pitch inputs of every module, the Audio Out input (so pulling the cable to the output fades it out), and the Unit Delay input. Gate, trigger, and phase inputs switch.
   - **The mixers the editor adds** (Sum, Stereo spread sum, Select, and Swap fade; [sub-patches](sub-patches.md)). A mixer's inputs carry any signal, so whether one of its inputs fades follows the first source upstream that is not a mixer. A gate through a Sum switches. If either the old or the new source of a mixer's input carries a gate, trigger, or phase, that input switches. An input's own gate, trigger, or phase port always switches. A Select's member input never fades.
     - **An exact rewire switches.** Moving a cable onto a new mixer that plays the old source alone on its first frame switches. So does moving a cable off a leaving mixer that played the new source alone on its last frame. This covers the start and the finish of a slot swap, Single to Layer of one member, and Single to Select. A running fade on that input goes on toward the new source.
     - **A Layer that adds members.** When a Layer of one member gets more members, the cable moves onto a new Sum at gain 1. It switches, and each new member fades in from 0, as a new cable does.
     - **Every other change of mixer fades once.** A stack going from 1 copy to 2 (without stereo spread; with it, the Stereo spread sum is there already at one copy, so the new copy's cable into it fades in), or from 2 to 1, and Layer to Select fade from the held value to the new output, whose own inputs read their signals from the first frame. There is never a fade into a fade. A slot swap during a fade fades too, so the step the first fade had left is softened.
   - **Modulation assignments** (settled 2026-11-14). The contribution, `depth · source` in the parameter's 0 to 1 range, fades:
     - **Added:** it ramps in from 0.
     - **Removed:** its last contribution is held and ramps to 0.
     - **Moved** to another source: from the held contribution to the new one. **Moved** to another target: it ramps out on the old parameter and in on the new one.
     - **Turned off or on, or a new depth or polarity** ([#762](https://github.com/brylie/LoomDSP/issues/762), agreed on the plan for #762, 2026-11-15; the maintainer chose to fade the setting, 2026-11-15): the old setting blends into the new one over 5 ms, and the source keeps playing through the blend. On frame k the contribution is `old(s) · (1 − k/N) + new(s) · k/N`, where `s` is the source's sample on that frame, and `old(s)` and `new(s)` are what each setting makes of it: the depth times the source after the polarity's remap, or 0 when off. So off fades the live modulation out, on fades it in, and a depth change glides the depth in a straight line. It is the same from the inspector, the matrix, and an arc drag, and undo or redo of one of these changes fades the same way. These changes still do not recompile: the blend starts at the next buffer. From frame N on, the contribution is exactly what the new setting gives, so an assignment turned off or set to depth 0 adds exactly nothing ([modulation](modulation.md), rule 9).
     - **A change while a blend runs** starts a new blend from where the running one is, so a depth drag that sends many changes glides the depth and never steps. This holds whichever started the first ramp: a schedule swap or an earlier change.
     - *Why:* to a player, turning a modulation off and removing it are the same gesture, so both must be click-free, and both must end on exactly nothing. They reach it in slightly different ways. A removed assignment has no source any more, so it holds its last contribution and ramps to 0. A turned-off assignment still has its source, so its modulation keeps moving while it fades out. With a slow source the two sound the same; with an audio-rate source they differ slightly during the 5 ms. Fading the setting also makes a depth change glide the depth exactly, where holding a value would freeze the source for 5 ms on every step of a depth drag, a flutter at audio rate. Depth and polarity are settings of the same contribution, so one rule covers all three.
     - An assignment from a gate or a phase source onto a continuous parameter ramps too. The target is a value, not a gate.
     - **Exceptions, each with its reason.** A whole-number or choice parameter switches, because a ramp across separate values adds steps instead of softening one. An assignment onto a module that is new in this swap applies from the first frame, so a new part, a paste, or an undo plays its modulated value at once (rule 7). An exact rewire through a mixer switches, as above.
   - **A panic ends every fade** at its silent frame, so nothing from before the panic reaches the modules it resets ([panic](panic.md)).
   - **A swap while a fade runs.** If the cable did not change again, the fade goes on where it was. If it changed again, a new fade starts from the value the input read last, so nothing steps. When two swaps land before one block, the middle schedule never ran. An input that was already fading keeps that fade's held value, an input that read a fixed default holds that value, and anything else holds 0, as for rule 5's delays.
   - **What still steps.** A player meets these, each for its reason:
     - gate and trigger inputs, which switch for the reason above. A module that turns a phase into gates or triggers may fire early, late, or not at all when its phase cable changes, because the phase jumps;
     - a phase that jumps with no phase cable change, such as a Select switching between members that make different phases: what it drives is not faded, because no phase cable changed;
     - a phase cable change in the same commit as an edit that adds a module on the phase path, such as a mode change that adds a mixer: the fade stops at the new module, which has nothing to hold, so what lies past it still steps;
     - a Unit Delay module on a phase path: its input is an audio port, so it fades, and the oscillator after it reads a ramped phase for 5 ms, heard as a short sweep through the wave (a known limit, accepted by the maintainer, 2026-11-15);
     - a module that picks another source in its own code when an input has no cable, such as a sidechain;
     - the extra voices a module's bundle input stops reading when the bundle gets narrower, such as lowering a voice count while notes ring ([#764](https://github.com/brylie/LoomDSP/issues/764)); the audio output fades the voices it loses;
     - deleting the Audio Out module itself: the output stops at once;
     - Single to Select, or Select to Single, made within 10 ms of a Member change, or while a MIDI control is moving Member: a small step, because the Select may not be playing the member the editor expects. A modulated Member is not a step: the output fades;
     - two swaps before one block, for an input that was not already fading;
     - a fade passes through every value between the old and the new signal, so where a module treats some value in between in a special way, the player hears it for a moment. A Selector's `select` can briefly play the inputs between the old and the new choice, and a Divide's B moved across 0 briefly divides by a very small number: a burst of up to a few milliseconds, longer the louder A is. Output safety holds it under -1 dBFS, and its limiter then recovers over 100 ms.

10. **Staged modules are retried when the queue has room** ([#416](https://github.com/brylie/LoomDSP/issues/416)). When a commit has more new modules than the bounded command queue can hold, the rest are staged on the control side, as today. While anything is staged, a watcher thread reads the queue's free space every 10 ms and wakes the UI when there is room for the next staged module. The UI then commits again. The watcher stops when nothing is staged. *Why a watcher:* the audio thread may not signal a waiting thread, because that takes a lock (AGENTS.md rule 1). Reading a counter from another thread is safe, and the app already wakes this way for audio state and MIDI learn.
    - The longest wait after the engine makes room is one audio buffer plus 10 ms.
    - A queue that stays full causes no compile and no repeated attempt: the watcher wakes the UI only when free space grows.
    - A staged module stays staged until it is committed; nothing is lost. The status bar keeps saying how many modules are waiting, and the undo step for the edit is recorded once, when the edit was made.

### How rule 9 handles assignment changes and phase cable changes (Agreed on the plan for #762, 2026-11-15)

The technical design for the two parts of rule 9 added for [#762](https://github.com/brylie/LoomDSP/issues/762) and [#763](https://github.com/brylie/LoomDSP/issues/763). Rule 9 says what the player hears. This section says which types change, where the work runs, and what happens at the edges. #763 reuses the input fades rule 9 already has (`Ramp`, `InputFade`). #762 gives the contribution ramps on `ModSource::Live` their own type, which blends one setting into another. Neither adds a thread, a lock, or an allocation on the audio thread.

#### Assignment changes (#762)

The maintainer chose to fade the setting (2026-11-15). The old setting blends into the new one, and the source keeps playing through the blend (rule 9, Turned off or on).

- **A setting is a straight-line map of the source sample.** A setting turns the source sample `x` into `depth · remap(x)`, which is `g·x + h`. `AssignmentRuntime::map()` gives `(g, h)`:

  | Setting | g | h |
  |---|---|---|
  | Off, depth 0, or a silent source | 0 | 0 |
  | Follows the source, or forced to the polarity it already has | depth | 0 |
  | A bipolar source forced unipolar, `(x + 1) / 2` | depth / 2 | depth / 2 |
  | A unipolar source forced bipolar, `2x − 1` | 2 · depth | −depth |

  Depth is clamped to -1 to 1, and NaN becomes 0 (`clamp_depth`), so `g` and `h` are always finite.
- **Contribution ramps get their own type, `ContributionRamp`** (`cable_fade.rs`): `g0` and `h0`, the map it blends from, plus a position and a length. `InputFade` and `ModSource::Leaving` keep `Ramp`. On frame `p` below `N`, with `t = p/N`, it gives `hold_finite(old · (1 − t) + new · t)`, the two-weight form `Ramp` uses, with `hold_finite` (ADR-0037). Here `old = hold_finite(g0·x + h0)`, and `new` is what the current setting gives, worked out as today: `depth · remap(x)`, or 0 when off. From frame N on it gives `new` exactly, so after the blend the contribution is bit-identical to the new setting. When `g0` is 0, `old` is `h0` and `x` is not read, so a NaN source never reaches a ramp that blends from a held value.
- **Two ways to start one.**
  - **From a value:** `g0 = 0` and `h0 = last`. A swap's fresh ramp starts this way (an added, moved, or #763 contribution), and gives the same values as today's `Ramp`. A `last` that is NaN or infinite gives a finished ramp, so the contribution switches, as a held input value does (rule 9, The ramp).
  - **From a setting:** a change of settings, below.
- **`ModSource::Live`** holds `ramp: Option<ContributionRamp>`, `last: f32`, `planned: bool`, and `fresh` as today. That is three floats per source (`g0`, `h0`, `last`) beyond today's ramp position.
  - **A slot on every source onto a parameter that ramps.** Today `ramp` is `Some` only when the compile planned a fade. It becomes `Some` (finished) for every source onto a continuous parameter: not a whole number or a choice, and not `shapes_graph`, the test `add_contributions` uses today. It stays `None` only where the parameter switches. An assignment onto a module that is new in a swap gets a slot too. The swap applies it from the first frame (rule 9, Exceptions), and a later change blends. *Why:* a change can come at any time after the compile, and only a slot prepared on the control thread can start a ramp without allocating.
  - **`last`** is what the source added to the parameter's 0 to 1 position on the last frame it ran, after its ramp. `fill_param` (`engine.rs`) writes it every frame, and writes 0 when the source adds nothing. *Why it is still needed with a setting blend:* a fresh ramp at a swap starts from a value. A `Leaving` source has no buffer to read, and a swap whose old schedule never ran (`frames == 0`) has no frame to read either.
  - **`planned`** is true when `FadePlan` fades the contribution (`FadePlan::contribution` gave `Some`). `Schedule::fade_keys` lists only planned contributions, so the controller's carried list does not grow with every assignment, and `a_disabled_assignment_s_ramp_still_ends` passes unchanged. `EngineStats::cable_fades_settled` keeps its meaning: it reports when the fades a swap started have ended. A ramp a command starts later does not reopen it, and needs no carried key, because every continuous source has a slot.
- **`AssignmentRuntime` gets `played`**, the settings its sources' ramps head for (depth, enabled flag, and polarity), and a `changed` flag. `Command::UpdateAssignment` writes the new settings, as today, and sets `changed`. It starts nothing itself. After the whole command batch, before the block, and only when a flag on the schedule says some runtime changed, the engine makes one pass over every fill's sources. For each `Live` source with a slot, it reads its runtime with `assignments.get(state)`, so a stale index cannot panic, and acts when that runtime is marked changed:
  - If the settings equal `played`, nothing starts. So a batch that ends where it began (A, then B, then A) is bit-identical to no command, and so are the same values sent twice.
  - Otherwise the source starts a ramp from where it is. Its from-map is `(g0, h0) · (1 − t) + map(played) · t` at its current position `t`, or `map(played)` when its ramp has ended.

  After the pass, every changed runtime's `played` takes its settings, and its flag clears. That includes a runtime with no slot on any source, such as one onto a whole-number parameter, which switches. Then the schedule's flag clears, so a stale flag never makes a later batch start a ramp. The pass costs one visit per source, however many assignments changed, and allocates nothing. Every copy, side, and voice of the target starts on the same frame.
  - *Why after the batch:* several commands in one batch act as one change. A ramp started on each command would blend A back into A through the map, which rounds differently from `depth · remap(x)` in the last bits, so A, B, A would not come out unchanged.
  - Before the engine has played its first block (`frame == 0`), nothing starts, and `played` takes the settings. Nobody heard the old setting, as for rule 9's first schedule.
  - An id the running schedule does not have is ignored, as today. The next compile reads the graph, which already holds the new values.
  - `Leaving` sources with the same id are left alone. They ramp to 0 anyway.
- **A change while a ramp runs** starts from the running blend, as above, whichever started it: a swap or an earlier change. A blend of two finite maps is finite, so `g0` and `h0` stay finite.
- **Off, past its ramp.** A silent source whose ramp has ended is skipped, as today, not multiplied by 0, because 0 · NaN is NaN. From frame N on, off adds nothing, and the fill keeps the base value's bits again ([modulation](modulation.md), rule 9).
- **A schedule swap.** `take_contributions_from` (`cable_fade.rs`) matches each `Live` source with the old one by fill key and assignment id. Every lookup into the old schedule, the old fill and source and the old runtime for `played`, goes through binary search and `.get`, as `contribution_of` does today, so a stale index cannot panic on the audio thread; a source whose old runtime is not found counts as having no old match.
  - **Fresh** (`FadePlan` fades it): a ramp from a value, the old source's `last` (`contribution_of`). `played` is the new settings.
  - **Not fresh, and the old runtime's `played` equals the new settings:** the old ramp carries on. `continue_from` copies `g0`, `h0`, and the position.
  - **Not fresh, and the settings differ:** a ramp from a setting, from the old source's blend with the old runtime's `map(played)`, as after a command. Undo and redo of a settings change reach the engine this way. They remove the assignment and restore it with the same id and the other settings (`crates/loom-app/src/undo.rs`), and the commit swaps the schedule. The same holds for the copies' assignments `sync_modes` restores in a stack. *Why compare in the engine, not in `Wiring`:* a command changes settings without a compile, so `Wiring` can hold settings the engine no longer plays. A depth drag and then its undo would compare equal there, and step. The engine compares what plays with what arrives.
  - **No old match:** a right side or a new copy takes `last`, `g0`, `h0`, and the position from the same assignment on its fallback fill (the left side, or copy 0), as `cable_fade::fallback` does for inputs, so both sides blend together. This runs as a second pass over the fills in `fill_order`, after the first pass has settled every matched source, as `take_state_from` fills pending input fades. It never runs inside the mutable loop over `new.fills`. A fallback fill is found by binary search on its key, and the source on it by binary search on the id. Anything with no fallback starts finished, with `last = 0`.
  - **`Leaving` is always value-based.** A `Leaving` source carries on only from an old `Leaving` source. One whose old source was `Live` starts fresh from that source's `last`. A map ramp is never carried into a `Leaving` source.
  - `last` is copied for every matched source, so a fresh ramp in a second swap before any block still starts from what played.
  - `contribution_of` reads `last` for a `Live` source, whether or not the old schedule ran. That fixes two gaps in the old reading. It applied the current settings to the last frame, though a command in the same batch may have changed them since. And it returned 0 for a silent source whose ramp was still running.
- **Panic** ends these ramps with every other fade, on its silent frame (`cable_fade::finish_all` ends every `ContributionRamp`). A change in the first block after the silent frame blends from the setting that played before. The output is still fading in from silence there ([panic](panic.md)), as it is for a swap at that point.
- **What the player sees.** The live value table reads the fill, so the live dot follows the ramp, though 5 ms is shorter than one drawn frame. Turning off a knob's last enabled assignment removes its dot at once, by the "No dot" rule. The arc and the ring show the new setting at once ([modulation](modulation.md), Editing and removing). The accessibility tree sends live values at most every 250 ms ([UI layer](ui-layer.md), section 7), so a screen reader hears no change from the ramp.
- **Cost.** One store per source per frame for `last`, and during a blend one more multiply and add for `old`. A parameter with no assignment is not touched. The modulation groups in `cargo bench -p loom-modules` (`crates/loom-modules/benches/engine.rs`) gain two cases: one that sends an `UpdateAssignment` every block, so the cost of a depth drag is measured, and one that changes many assignments in one batch, so the cost of the pass over the sources is measured too.
- **Block size and determinism.** Commands are applied before a block, ramps start after the batch, and each ramp steps once per sample. So a change that lands on the same frame gives the same output at every block size.

#### Phase cable changes (#763)

- **Where it runs.** In `FadePlan::new` (`compile/fades.rs`), on the control thread, after the two loops that fill `fresh` and before `old_reads` is worked out from `fresh`. That order matters: a voice only the old schedule read gets its fade slot only if its input is in `fresh` by then. Nothing changes in `compile/build.rs`, `cable_fade.rs`, or the engine. The walk only adds inputs to `fresh` and contributions to `live`, and the fades built today do the rest.
- **The seeds.** A module that was in the last schedule's wiring, one of whose inputs that carries a phase changed cable: plugged, pulled, or moved. The compare is the same as for every other input (`previous.cables` against the graph), so the change between a cable and the oscillator's own phase is a seed too. "Carries a phase" means the port's `SignalType` is `Phase`. On a mixer the editor adds, whose ports carry anything, it means `Carried` finds a phase upstream for the old or the new source. An exact rewire, or a Layer that adds members, is not a change (rule 9, The mixers the editor adds), so a slot swap or a change of mode never seeds the walk.
- **The walk.** From each seed, follow every cable out of the module. For each input it reaches, on a module that is not new in this compile:
  1. If `input_fades` says the input fades (by the port's type, or for a mixer by what it carries), add it to `fresh` and stop there. The reader's input is continuous, so what the reader makes is continuous too.
  2. Otherwise, if the input carries a phase (as for a seed), the reader becomes a seed and the walk goes on from it.
  3. Anything else switches, and the walk stops there: a gate or a trigger, a Select's `member` input, and any input of an unknown module. "Carries a phase" reads the port with `descriptor.inputs.get(port)`, so an unknown module's placeholder, which has no ports, is never a phase, and the walk never indexes past a descriptor.

  The walk uses a worklist and a visited set, not recursion, so a long chain cannot overflow the stack. Each module is visited once, so a loop through phase cables ends, and the cost is linear in the cables. The walk needs to know who reads each module's outputs, and `Graph::cables` maps inputs to outputs. So it builds that index once, and only when there is a seed. A compile with no phase change does no extra work.
- **Assignments.** An assignment whose source module is a seed, onto a parameter that ramps on a module that is not new, joins `live` as fresh (`add_contributions`), as a moved source does. So it ramps from what it added last to its new value. The walk does not follow assignments: a parameter changes how fast a phase runs, not where it is.
- **A phase output into an audio, modulation, or pitch input** fades, by step 1, because the port decides, as everywhere in rule 9. So a phase played as a sound, or used as a ramp on a modulation input, does not click.
- **No fade on top of a slot's swap fade.** A slot swap's own rewires are exact rewires, so they switch, and the swap fade alone softens them ([sub-patches](sub-patches.md#empty-slot-swaps-inside-a-stack-agreed-on-the-plan-for-762-2026-11-15)). If the walk reaches the `a` or `b` input of a running swap fade, that input fades by step 1. That softens a step in one of the two signals the fade blends. It is not a second fade on the swap.
- **A known limit: a Unit Delay on a phase path.** A Unit Delay's input is an audio port, so step 1 fades it, and an oscillator after the delay reads a ramped phase for 5 ms. Rule 9 already does the same when that cable itself is replugged. A phase through a Unit Delay module is rare. A delay the compiler inserts is not a module, so it does not count.
- **Copies, sides, and voices.** `fresh` holds inputs, and every channel of a fresh input fades (rule 9, What counts as a cable change), so every copy and voice of a reader fades together.
- **Determinism.** The walk runs over sorted maps on the control thread, so a compile gives the same set every time. The fades it adds are ordinary rule 9 fades, so block-size invariance and the no-allocation rule hold as they do today.

#### Tests

- **#762** (`crates/loom-modules/tests/cable_fade.rs`). The target is a parameter whose module outputs it, such as the Add `offset` the existing assignment tests read, so the test reads the contribution through `ParamSpec::denormalize`. The source moves: a Sine at a known rate, whose sample `x_k` on each frame the test knows. A held source would pass a test that holding the value also passes, so it cannot tell the two designs apart. Each case is checked at block sizes 1, 77, and 512, against values the test works out from the rule, within 1e-6 (the map rounds differently from `depth · remap(x)` in the last bits):
  - Off, on, a depth change, and a polarity flip each give `old(x_k) · (1 − k/N) + new(x_k) · k/N` on frame k, and from frame N on exactly what the new setting gives. Off then adds exactly nothing, and the parameter keeps its base bits.
  - **A drag:** five depth changes 800 frames apart, each of which ends before the next, and five 100 frames apart, each of which starts from a running blend. Both are checked against the exact sequence of blends.
  - A, then B, then A in one command batch, and the same values sent twice: bit-identical to sending nothing.
  - A change before the engine's first block: bit-identical to a patch loaded with the new setting.
  - A swap during a blend carries it on with no step. A swap and a change in the same batch blend from what played.
  - **Undo and redo:** `remove_assignment` and then `restore_assignment` with the same id and another depth, then a commit, blend the setting (`a_restored_assignment_with_new_settings_fades_the_setting`). In the app, the undo of a depth change blends too (`crates/loom-app/src/undo/tests.rs`, `undo_of_a_depth_change_fades`).
  - A target that turns stereo during a blend: its right side gives the left side's contribution on every frame.
  - Unit tests in `crates/loom-core/src/cable_fade/tests.rs`: a swap whose old source names a runtime index past the old table, or a fill key the old schedule lacks, counts as no match and does not panic; the second pass gives a right side and a new voice their fallback fill's `last`, `g0`, `h0`, and position; and one batch that changes several assignments starts a ramp on each of their sources and on no other.
  - A source that outputs NaN: the parameter stays finite, and a blend from a NaN `last` switches. A whole-number parameter switches.
  - A panic during a blend ends it on the silent frame. `a_disabled_assignment_s_ramp_still_ends` passes unchanged.
  - `no_alloc.rs` sends a burst of `UpdateAssignment` during a blend and during a swap's fade.
- **#763** (`cable_fade.rs`, and unit tests of the walk in `compile/fades/tests.rs`). The click threshold's measure, an error under -40 dBFS against the ideal continuation, cannot pass here. The ideal is the oscillator at its new phase from the swap frame, and the fade holds the old output on its first frames, so the error is as large as the jump. The criteria check the ramp instead: with output safety Off, frame k of the Audio Out input is `held · (1 − k/N) + new · k/N`, where `new` is the Sine's output at its new phase, and from frame N on it is exactly `new`. That also shows the phase switched on the swap frame: a ramped phase would not give `new`. The walk's unit tests check which inputs join `fresh` for a direct replug, one through a Phase Shift, a gate downstream (not added), a loop through phase cables (it ends), an exact rewire (nothing added), and an unknown module downstream of a replugged phase (it switches, and nothing panics). One more test fails if the walk runs after `old_reads` is worked out: a 4-voice phase bundle into a Sine, replugged to a mono phase, so the Sine narrows to one voice. Audio Out's voices 2 to 4 then fade out from their held values, where without their fade slots they would stop at once.
- **Tests #763 changes.** `gate_trigger_and_phase_inputs_switch_on_the_swap_frame` asserts no fade and output equal to the ideal from the swap frame for a Sine into Audio Out. After #763 that Audio Out input fades. The phase case there moves to the ramp check above, and its gate and trigger cases stay. Any other test that replugs a phase cable while it renders and expects no fade must change the same way.
- **Load.** A patch rendered from load stays bit-identical (`tests/reference.rs`, `tests/patches.rs`): nothing fades on the first schedule, and the walk starts only from a phase cable that changed.

### Click threshold

The measurements compare what the engine plays with the ideal continuation: what the patch would play if the new path had been running all along. An error that peaks above -40 dBFS (0.01) counts as a click. One below -60 dBFS (0.001) counts as inaudible. *Why:* a one-sample error near -40 dBFS is audible over quiet material, and -60 dBFS is below the noise of most rooms. The numbers are a test tool, not a perception study. A listening check confirms them (see Acceptance criteria).

## Out of scope

- **Keeping the state of a deleted module for undo.** Undo of a delete creates a new instance (rule 4). A later change could hand the old state over through the same method as ADR-0022.
- **Replacing a module with a newer version** while it plays.

## Open points

1. **Time to copy large state.** Copying a 2 second delay line takes tens of microseconds. A chain of many long delays turning stereo at once adds up inside one buffer. Watch it with the engine benchmark when MT-DELAY-02 lands. If it is too slow, the copy could be spread over several buffers while the right side still plays copy 0's output, which would need its own rule.
