# UI Layer Specification

How LoomDSP's own UI layer turns events into messages, decides what to rebuild, lays out and draws panels, moves keyboard focus, and exposes an accessibility tree, for the desktop app and for other tools that use the layer.

- **Kind:** living specification.
- **Status:** Agreed (2026-11-09). Each section gives the phase of [the plan](../dev/leaving-iced-plan.md) that first builds it. The text crate, agreed as a decision rule, was chosen at plan step 2.4: Parley (section 8, rule 8). Phase 4 (removing Iced, plan steps P0 to P8): Agreed (Brylie, 2026-11-25 and 2026-11-26); each part names the decision it rests on.
- **Decision behind it:** [ADR-0041](../adr/0041-own-ui-layer.md), superseding [ADR-0009](../adr/0009-ui-stack-iced.md) for the window and widgets, and [ADR-0028](../adr/0028-app-accessibility-waits-for-iced.md). ## Goal

A blind musician opens a patch with VoiceOver on. They hear the toolbar, move into the inspector with Tab, hear "Cutoff, 800 hertz, slider", and turn it with the arrow keys. A sighted user beside them sees the same focus ring move. An agent drives the same app through the control channel, and a test checks the same thing headlessly.

All three work because one runtime, one set of view models, and one identity scheme sit under the window, the accessibility tree, the control channel, and the tests. This specification says how that layer behaves. A view looks the same after each phase unless a change to it is decided and listed in its pull request (design goal 5).

## Design goals

**Status:** Agreed (Brylie, 2026-11-19). These hold for every section below.

1. **Iced was a starting point, not a constraint.** We move away from its design, conventions, and output step by step, as views move. We never copy its implementation, code, or APIs (ADR-0018, and ADR-0041's decision for a UI layer of our own). A bridge shaped like Iced is temporary, and goes in phase 4. *Why:* a design copied from a general toolkit would carry its limits into ours, and copying its code would break the clean room.
2. **It is a UI system for LoomDSP's audio tools, not a general desktop toolkit.** It serves patching, live play, and the tools beside them, and adds only what they need. *Why:* a general toolkit pays for every case; ours pays only for its own, such as a canvas, live values, and a screen reader on every control.
3. **Every target is first class:** a web browser (`wasm32`), a CLAP or VST3 plugin inside a host's window and event loop, and the stand-alone app on Windows, macOS, and Linux. A design that assumes it owns the window or the event loop, that it can reach the system synchronously, or that one platform's convention holds everywhere says so and gives its reason. *Why:* each assumption made for one target is work to undo for another (OQ-13 for plugin windows, NFR-PORT-01 and NFR-PORT-04 for the web, and [OQ-23](../product/open-questions.md#oq-23-accessibility-for-a-ui-drawn-in-a-browser-canvas) for accessibility in a browser canvas).
4. **Accessibility from day one.** Every widget gets its role, name, focus, keyboard path, and contrast in the change that adds it, never later. *Why:* NFR-UX-01 and NFR-UX-06, and a widget added without them is a widget some users cannot use until someone goes back.
5. **The parity gates catch change no one meant.** A deliberate move away from today's look or behaviour is allowed once it is decided and listed in its pull request. *Why:* the gates keep the app working while it moves; they are not a promise to match Iced.

## Words

| Word | Meaning |
|---|---|
| **App** | The program built on the layer. For LoomDSP, `loom_app::App`. The layer knows it only through a trait. |
| **Runtime** | The code that takes events, calls the app, runs effects, rebuilds what changed, and asks for redraws. The same code in the window and in the harness. |
| **Driver** | What feeds the runtime events and shows its output: the `winit` shell, or the headless `Ui` harness. |
| **Message** | The app's own type for "something happened that may change state". The only way app state changes. |
| **Effect** | A plain value the app returns from `update` asking the shell to do something outside the app: focus a field, use the clipboard, open a dialog, run work off the UI thread, quit. |
| **View model** | A plain-data struct the app builds from its state, describing what one panel shows (ADR-0021). |
| **Panel** | A part of the window with its own view model and its own place in a layer: the toolbar, the stats bar, the inspector, the module browser, an overlay. The unit of rebuild. |
| **Element** | One node of the tree a panel builds from its view model: a row, a button, a slider, a text. Elements are rebuilt when their panel is rebuilt. |
| **Widget state** | State that belongs to one element and lasts across rebuilds: hover, pressed, scroll offset, caret and selection in a text field, an open list. Not app state. |
| **Live value** | A value that changes at display rate while audio plays: a meter reading, a light, a live modulated position, a scope trace, the audio load. |
| **Custom element** | An element that owns its own drawing, input, and accessibility nodes, such as the patch canvas. |
| **Layer** | A stacking level of the window: canvas, panels, overlays, question. |
| **UI ID** | The stable identity of an element across rebuilds. |
| **Logical pixel** | A window pixel before the display's scale factor. On a Retina display at scale 2, one logical pixel is two physical pixels wide. |

Rules:

1. **`loom-ui-core` and `loom-ui` know nothing about patches.** They never depend on `loom-core`, `loom-patch`, `loom-canvas`, or `loom-app`, and they use no patch words in their API. *Why:* other tools should be able to use them, and publishing them later (FR-SDK-06) should not need a second refactor.
2. **The runtime and the shell take the app as a trait or a generic parameter,** never as `loom_app::App`. *Why:* the same reason.
3. **Each crate has a crate-level doc comment and an example program that does not use LoomDSP.** *Why:* the example proves rule 1, and it is the first documentation a new user reads.
4. **The engine crates never depend on UI crates.** `loom-core`, `loom-dsp`, `loom-modules`, `loom-patch`, and `loom-rt` stay portable (AGENTS.md, hard rule 6).
5. **Every new crate passes `cargo deny check` before it is used** (ADR-0006).
6. **All Iced code during the move lives in the bridge.** `loom-ui` never depends on Iced. The runtime lives in `loom-ui` from phase 2, and the bridge plugs Iced's views into it as one more drawing and routing target per layer. An element still drawn by Iced gets an `iced::widget::Id` made from the text form of its UI ID (section 4, rule 5), so focus and scroll effects reach the same element in both toolkits. *Why:* one place to delete in phase 4, and no Iced type can leak into the crates meant for reuse.
7. **From phase 4, no crate names Iced** (plan step P5). No `Cargo.toml` names an `iced*` crate, and the lock file holds none. `deny.toml` bans the `iced*` crates (`[bans] deny`), so `cargo deny check` in CI fails if Iced comes back, directly or through another crate. There is no test that scans sources for Iced names: with Iced out of the dependencies, no source can name it and build. The Iced rules in `loom-app`'s and `loom-canvas`'s `tests/purity.rs` go, and those files keep their other rules. `rfd` keeps a rule of its own: only the app's dialog file names it. **Agreed** (Brylie, 2026-11-26, changed from a source scan). *Why:* the bridge's rules limit where Iced may be named; once it is gone, the dependency ban keeps it out. `rfd` stays a dependency, and keeping it in one file keeps the dialogs in one place for the plugin and web drivers to replace.

### Keys in `loom-ui-core` (phase 4, plan step P2)

**Status:** Agreed that `Key` gains F1 and F2 and that a key event carries the physical key, so behaviour stays the same on every keyboard layout (Brylie, 2026-11-25). The shape below is **Agreed** (Brylie, 2026-11-26).

The app's key handlers take `loom_ui_core::{Event, KeyEvent, Key, Modifiers}` from P2 on, not Iced's types. Three things they read today have no `loom-ui-core` value: F1 (help), F2 (enter a matrix cell, row 4e), and the physical key, which the Outline's cable following reads (`[` and `]`, and Cmd+`[`). **Built in P2:** the app's key handlers, the listeners (`input_owner.rs`, `subscriptions.rs`, `panic.rs`, `controls.rs`), the menus' and the Outline's keys, the shortcuts in `lib.rs`, `Message::Key`, `Message::Input`, and the control channel's `key` and `type` take `loom-ui-core` values. Iced still delivers until P4, so one function turns each event Iced hands the app into ours (`subscriptions::Listeners::messages`), and a key the control channel or the harness makes up goes to Iced through `iced_convert::key_event_to_iced`. The close request and a dropped file reach the app as the runtime's window events (`App::window_event`, `subscriptions::window_message`), no longer as Iced's. No handler reads modifiers on a release (rule 4 holds). Before P2 the shell mapped F1 to `Key::Other`; row 4e added `Key::F2`. Built in P2: `Key::F1`, `Code` with `KeyEvent`'s `code` field, and their mapping in the shell (`shell/events.rs`) and in the bridge's conversion (`iced_convert.rs`). For tests and scripts, `Modifiers` gains `SHIFT`, `CONTROL`, `ALT`, `META`, `platform_shortcut()` (Command on a Mac, Control elsewhere, through `Platform`), and `|`.

1. **`Key::F1` and `Key::F2`,** beside `Key::F10`. If row 4e adds `Key::F2` first, P2 keeps it as it is. Other function keys stay `Key::Other` until something uses them (the rule of `Key::Other`).
2. **A physical key on every key event.** `KeyEvent::Pressed` and `KeyEvent::Released` gain `code: Code`, where the key sits on the keyboard, named by its place on a US layout. The names are the W3C UI Events `KeyboardEvent.code` values (a standard, so no toolkit's list is copied): `Code::BracketLeft`, `Code::BracketRight`, and `Code::Other` for any key nothing reads yet. A code is added when a handler needs one, as a `Key` is. Browsers deliver these same names in `KeyboardEvent.code`, so a web driver passes them on with no table.
3. **A handler matches by meaning, not place,** with one exception: a pair of keys whose meaning is their place, as `[` and `]` for "follow the cable back" and "forward", which sit side by side on every layout even where they type other characters. Those match `code`. Everything else matches `Key`. *Why:* a shortcut named by a letter must follow the letter on a French or German layout; a pair named by where it sits must not.
4. **`KeyEvent::Released` gains no modifiers.** P2 checks that no handler reads them on a release; if one does, it takes them from the last `ModifiersChanged`, and this rule changes in the same pull request.
5. **The control channel's `key` names do not change.** A scripted `[` carries `Code::BracketLeft`, as the US layout gives it, so a script behaves the same on every machine (section 10, rule 6).

## 2. The runtime: events, messages, and effects

**Status:** Agreed, phase 2.

### Behaviour

One turn of the runtime:

1. An **event** arrives from the driver: a pointer or key event, IME, a file dropped on the window, a resize, a scale factor change (the window moved to another display), window focus gained or lost, a close request, a redraw request, an animation frame (section 3, rule 8), word that the last frame was shown, a wake-up from another thread (a watcher, background work, or a screen reader's action), or a deadline that has passed. The driver passes the moment with it; the runtime never reads the clock.
2. The runtime **routes** it (sections 5 and 6). The element that takes it either handles it as widget state, or turns it into a **message**. Window events with no element (a file drop, a close request) become messages directly.
3. For each message, the runtime calls **`update`** once. `update` changes app state and returns **effects**.
4. The runtime **runs the effects** after `update` returns, before the next message's `update`: each message's effects run right after its own update. An effect that produces a message (a dialog closed, a clipboard read, background work finished, a frame shown) queues it for a later turn.
5. The runtime asks each panel whether its view model changed, and **rebuilds** only the panels that did (section 3).
6. It redoes **layout** for rebuilt panels, updates the **accessibility tree** for changed nodes, and asks the driver for a **redraw** only if something visible changed.
7. With nothing queued, no animation frame asked for, and nothing visible to change, the loop **sleeps** until the next event or deadline.

The contract the app implements, as built in plan step 2.1 (`crates/loom-ui/src/app.rs`). It is designed from what LoomDSP and the tools beside it need, not from Iced's `Task`, `Subscription`, or widget operations. Phase 3 adds the builder that makes a panel's elements, and `View` then gains the message type.

```rust
pub trait App {
    /// The only way app state changes. `Send`, since watchers send it.
    type Message: Send + 'static;

    /// Applies one message and returns its effects.
    fn update(&mut self, message: Self::Message, cx: &Context<'_, Self::Message>) -> Effects<Self::Message>;

    /// Describes the window, one panel at a time: a key, a layer, a model.
    fn view(&self, view: &mut View);

    /// The title and limits, compared after each update like a panel model.
    fn window(&self) -> WindowSpec;

    /// When to wake with no event, and the message to get then.
    fn next_deadline(&self) -> Option<Deadline<Self::Message>> { None }

    /// The message for a close request or a dropped file, if any.
    fn window_event(&self, event: &WindowEvent) -> Option<Self::Message> { None }

    /// True while something moves: a frame each display refresh, no update.
    fn animating(&self) -> bool { false }
}

// Inside `view`. Phase 3 adds a builder after the model.
view.panel(UiId::panel("inspector"), Layer::Panels, &inspector_model);
```

`Context` gives `update` the moment (`now`), a `Waker` for watcher threads, the element with focus, and the window's size, scale, and focus, all read only. `update` reads focus there in the same turn, instead of asking for it with an effect and waiting for the answer.

### Effects

The table covers every use of Iced's `Task`, its widget operations, and `rfd` in `crates/loom-app/src` at commit `a781de4`, and what replaces each (`Task::none` and `Task::batch` become an empty and a combined `Effects`). A new kind of effect is added here first. Each is a variant of `loom_ui::Effect`, and each has a stable name that a driver's panic text uses.

| Effect | Used today by | What the shell does | What the headless harness does |
|---|---|---|---|
| Focus an element, by UI ID, or the next or previous one, optionally selecting all of a text field, or no element (section 6, rule 1). The UI ID may name an inner part of a custom element (section 9, rule 6) | Focusing a field, Tab between fields (`editing.rs`, `StepFocus`); opening a field for typing selects all; Tab out of a field on the main view, and a screen reader moving to the canvas, take focus from every field (`editing::unfocus_text_fields`); later, Enter on an outline row focusing a tile control | Moves keyboard focus | The same |
| Scroll an element into view | The module browser and patches lists, a matrix card and its cell (`matrix.rs`) | Moves the nearest scrolling area around the element just enough to show it, on each axis on its own; an element larger than the area shows its top-left. | Write the clipboard | Copy, Cut | Writes the system clipboard | Writes its in-memory clipboard |

| Messages for the next turn, as one batch (2026-11-13) | What the player chose through another part that names a message of its own: Enter on a menu item, a screen reader's action, a control command's UI messages, each followed by what must come after them (a step's release, the command's reply). `App::post` collects them and `update` returns them as one effect | The runtime queues them itself, after what wakers have sent so far, so each is its own update on the next turn, in order, and no other thread's message lands among them | The same |
| Draw again although no panel model changed | A request handed to a custom element that it applies when it draws, such as a screen reader's Focus action on the canvas | Draws | Counts the draw |
| Quit | Quitting (`iced::exit` in `lib.rs`) | Ends the loop | Marks the app as exited |
| Accessibility tree | The tree for a screen reader, the whole tree and what changed, while one listens (`a11y.rs`, section 7, rule 7) | Keeps the whole tree, and hands the platform's adapter the changes, or the whole tree when it has none yet (rule 11) | Keeps the whole tree, for a test to read |

Not effects, because nothing needs them as effects:

- **Which field has focus.** `update` reads it from its `Context`. Iced needed a round trip (`Message::TextFocus`) because it keeps focus inside its widgets. Under the bridge to Iced (plan step 2.1, item 2), the context holds Iced's last answer, and the app hears of each answer as `Message::FocusMoved`. Undo, redo, Tab between a view's fields, and the control channel's `type` keep the round trip until the phase 4 cut-over (plan step P4), as window questions (below), when the window's root is the runtime's and the answer is known in the same turn.
- **The window's title and limits.** The app describes them in `App::window`, and the runtime passes them on only when they change, as with panel models.
- **Timers.** Nothing uses a one-shot timer; every periodic check is a deadline from state (rule 8). A timer effect can be added when something needs one.
- **A message queued for the next turn** (`Task::done`). It makes a chain of updates, which rule 6 rules out. Inline results come from work, and "after this turn is drawn" is the after-draw effect. One case is not a chain, and is an effect: what the player chose through another part, which names a message of its own (the next-turn effect in the table). Each of its messages is its own update on the next turn (rule 5), as a click on the part would be. A step that must come after them is in the same batch, after them: a screen reader step's release, which closes its undo group, and a control command's reply, which reads what its messages changed and then waits for the draw (`Message::ControlReply`). The control channel reads its next command only after the last one's reply (control channel, rule 5), so no other command's messages come between.

**Under the bridge, input is routed before `update`, and the window answers questions.** Until the `winit` shell, Iced's listener hears window events, so the bridge routes each one before `update`, as the runtime's routing target does for core events: each message an event becomes is its own update in that turn, after the messages already waiting. `update` never sees the raw event, and a debug build checks that it does not. Until the phase 4 cut-over (plan step P4), three things the app needs are known only to Iced's widgets: which part has focus, where a text or a named part is (the control channel's `locate` and `screenshot`), and where every named part is (the accessibility tree). The app asks them as window questions (`App::ask_window`, `window_question.rs`). The bridge takes them after the turn, runs Iced's widget operations, and hands each answer back as a message on a later turn, in the order asked. The `Ui` harness answers them the same way on its own view, and `App::send`, which has no window, drops them. They are not effects: the runtime never carries them out, so `loom-ui` names none of them. They go in P4, with the window's root, the canvas's place, and its live camera, which the last of them reads (Agreed, Brylie, 2026-11-25: these move in phase 4, not in row 4e).

**Under the bridge, deadlines wake the loop through a sleeper, and frames stand in for "shown".** Iced wakes only for an event, a subscription's message, or a frame, never at a chosen time. So the bridge keeps one long-lived thread for the window: it waits on a condition variable for the deadline the last turn gave, and calls the runtime's wake function once that time comes. A deadline that moves every turn changes only the time it waits for and starts no thread. A deadline already due runs at once, as before. Iced reports when a frame begins, not when it is on screen, so while a message waits for a frame to be shown (`Runtime::waits_for_draw`), the bridge listens to Iced's frames and sends `DriverEvent::Presented` for each. It comes just before Iced draws that frame, so it can be a frame early. The exact event comes with the `winit` shell, which sends `Presented` after it has presented the frame's surface. The frames that run `update` until phase 3 (`Frame` while measuring, `LiveFrame` while modulation plays) are deadlines at display rate (section 3, rule 8).

**On the shell, Iced draws as the window's layers** (plan step 2.2b-ii, `iced_bridge/window.rs`). The `winit` shell owns the window, the runtime, the deadlines, and `Presented`, which it sends after the frame's surface is presented, so the sleeper and the frame stand-in above are the `Ui` harness's only. Iced keeps three jobs until P4. After each turn, the layers run one Iced update over the window events since the last, post the widgets' messages and then the listeners' (`subscriptions::Listeners`, as the app stood before the events), each routed before `update`, and run the turn's widget operations and window questions. A focus answer is delivered alone, after what was queued, as the bridge did (`Report::alone`). A control channel's scripted key goes as the keyboard's does (`Report::input`, plan 3.2, row 5, 2026-11-24): each report hands the shell one, Iced keeps its copy as it keeps a real key's, the shell runs the runtime's turn for it, and the next report lets Iced hear it unless the runtime took it. Before, scripted keys went to Iced alone, so a field of the runtime's never heard them. Each frame, they run Iced's redraw update, draw, and present; its messages run on the next turn, since the layers only read the app while they draw. A capture presents the last frame again, with no update, as Iced's screenshot did, and waits for the first frame to be shown. A window task the layers cannot finish is logged once and dropped; the harness panics on it.

**From the phase 4 cut-over (plan step P4), there is no bridge.** **Agreed** (Brylie, 2026-11-26). The four paragraphs above describe the app until P4, and P7 removes them.
- The app implements `loom_ui::App` itself. Nothing wraps it.
- The window's root is a panel of the runtime's: the canvas (a custom element, section 9), the rule beside it, the right column, and the stats bar's rule, laid out by section 5's layout.
- The shell's layers are the app's own, drawn in section 9, rule 8's order. There is no routing target: every event is the runtime's, so section 5, rule 10's late answer (`Routed::Later`) and the redraw after any update (rule 10) go with the bridge. `--measure-idle` may then count fewer frames; P4 records the counts before and after.
- Window questions, `Message::FocusMoved` from Iced, the sleeper, and the frame stand-in go. `update` reads focus and layout from its `Context` in the same turn.
- The `Ui` harness runs on `loom_ui::headless`: it lays out with the `Typesetter` the window uses, so section 10, rule 3 holds with no measuring renderer of Iced's, and captures draw to an offscreen `wgpu` texture.
- A window event the shell hears (a file dropped, a close request) reaches the app through `App::window_event`, as the trait already says.

**Dialogs take two turns.** Until plan step 2.1, item 2, `files.rs` and `recovery.rs` called `rfd`'s dialogs inside `update` and blocked until they closed. As effects, the question is one turn and its answer is the next, so the app holds what waits on the answer (`dialogs.rs`): what an Open or Save dialog is for, with what was asked after the save (Close, New, Open), the save that waits for the credit question, and the crash copy the recovery question offers. The recovery question is asked once the window is open, from a deadline due at once while a copy waits ([autosave](autosave.md), The offer at start). One dialog waits at a time: a second request while one waits is dropped. What waits keeps the patch it was asked about, by the session's number (`PatchSession::id`), which only New, Open, and a restore change; not the engine's generation, which a device change also moves. A save's or a credit's answer that arrives after the patch was replaced is not used, so a Save As never writes a newer patch to the place chosen for an older one. Open's answer is used, asking first about the new patch's unsaved changes, and so is the recovery question's, since it is what replaces the patch. The window still shows each dialog to its end, outside `update`, blocking and modal, as under Iced. The two turns make room for the loop to keep running while a dialog is open, so meters, telemetry, and the accessibility tree would not stall, once dialogs are macOS sheets (`rfd`'s `set_parent`), a later pull request (plan step 2.2).

### Rules

1. **The app keeps the Elm architecture:** one message type, one `update`, no second path that changes app state. *Why:* undo, autosave, the control channel, and the tests all rely on every change passing through one place. Splitting state changes across callbacks would make each of them miss some changes. ([research](../research/2026-11-ui-change-propagation.md#the-elm-architecture))
2. **An effect is a plain value, not a future.** Background work is a closure the shell runs on a worker thread, not an async task. *Why:* the harness can see each effect and run it or refuse it, so no test passes by skipping one.
3. **A harness that cannot run an effect panics, naming it.** *Why:* a silent skip would let a test pass that the real app fails.
4. **The harness runs background work inline and in order.** *Why:* tests stay deterministic, and a test never waits on a thread. The patches browser already reads its folder this way under test.
5. **One message gives one `update`.** Effects run after it returns. An effect never calls `update` again in the same turn, and a message produced by an effect waits for the next turn. *Why:* chains of updates in one turn are hard to predict and hard to test.
6. **Derived values are computed in view model builders,** not through chains of messages or effects. *Why:* the same reason. A value that follows from state is a function of state.
7. **Threads wake the loop through a waker.** The control channel listener, the MIDI learn watcher (`learn.rs`), the audio input watcher (`input_watch`), the audio stream watcher (`audio_watch`), the telemetry monitor, and background work send messages through it. The waker queues the message and calls the driver's wake function: in the `winit` shell that nudges the `EventLoopProxy`; in the harness it does nothing, since the harness drains the queue itself. A watcher takes its waker from `update`'s `Context`, and the app keeps the watcher's handle in its state: the watcher lives as long as the handle, and dropping the handle stops it. Dropping a handle never blocks the UI thread. It signals the thread and detaches, or joins only a thread known to end at once. *Why:* the loop then sleeps until something happens, rather than polling for it. Holding watchers as state, not as a list of subscriptions restarted by key, makes their lifetime the lifetime of what they watch (an engine, a stream, a listener). A watcher stuck in a MIDI or audio call must not freeze the window on New or Open.
8. **Periodic checks become deadlines, and a deadline that changes nothing costs nothing.** These stay periodic: the device poll (`AudioPoll`, every 250 ms), the MIDI port poll (`MidiPoll`), the MIDI ghost check (`MidiGhosts`), the 500 ms `Tick`, the autosave check (`Autosave`), the drop-out check (`DropsDone`), and the accessibility layer's live value timer (`LiveTick`). Each wakes the loop and runs `update`. The app keeps when each is next due in its state (`timers.rs`): after every update a check starts a period from now while its condition holds and stops when it does not, and its message moves it on by a period from when it was due, or makes it due at once when that has passed, so the time a turn takes does not add up from one to the next. `App::next_deadline` gives the earliest, or the crash recovery question when it comes first. When its message changes no view model, it causes no panel rebuild, no accessibility update, and no redraw. *Why:* these checks poll the operating system, which has no event for them. NFR-PERF-04 asks for no redraw while nothing visible changes, which holds even while the loop wakes.
9. **The driver is a trait, and the runtime and the `App` trait use no `winit` type.** No `EventLoop`, `EventLoopProxy`, `ControlFlow`, `Window`, or `winit` event reaches them. The runtime takes events as `loom-ui-core` types, returns the next deadline, and asks the driver to redraw or to apply window commands. Two drivers exist after phase 2: the `winit` shell and the headless harness. *Why:* a plugin's window belongs to the host, and the host runs the event loop. `winit` owns the process's one event loop (on the main thread on macOS), so it is not expected to serve inside a plugin; plugin GUIs use host-window backends instead. The OQ-13 spike confirms which. A third driver for a host window must then be possible without changing the runtime. Otherwise the contract carries the kind of cost section 3, rule 5 warns about.
10. **A turn draws only when something visible changed.** The turn's result tells the driver to draw (`Next::draw`; the runtime never calls the driver to draw, so a shell cannot turn its own redraw request into a loop) when a panel's model differs from the last (section 3, rule 2), when the routing target says it needs a draw, when an effect asks (draw again, a message after the next frame, a capture), or when the system asks. An animation frame draws and runs no update. Nothing else draws. A frame the driver asked its window system for is drawn when it comes, with no redraw request sent for it, and several turns that say to draw before then make one frame. A resize or a scale change draws through the redraw request the window system sends after it; a driver whose system sends none sends one itself. After each frame is on screen the driver says so once, and only for a frame that began after the latest turn that said to draw, since a message waiting for the next frame arrives then. Until the phase 4 cut-over (plan step P4), the routing target for the views Iced still draws is the bridge, and it says it needs a draw after any turn that ran an update. That is Iced's own habit, kept inside the bridge and deleted with it. Measured on `main` at `085f217a`, `--measure-idle` on `subtractive.ron` drew 266 frames in 10 s, 263 of them for meter messages and none for polls, so this keeps today's cost exactly. *Why:* the runtime must not hard-code one toolkit's habit, and no `update` path may write its own "did this change?" guard (section 3, rule 2). The saving comes in phase 3, when each view is a compared panel and meters are live values.
11. **The runtime never reads the clock.** Every turn takes the moment from the driver, and `update` reads it from its `Context`. *Why:* a test then decides what time it is, and a deadline test runs in no time at all.

## 3. Change and cost model

**Status:** Agreed, phase 3. Rule 7 also applies to the accessibility tree built in phase 1 (section 7, rule 7).

This section answers "what changed, and who depends on it?" The background is in the [research snapshot](../research/2026-11-ui-change-propagation.md).

### Rules

1. **The panel is the unit of rebuild.** One panel has one view model. When a message changes nothing a panel shows, that panel's elements, layout, and accessibility nodes are not rebuilt. *Why:* the per-panel view models of ADR-0021 already match what each part of the window reads. A finer unit adds bookkeeping; a coarser one makes every change cost the whole window.
2. **The runtime decides whether a model changed, by comparing it with the last one.** View models implement `PartialEq`. A large model may hold its data in `Arc` and compare with `Arc::ptr_eq`. No call site writes its own "did this change?" guard. *Why:* a guard that each call site must remember will be forgotten somewhere, and the cost of forgetting is a full rebuild that no test notices.
3. **A panel's model is built from the narrowest input that gives what it shows.** The toolbar does not read the graph; the inspector reads the selected module, not the whole patch. *Why:* a model built from a large shared struct changes whenever anything in it changes, which defeats rule 1.
4. **Widget state does not go through `update`.** Hover, pressed, focus rings, the caret, its blink, text selection, scroll offsets, and an open list redraw their element only. They reach the app only when they mean something: a click, a committed value, a focus change the app asked to know about. Hover reaches the app only from an element that asks for it (`Element::reports_hover`): `App::hovered` on the next turn, once each time the pointer comes onto it, and only from the pointer's own move or press, never from a layout that moves the element under a still pointer (plan 3.2, row 5, 2026-11-24). A browser's row is the case it is for: there the pointer moving onto a row moves the highlight, as the keys do, so the hover means something. *Why:* in the frameworks the research looked at, hover and typing cost as much as a real data change when they went through the app.
   - **A click** (Brylie's decision, 2026-11-17) is a left press and a left release over the same keyed element of the runtime's. The press holds while the pointer leaves the element and comes back, so letting go on it still clicks, as on macOS and Windows; a release anywhere else cancels it, and so does the pointer leaving the window or the input layer rising above the element (section 5, rule 10). The app turns a click into a message by UI ID, through `App::clicked`, as it turns a screen reader's Click action on the same node into one (section 7, rule 6). The message runs on the next turn. Keyboard activation calls `App::clicked` too, so the pointer, the keyboard, and the screen reader give one message (plan 3.2, row 1): Enter on a focused button clicks it when the key goes down, and so does Enter on a focused link, which Space does not click (section 8, rule 10). Space on a focused button or switch clicks it when the key comes up (Brylie's decision, 2026-11-17), as HTML buttons and the platform toolkits do: Escape, any move of the focus (Tab, a press, a focus effect, the toolkit taking the keyboard, even away and back), or a press of the pointer while Space is held cancels it, and the release then clicks nothing. The release clicks only an element that can still be clicked then: in a layer that takes input, turned on, and offering Click. A pointer press cancels a held Space with or without a position; the pointer leaving the window does not, since no focus moved. While the canvas has the keyboard (`InputState::canvas_focused`), Enter and Space are the canvas's: they activate no element of the runtime's, even one that still has the runtime's focus. A key held down clicks once; its repeats do nothing. A turned-off element is no focus stop (section 6, rule 2), so no key reaches it. *Why:* it is the platform convention, and one message by UI ID keeps `Element` free of the app's message type.
   - **A menu item is activated as a button is** (plan 3.2, row 3a): Enter on a focused menu item clicks it when the key goes down, and Space when it comes up, through `App::clicked`, so a menu's pointer, keys, and screen reader give one message as the toolbar's do. A pointer press on it takes no focus, as on a button (section 6, rule 3): it picks the item on release, and the menu closes. *Why:* a menu item is a button in a list; the keys that press a button must press it too, and one rule in `loom-ui` (`activatable`) keeps the two from drifting apart.
5. **The contract has a boundary below the window from the start.** `view` builds panels by key, never one undivided tree. The first version may still rebuild more than it must. *Why:* a cost built into the API cannot be fixed later behind it. Faster code inside the runtime can remove work; it cannot remove a call the contract requires.
6. **Nothing redraws while nothing visible changes.** A blinking caret is allowed, though none is built yet: today's caret is steady (section 8, rule 2). One that blinks redraws only its own element, only while a text field has focus and the window is focused. *Why:* NFR-PERF-04, and the control channel's rule that the app sleeps when idle.
7. **Live values are not part of panel models.** Meter readings, lights, live modulated positions, scope traces, and the audio load live in a live value table that the app updates from the engine. An element that shows one reads the table when it draws, and is redrawn, not rebuilt, when it changes. The canvas already works this way: panel control values have their own GPU buffer (`PanelValues`), so a moving meter never rebuilds tiles. *Why:* these values change at display rate while audio plays. In a panel model, they would rebuild that panel 60 times a second, and an "equal message rebuilds nothing" check would pass while the real cost went unmeasured.
8. **Animation frames are asked for, not constant.** An element that shows moving live values asks the runtime for animation frames while they move, and stops asking when the engine is idle or the element is off screen. The runtime delivers one frame event per display refresh, only while some element asks. This replaces Iced's `window::frames()` subscriptions `Frame` and `LiveFrame`. `ControlFrame` is replaced by section 2's message once the next frame is shown. Until the live value table lands (rule 7, phase 3), live modulated positions and the audio input check move by a deadline at display rate that `App::next_deadline` returns only while modulation moves. It runs `update`, as `LiveFrame` did; an animation frame still runs none. `Frame` while `--measure` runs is the same kind of deadline, since its `update` records the frame meter and collects garbage; the meter moves to draw time with rule 7. The display rate is the window's frame period (`WindowState::frame`). The `winit` shell reads it from the monitor's refresh rate at start, and again when the window moves or its scale changes, since it may then be on another display. A driver that cannot read it, such as the headless harness, keeps 16 ms. *Why not the table now:* the meters need the same table (#730), and one value kind alone would bring rule 7 into phase 2 for no saving, since the deadline costs what `LiveFrame` costs today. *Why:* frame-rate drawing costs nothing when nothing moves (NFR-PERF-04, "a display redraws only while it is on screen").

### Measuring it

The runtime counts, per turn: messages, panels compared, panels rebuilt, panels and elements laid out, keys dropped as duplicates, accessibility nodes sent, animation frames, and redraws. `--measure-idle` reports these counts beside its existing rebuild counts and causes. *Why:* a cost model that is not measured drifts. The counts also make rules 1 and 7 testable.

### Rules

1. **One identity scheme serves five uses:** widget state, keyboard focus, accessibility node IDs, event routing, and the control channel's `locate`. *Why:* if each use had its own scheme, they could disagree about which element is which. A screen reader would follow one element while the keyboard moved another.
2. **A key names its kind where a module shows more than one kind of item.** The kind is one of `param`, `exposed`, `display`, `input`, `output`, and `badge`, as the control channel's prefixes already name them. An instance's exposed "Cutoff" and the inner module's "cutoff" row then never share a key. A flat ID needs no level beside it: the flat ID table is keyed by path and never gives an ID to something else while the patch is open ([flattening](../learn/flattening.md)). *Why:* that table already lets the canvas, the selection, and undo work across levels, so identity can rest on it too.
3. **Elements in a list that can change are keyed by a stable domain ID, never by position.** *Why:* by position, removing one row moves every later row's state, focus, and accessibility node onto its neighbour. ADR-0021 recorded this limit in Iced's `keyed_column`.
4. **An accessibility node ID stays the same while its element exists,** and is not reused for another element in the same run. The runtime keeps a table from UI ID to the 64-bit AccessKit node ID. It gives out IDs from a counter that only increases, and removes an entry when its element is gone; if the same UI ID comes back later, it gets a new node ID. *Why:* a screen reader keeps its place by node ID, and a reused ID would make it read the wrong element. Removing entries keeps the table the size of the window, not of the session. The spike packed a module ID and a widget index into 64 bits, which works for tiles but not for rows and overlays.
5. **A UI ID can be written as text,** and that text is what the control channel's `locate` accepts beside its existing names. The text is the keys joined by `/`: `canvas/4/param/cutoff`, `canvas/5/badge/out`, `toolbar/undo`, `inspector/4/param/cutoff`.
   - A key made only of digits is a number. Any other key is a name.
   - Inside a name, `/` is written `%2F` and `%` is written `%25`, so a library item's path stays one key: `browser/list/library/pads%2Fwarm`.
   - A name made only of digits has its first digit escaped, so it does not read back as a number: the name `12` is written `%312`.
   - Writing a UI ID and reading the text back gives the same UI ID, for every UI ID. A test checks it.
   - The control channel's short names, such as `4:cutoff`, keep working beside it.
   - `locate` takes a target for a UI ID when its first key is a panel's name: `canvas`, `toolbar`, `breadcrumb`, `panel`, `inspector`, `matrix`, or `stats`, or an overlay's: `menu`, `recent`, `question`, `help`, `browser`, `patches`, `preferences`, or `licence`. If it reads as a UI ID but names nothing the window shows, `locate` still looks for the target as text in the window before it fails. Any other target is a short name or text, as before.
   - On the canvas a UI ID resolves to where the accessibility tree puts that node, and a port or a badge to where its short name does, since tiles give no port nodes yet (section 7, rule 19). Outside the canvas it resolves to where the window drew the part. A part scrolled out of view is an error, because a pointer sent there would land on something else.

   *Why:* agents, tests, and people then use the same names. A path reads like the tree it names, and one escape rule keeps every ID readable back.
6. **An element's UI ID is its panel's key, then the keys of the keyed elements around it, then its own key** (`Element::key`). An element with no key adds nothing to the path and has no UI ID of its own. *Why:* wrapping a part in another row or stack, for layout, then changes no ID, so focus, widget state, and the screen reader's place stay where they were. So an ID under another is inside it on screen, always: `loom-ui` offers no way to key an element by a path, or to give it an ID its nesting does not make (2026-11-25, the decisions row on how the inspector's parts are keyed). *Why:* code reads "under" as "inside" (which panel owns an ID, which overlay a node is in), and one exception would make every such check a trap.
7. **Two elements with the same UI ID are a mistake in the panel's code.** In a debug build, the layout panics, naming the ID. In a release build, the first element in tree order (the order the panel built them, parent before children) keeps the ID. Every later one is laid out and drawn, but has no UI ID, and nothing inside it has one either, since each would name a place inside the first element. They are out of the bounds by UI ID, hit-testing, and, later, focus and the accessibility tree, and the pointer passes through them to the nearest keyed element around them. The layout counts every key dropped this way (`Layout::duplicate_keys`). *Why:* a debug build should stop at the mistake. A release build should not crash a performance over it, and the same model must always give the same result, which tree order does.

## 5. Layers, hit-testing, and who has the input

**Status:** Agreed, phase 2. Rules 5 to 9 are built in phase 3 (plan step 3.1: `layout.rs`, `hit.rs`, `window.rs`, `draw.rs`); no view uses them yet. Rule 12 is built in plan 3.2, row 4a (`layout/scroll.rs`, `window/scroll.rs`); no view uses it yet. Rules 13 to 15 (placement, a press outside, a shadow) are built in plan 3.2, row 3a, for the overlays. Rules 16 to 18 are built in plan 3.2, row 4b (`slider.rs`, `select.rs`, `Element::slider`, `Element::checkbox`, `Element::select`), and rule 18's step's start in row 8 (`Select::steps_from`); no view uses them yet.

### Behaviour

The window has four layers, drawn bottom to top: **canvas**, **panels** (toolbar, breadcrumb, inspector, stats bar, module browser), **overlays** (probe menu, recent files, licence chooser, help), and **question**. A layer is drawn by whichever code owns it; during the move, by Iced or by `loom-ui`.

### Rules

1. **A pointer event goes to the topmost layer first,** and down to lower layers only if no element in that layer takes it. *Why:* the user sees the top layer on top, so it must take the click. This holds while two toolkits draw (rule 10).
2. **The app decides who has the input,** as today (`App::input_owner`, `Overlays::owner`). The layer asks the app; it does not keep its own idea of a modal panel. The runtime asks through `App::input`, which gives the lowest layer that takes input and whether the canvas has the keyboard (`InputState`); the bridge maps the input owner onto it: the question is the Question layer, every other panel or menu over the canvas is the Overlays layer, and nothing open is the Canvas layer. *Why:* one owner of this rule, so the canvas, the keys, and the accessibility tree all follow the same answer.
3. **While a panel owns the input, the layers below it are hidden from the accessibility tree** and take no screen reader actions. *Why:* the spike left canvas controls in the tree under an open browser, where a screen reader could reach controls the pointer could not.
4. **Layout is in logical pixels, and hit-testing and layout need no GPU.** *Why:* the harness tests events on machines with no GPU, and the control channel answers in logical pixels.
5. **Sizes follow flexbox's defaults** (decided 2026-11-14), through `taffy`. Our `Length` sets only what it names, and the rest is flexbox's default (basis auto, shrink 1, minimum size auto):

   | Ours | What it means |
   |---|---|
   | `Fill(n)` | Along a row's or column's main axis, grows by n shares of the space left after every item's content size. So two `Fill(1)` items with different content end up of different sizes. Across that axis, and in a stack, it stretches to fill |
   | `Shrink` | The content's size, shrinking when the space is too short |
   | `Fixed(px)` | `px` when there is room. It also shrinks when the space is too short, as flexbox's default does |

   No item shrinks below its narrowest content: its longest word, or its widest fixed child. Across a row or a column, an item with no alignment set stretches, as in flexbox. A stack is a grid of one cell that holds every child, so it is as large as its largest child. A wrapping row is a row with `flex-wrap`, its spacing also between its lines. *Why:* Brylie's words: "flexbox defaults are fine. We can do sub-pixel rendering when it becomes an issue. We're moving away from Iced so don't need to preserve its behavior." Flexbox's meanings are published and widely known, so a reader can check a layout against them, and `taffy` is tested against them. Views may move by a few pixels when they leave Iced; [the plan's parity gates](../dev/leaving-iced-plan.md#parity-gates) say how that is checked.
6. **Layout rounds to whole logical pixels,** with `taffy`'s rounding: each edge is rounded from its place in the panel, never each width, so neighbours meet with no gap and no overlap. At a scale factor of 2, every edge therefore lands on an even physical pixel. That is accepted, and not worked around: placing at half a logical pixel waits until it shows up as a problem. *Why:* the same decision.
7. **Hit-testing reads the layout:** the deepest keyed element under the point is hit, a later sibling over an earlier one and a child over its parent. A point over an element with no key hits the keyed element around it. An opaque element takes the point, so nothing under it is hit, even where it holds no keyed element. Rectangles are half-open, so a point on a shared edge hits exactly one element. Clipping cuts hits as it cuts drawing (rule 9): a part outside the clip of a clipping element around it, or outside its panel's slot, is not hit. Across layers, the topmost is tried first (rule 1). *Why:* the order matches what is drawn on top, and a panel over the canvas must take the clicks the user aims at it. A part the user cannot see must not take a click.
8. **The window is laid out first, then each panel inside the place it gets** (decided 2026-11-14).
   - A panel's elements may hold a **slot**, `Element::slot(key)`, which names another panel of the same layer: its child, laid out inside the slot's box. A panel that no slot names is a **root** of its layer, laid out at the window's size. The window's own model (which panels are open, which tab is shown) is the model of an ordinary panel made mostly of slots, so it rebuilds only when that model changes (section 3, rule 1).
   - A panel lays out only its own elements, in a layout it keeps across rebuilds. Its bounds are kept relative to its own origin, and the slot's place is added when a bound is read. So when only a parent rebuilds and a slot keeps its size, the child is not laid out again. When the slot's size changes, the child is laid out again with no rebuild.
   - **A slot that fills or is fixed is sized by its parent alone:** it has no content size, and its child is never asked. This departs from the flexbox defaults of rule 5, for slots only, where a fill item grows from its content. A **shrink slot** asks its child how large it is, so when only the child rebuilds, the parent is laid out again only if the child's measured size changed. A size change moves up through every enclosing shrink slot. A panel that comes into a slot or leaves one lays its parent out again, though the parent did not rebuild.
   - **Draw order is hit order.** Each layer draws its roots in `view` order. After each root come the panels in its slots, in slot order, each after all of its parent's elements, so a child panel is over any element its parent puts after the slot. Hit-testing (rule 7) tries panels in the reverse of that order: a later root of a layer is over an earlier one and everything in its slots. Several roots in one layer are each laid out at the window's size, and overlap.
   - A new order of panels, or a panel in another slot, is drawn as a changed model is, even when no model changed, and reads wait for the next layout.
   - Layout runs when the driver asks (`Runtime::lay_out`), before it draws or reads a place, not in the turn: the driver holds the text that measures. In a debug build, `Runtime::bounds` and `Runtime::hit` panic when something changed since the last layout, so a stale read cannot pass unnoticed.
   - A slot that names its own ancestor, a panel in another layer, or a panel another slot already holds is a mistake: in a debug build it panics, and in a release build the first slot in view order holds the panel, and the first panel of a loop becomes a root.

   *Why:* the panel is the unit of rebuild (section 3, rule 1), and this makes it the unit of layout too: a change inside the inspector lays out the inspector, not the window. Keeping each layout relative to its slot is what lets a parent move a child without touching it. Sizing a fill or fixed slot by its parent alone keeps a child's content from moving the window around it, and is the only way a change to the parent alone can leave the child untouched. One order for drawing and hitting means the user clicks what they see on top.
9. **Panels draw from the composed layout** (decided 2026-11-16). `Runtime::paint(layer, painter, style)` paints one layer's panels into a `TextPainter` (`draw.rs`), in the draw order of rule 8, which is the reverse of hit order.
   - **Look.** An element sets only what it names: `.background(colour)`, `.border(width, colour)`, `.radius(r)`, and `.clip()`; text sets `.colour(c)`. An element with a background or a border paints its box first, under what is inside it. A border takes room in the layout, as CSS's does with border-box sizing: the content sits inside the border, then inside the padding. A slot is placed the same way: its panel is laid out and painted in the slot's content box, so a framed slot's panel never covers its frame, and a point on the frame hits the parent.
   - **Text** is painted at the top-left of its content box, so a border of 2 and padding of 4 put it at 6. The content box is rounded as `taffy` rounds a child's place, from the edge inside the border and the padding together (rule 6): a padding of 2.5 puts text at 3, where a child at that edge sits, never at 2.5. A wrapping text breaks its lines at its content width before rounding, the width it was measured at: the rounded width could break a line the measure kept whole, and the extra line would spill out of its box. A text box taller than its lines keeps its text at the top, as flexbox does; centring is the parent's alignment. Text with no colour of its own takes the `PanelStyle`'s text colour. `loom-ui` decides no colour: the app fills `PanelStyle` from its own style tokens, and those tokens are what its contrast tests check (visual-system.md).
   - **Clips are rectangles.** An element that clips opens a layer cut to its bounds, and closes it after its last child. A GPU scissor cannot round, so a clip on a rounded element cuts to its square bounds: a child past the corner's curve and inside the bounds still shows, and is still hit there. A rounded clip waits until a view needs one. Each panel is painted inside a layer cut to its slot and to every clip around the slot; a root is cut to the window. A clip in logical pixels becomes a scissor rounded outward to whole physical pixels, so nothing hit inside the clip is cut away.
   - **One typesetter.** The driver lays out and paints with the same `Typesetter`: `Runtime::lay_out` measures with it, and the painter sets text with it, so what is measured is what is drawn. A driver's drawing code reaches the layout and painting through `Runtime::parts`, which lends the panels (`Panels`) with the app and the target. A layout through `Panels` settles the focus as `Runtime::lay_out` does (section 6, rule 4). When that gives one of the runtime's elements the focus, the target, which the driver holds then, lets go of its own at the start of the next turn, before that turn routes anything, so no key reaches two owners (section 6, rule 1).
   - **Cost.** The walk paints a whole layer each time it is asked, and runs only for frames that are drawn: a still window draws none (NFR-PERF-04). The runtime counts the panels and elements painted (`Counts::panels_painted`, `elements_painted`). If a view shows that the walk costs too much while live values redraw, a panel's paint list is rebuilt only where it changed; not before.
   - In a debug build, painting after a change and before `lay_out` panics, as a read does.

   *Why:* drawing from the same records hit-testing reads, with the same clips, is what keeps what the user sees and what they can click from drifting apart. The look is set on the element, not looked up from a theme inside `loom-ui`, so the crate holds no palette and the app's tokens stay the one place colours and sizes are chosen.
10. **Two toolkits draw and route by layer** (decided 2026-11-17, plan step 3.1, item 2). While Iced still draws part of the window, the runtime's layers sit on both sides of it: Canvas and Panels below Iced, Overlays and Question above it.
   - **Draw order.** A frame clears, draws the canvas, the runtime's panels in the Canvas and Panels layers, Iced's layers, then the runtime's panels in the Overlays and Question layers (`iced_bridge/paint.rs`). Each side has its own `PaintRenderer`, since a renderer keeps the one list it last prepared, so each has its own glyph atlas too. A side with nothing painted prepares nothing and starts no pass, so a window with no panel of the runtime's draws what it drew before. A capture draws the last frame again, preparing again only for a new target, as the canvas does.
   - **Route order.** A pointer event goes to the runtime's layers above the target, then to the target, then to the runtime's layers below it. The target answers `Routed::Taken` (nothing below hears it), `Routed::Passed` (the layers below are offered it), or `Routed::Later`. Iced answers `Later`: it hears the window's events before the runtime's turn and routes them after it, so the bridge hands each pointer event Iced leaves unused to the layers below with `Panels::pointer_below`, the same step the runtime runs for `Passed`. Before Iced hears an event, the bridge asks `Panels::over_target`: over one of the runtime's layers above Iced, a press or a release never reaches Iced, and a move reaches it as the pointer leaving, once. Both halves are one bridge module (`iced_bridge/pointers.rs`), which the window and the `Ui` harness both call. *Transitional, until P4 removes Iced:* on that late path there is no turn to run in, so what a custom element sends there (section 9, rule 1) goes through the waker and runs on the next turn, in the order it was sent, cancels included. On the runtime's own routing it runs in the event's turn.
   - **What a layer that takes a pointer does** is widget state (section 3, rule 4): the element under it is hovered, a press focuses the stop there with no ring, unless it is a button or a switch, which takes no focus from a press (section 6, rule 3), and a press and a release on the same element are a click, which reaches the app as a message through `App::clicked` on the next turn. *Why the next turn:* the late answer comes while the driver holds the runtime's parts in its report, so the message goes through the waker; the runtime's own routing does the same, so every click waits the same one turn.
   - **One layer in one toolkit holds the hover.** A move a layer of the runtime's takes hovers its element, and over a layer above Iced, Iced hears the pointer leave. A move the target takes, or one over nothing of the runtime's, clears the runtime's hover, and so does the pointer leaving the window. A press survives a move the target takes, so dragging across Iced and back still clicks (section 3, rule 4); a left release the target takes ends it, as a release anywhere else does, and so does a left press the target takes (`Panels::pointer_taken`). Hover redraws and runs no update; the runtime keeps it (`Runtime::hovered`), and hover text reads it.
   - **The input layer.** A layer below `App::input`'s layer takes no pointer event and shows no hover, and the event goes on to the target, as it did when Iced's full-window layers held it. A hover or a press in a layer the input layer rises above clears after the update that raised it, so no hover text shows under an open question or panel.
   - **Keys.** Keys go by focus, not by point (section 6). A key the runtime's elements take (Tab among their stops, or a key a focused text field takes, section 8) is kept from the target with `Target::kept`, and the bridge leaves it out of what Iced hears, so one owner acts on it. A release of the focus the runtime owes the target (section 6, rule 1) goes through `Target::release_focus`, which the bridge applies before Iced hears the turn's events, so a key after it never reaches the field that had the focus. The other way round, when one of the target's own elements takes the keyboard (a click on a field, the toolkit's own Tab, a focus answer), the runtime lets go of its focus at the start of the next turn, so the app's context names the target's element (`Runtime::follow_target`). The target's focus only going to nothing leaves the runtime's as it is.

   *Why:* our panels and Iced's never overlap, since a view moves whole from one toolkit to the other, and everything Iced draws over one of ours belongs above the Panels layer anyway. So drawing and routing by layer, with each toolkit in turn, keeps what is on top what takes the pointer at every step of the move off Iced.
11. **Hover text is the runtime's, from the element** (Brylie's decisions, 2026-11-17, plan 3.2, row 1). An element sets its hover text with `Element::hover_text`, and the runtime shows it; no panel of the app's draws it, since hover runs no update (rule 10) and the app's view never hears it. A hover the app heard of ends once (`App::unhovered`, plan 3.2, row 4d): when the hovered element changes, the pointer leaves every element or the window, the input layer rises above it, or the element leaves the layout. One check after each turn and each layout tells it, so every way a hover ends is heard the same way, and never twice. A drop row in the inspector uses it to go dark.
   - **When it shows.** At once, with no delay, as the toolkit's tooltips did: while the pointer is over the element, and while the element has keyboard focus (WCAG 2.2, SC 1.4.13). Where both apply to different elements, the latest input wins (Brylie's decision, 2026-11-17): a focus move shows the focused element's text, and a pointer move over an element, even within the one already hovered, the hovered one's. The order is kept as the inputs happen, not when the text is laid out, so a Tab and a pointer move before one frame count in the order they came (the focus's move count, `Focus::moves`). *Why:* a keyboard user who tabs while the mouse happens to rest on the bar must still see what they moved to.
   - **Escape hides it** without moving the pointer or the focus. It stays hidden until the hover changes or the focus moves, even when the same element's text would show again. Leaving and returning between two layouts also ends the suppression. An Escape that hides hover text does nothing else, except that it also cancels a Space held on the same element (section 3, rule 4): both happen, and the key goes no further. With no hover text showing and no Space held, Escape goes where it went before (section 6, rule 6), and so it does when a held Space could no longer click (the focus moved, or a layer rose above its element): that Space is dropped without taking Escape.
   - **In a menu, Escape closes the menu at once** (Brylie's decision, 2026-11-20), and the hover text of its items goes with it: closing the menu dismisses the text too, which is what SC 1.4.13 asks, and a second Escape to close a menu would surprise anyone used to native menus. This is the one exception to the bullet above. Built with the menus in row 3b.
   - **It stays while the pointer moves onto it,** so text wider than the window's edge, or a long list of port names, can be read: while the pointer hovers its element and is on its box, on its element, or on the strip between the two where they line up. Text shown for the focus keeps nothing, so a move onto its element hovers that element as any move does. Anywhere else, such as a neighbour beside a narrow element under a wider box, the hover moves as it would without the text. It goes when the pointer leaves both the element and its text, when the element goes, when the last pointer point falls outside the box, source, and strip after layout, and when the input layer rises above the element's layer. The strip uses the source's new bounds after layout. A pointer press records its position for this check. A move that changes which hint wins asks for a redraw.
   - **Where.** Above the element, its left edge at the element's, moved in to stay inside the window; below the element when there is no room above. The box and its text come from the app's style tokens through `PanelStyle`, as the rest of a panel's look does (rule 9).
   - **What it is not.** It takes no pointer event except to keep itself open, is never a focus stop, has no node of its own (it is its element's description, section 7, rule 23, from the same string, when the element sets no description and the text adds to its name or value), and does not change `App::input`'s layer. It is drawn in the Overlays layer only so it shows above the panels, or in the Question layer when its element is in a question, so the question's own panel never covers it.

   *Why:* one string for what a sighted user reads by pointing and what a screen reader reads as the description keeps the two from drifting apart. SC 1.4.13 asks that such text can be dismissed, hovered, and kept, and once the runtime paints it itself, each part is a few lines.

12. **A scroll container is the runtime's** (plan 3.2, row 4, part 4a; for the inspector, the matrix, and the licence chooser of row 3). `Element::scroll(child, style)` shows its child, laid out at its own height, through a window as tall as the container, clipped to it. In row 4 it scrolls vertically only; its offset is a vector, so a horizontal one can follow with no change to the API. The offset is widget state (section 3, rule 4), kept by UI ID as a field's editing is: a rebuilt view keeps it, and it goes with the container at the next layout.
   - **The wheel and the trackpad** (`Event::Scrolled`) over the container or anything in it move it. Lines become pixels at three times the line height of the panel's body text; pixels are taken as given. A container that cannot move further in that direction passes the event on to the next container out, then to the target. A wheel over a panel with no container under the pointer is taken where it lands, as before.
   - **The scrollbar shows whenever the content is taller than the container** (Brylie's decision, 2026-11-20), not only while it scrolls: a thumb on the right, drawn from the container's `ScrollStyle`, which the app fills from its tokens (`style::SCROLLBAR_WIDTH` 6 px, `SCROLLBAR_INSET` 2 px from the edge, `SCROLLBAR_RADIUS` 3 px, and `SCROLLBAR_THUMB`, the quiet text colour). The style goes with the container, not in `PanelStyle`, because layout needs it before anything is painted: the content is laid out beside the bar's gutter, never under it, and the style also holds the ring room and the body text's line. A thumb is never shorter than 24 px, so a long content still has one a pointer can grab. No track is drawn, so the panel behind is its track, and the thumb has a contrast of at least 3:1 against it (WCAG 2.2, SC 1.4.11), which a test checks. Dragging the thumb scrolls in proportion; a press above or below it moves one page toward the press. *Why always:* a bar shown only while scrolling hides that there is more to read, which a keyboard user and a sighted user both need to see. macOS hides it by default; Windows and GNOME show it, as Iced did.
   - **Focus moving in brings the focused element into view.** When the runtime's own focus moves to an element inside, by Tab, by an arrow in a radio group (section 6, rule 9), or by a focus effect, and that element is not wholly in view, the container scrolls the least distance that shows it and its ring, with 2 px more to spare. No effect is needed. Nested containers each move, the innermost first.
   - **`Effects::scroll_into_view(id)` for the runtime's elements** is the runtime's: when `id` is inside one of its panels, the runtime scrolls the containers around it as for focus, once its layout is current, and an element in no container needs nothing; otherwise the effect goes to the target, as before (section 2, the effects table).
   - **A container whose content has no focus stop is a stop itself,** so a keyboard user can scroll it (WCAG 2.2, SC 2.1.1): with it focused, Up and Down move one line, Page Up and Page Down a page less one line, Space and Shift+Space a page, and Home and End go to the top and the bottom. A container whose content has stops is none: focus moving does its scrolling, and a scroll key the focused element does not use goes on to the container (section 6, rule 6, step 3). The APG has no scrolling pattern; these are the browsers' keys.
   - **A container can take its keys from a named stop** (plan 3.2, row 4b; for the module browser's results and help's text). `Element::scroll(..).keys_from(id)` names a focus stop in the same panel, such as a search field above a list of results. The container is then never a stop itself, even with no stop inside, because that stop drives it: through the app, which moves its highlight on the stop's keys and asks for the highlighted row with `Effects::scroll_into_view`, as the APG combobox pattern has a list follow its field. It takes no scroll key itself, so the app's keys for the stop (step 4 of section 6, rule 6) always hear them first; a stop's key never scrolls the list under a highlight that stays put. The named stop must be in the panel when it is laid out; a debug build panics when it is not, and a release build reports it as a problem of the panel, as an access problem is (section 7, rule 2). *Why:* a list under a search field is scrolled while the field keeps the keys, as a browser's page scrolls while its find bar has them, and a container that were a stop as well would make Tab stop twice for one list.
   - **A container can scroll from a named stop outside it** (plan 3.2, row 6, built for help). `Element::scroll(..).scrolls_from(id)` is `keys_from` with one difference: a scroll key the named stop leaves unused moves the container, as it would move a container around the stop (section 6, rule 6, step 3). Help's body scrolls from its Close button above it this way. A combobox's list keeps `keys_from`, since there the app moves the highlight. *Why:* help's first focus is Close, outside the body, and a keyboard user must be able to read on from there (WCAG 2.2, SC 2.1.1).
   - **The ring has room.** The content keeps a padding of the ring's reach (`ScrollStyle::ring`, 4 px from `style::focus_ring`) inside the clip, so a focused element at the container's edge keeps its whole ring (section 6, rule 3), and a test checks that no ring inside a container is clipped.

   *Why ours:* the inspector, the matrix, and the licence chooser all scroll, and the runtime must know the offset to keep focus in view, to scroll for the tree, and to cut each part's bounds as it draws them.
13. **An overlay's root panel can be placed at a point or under an element** (plan 3.2, row 3a). Every other root fills the window from its top-left corner (rule 8). An overlay's root may instead say where it goes: at a point in the window, under an element of another panel by its UI ID, its left edge at that element's, read from the layout already made, so the layout does not depend on itself, or centred in the window, on whole pixels, for a panel that belongs to no one place (the cable picker, section 6, rule 8). Either way it takes its content size and is moved in to stay inside the window, by as little as it must, keeping its top-left corner inside when the window is smaller than it. A root under an element that is gone is not placed and shows nothing until the element comes back: it is not hit, and it has no focus stops, so Tab never reaches its parts and a focus on one falls back as when its element goes (section 6, rule 4), keeping the focus visible (SC 2.4.7). *Why:* menus open where they were asked for (the probe menu at the pointer, Recent under its button), and a plugin's window may be small, so placing and clamping belong in the layout, not in each panel's code. Under its button, Recent follows the breadcrumb inside a sub-patch, where a fixed point covered it (Brylie's decision, 2026-11-20).
   - **A root under an element that stops showing is told** (plan 3.2, row 5, 2026-11-24). While its element shows, a root placed `Under` it follows it at each layout, so a menu under a list's row moves with the row as the list scrolls. Once a settled layout finds that element no longer shows (scrolled out of view, cut away, or gone), the app hears `App::anchor_hidden(root)` on the next turn, once; it hears it again only after the element shows and hides once more. The app closes what hangs there: a library row's menu closes with no choice, as a select's list closes when its select scrolls away (rule 18), and the focus, which stayed in the search field, has the keys at once. *Why:* a menu left hanging past the list's edge points at nothing the user can see (Brylie's decision, 2026-11-24).
14. **An overlay can close on a press outside it** (plan 3.2, row 3a). A root that asks for it (`Element::closes_on_press_outside`) hears a press of any mouse button anywhere outside its own elements, while its layer is the input layer: the runtime takes the press, so nothing under the overlay sees it, and tells the app through `App::pressed_outside` with the root's UI ID, on the next turn, as a click is told. A press inside, on an element or on its unkeyed padding, is the overlay's own. With two such roots open, one drawn over the other (a library row's menu over the module browser, row 5), a press inside the lower one closes only the one over it, and a press inside the upper one closes neither, even where it hangs past the lower one's edge. *Why:* a menu closes when the user clicks away, with either button, as native menus do. The press is taken, so a click meant to close the menu does not also select a tile under it.
15. **An element can cast a shadow** (plan 3.2, row 3a): a blurred, offset copy of its rounded box in one colour, drawn under the element. It is cut by the same clips as the element's own box: an overlay's root panel is clipped by nothing but the window, so a menu's shadow can reach past its panel up to the window's edge, while a shadow inside a slotted panel or a clipping container stops at that clip. Its colour, offset, and blur are a token (`style::MENU_SHADOW`, visual-system.md, Overlays), painted as one shape. *Why:* a menu over the canvas must stand apart from the tiles under it (Brylie's decision, 2026-11-20: build it, not drop it). One shape keeps it cheap, and every later menu and popover uses the same token.

16. **A slider is the runtime's** (plan 3.2, row 4b; for the inspector, the matrix's depth, and the stack's spread). `Element::slider(Slider)` draws a track and a thumb for a position from 0 to 1 along its travel, the control's travel and not its value, which the app maps. Its settings say how keys and a drag move it: `key_step` for an arrow key and a screen reader's Increment and Decrement, `fine_key_step` with Shift, `page_step` for Page Up and Page Down, and `drag`, either continuous or snapped to a step of its own. *Why a drag step apart from the key step:* a drag must stay fine while a key moves a clear amount; Iced's slider shared one step between both, so the inspector's arrows moved a tenth of the tile knob's (the decisions row of 2026-11-11). The app keeps the position, as with a field: the slider never keeps a value of its own, and the app's wins at the next layout. A slider can show a ghost mark (`Slider::ghost`, plan 3.2, row 4d): a hollow 10 px ring with a 1.5 px edge in the text colour, where the thumb would be at that position, over the thumb. It takes no press, moves nothing, and adds nothing to the slider's node, so a screen reader hears what it does today, which is nothing of the mark (midi-learn.md, Seeing a waiting pickup, says what it shows). As Iced's inspector drew it, but centred on the thumb's travel, whose 14 px thumb leaves 7 px at each end, where Iced's ring used 5 px: up to 2 px apart at the ends.
   - **It reports `App::slid(id, position, phase)`** on the next turn, with the phase Start, Move, or End. A drag is one Start, its Moves, and one End at release, so the app makes it one undo step, as `SliderReleased` does today. Keys report Start and Move, and End when their group closes, as the panels spec's arrow groups do ([panels](panels.md), Keyboard without a mouse): a repeat and a press within 500 ms join one group, which ends 500 ms after the last key, when focus leaves, or on a pointer press.
   - **A press on the track** sets the position under the press, then drags. **Shift while dragging** is ten times finer, from where Shift went down, and **a double-click resets it to its default**, as on tiles ([panels](panels.md), the gestures table and Interaction), so a player meets the same gestures on a tile and in the inspector. The app gives the default's position (`Slider::default`), and a reset is one Start, Move, and End, so one undo step. Iced's slider had neither.
   - **A press takes focus, with no ring** (section 6, rule 3), so the arrows then fine-tune the slider just dragged.
   - **The wheel never moves it,** with or without a modifier: the wheel over it scrolls the panel, as over anything else (rule 12), since scrolling over a control never changes its value ([panels](panels.md)). *Changed:* Iced's slider stepped with Ctrl and the wheel.
   - **Its look:** a 4 px track and a 14 px round thumb, from `PanelStyle`, which the app fills from its tokens. The part of the track filled runs from the minimum, or from the middle for a range that is centred on 0, such as a modulation's depth. The focus ring goes around the thumb and the track.

17. **A check box is the runtime's** (plan 3.2, row 4b). `Element::checkbox(label, style, on)` draws a 14 px box beside its label. Off, it is empty, with a 1 px border in its edge colour; on, it is filled, with a check mark drawn on the fill (`PanelStyle::check`: `edge`, `fill`, `mark`), as Iced's check box looked since #856 (#463's contrast work). Each pair needs 3:1 (WCAG 2.2, SC 1.4.11): the edge and the fill against the panel, and the mark against the fill. The app sets them from its style tokens. Changed 2026-11-25 (plan 3.2, row 4d): it was a 1.5 px border and a primary mark on an empty box, unlike Iced's boxes. A press on the box or on its label toggles it, and it takes no focus from the press (section 6, rule 3); the toggle reaches the app as `App::clicked(id)` on the next turn, from a press, a key, or a screen reader alike. The app keeps whether it is on.

18. **A select is the runtime's, and so is its open list** (plan 3.2, row 4b; for the inspector's stepped parameters, the matrix, and Preferences). `Element::select(Select)` shows the chosen option's label, and a mark that says it opens. The app gives the options' labels and which is chosen, and keeps the choice: the select never keeps one of its own, and the app's wins at the next layout, as with a field. A choice reaches the app as `App::chose(id, index)` on the next turn.
   - **The list is a panel of the runtime's,** in the Overlays layer, which the runtime adds to the view while the select is open: placed under the select (rule 13), closing on a press outside it (rule 14), with the menu shadow (rule 15). The app declares no panel for it and hears nothing when it opens or closes, only the choice. *Why the runtime's:* an open list is widget state, as a field's caret is (section 3, rule 4), and every select would otherwise need the same panel, keys, and placing written again in the app.
   - **It is as wide as the select, or its widest option, whichever is wider,** and as tall as its options, up to the room below the select, or above it when there is more room there, where it scrolls (rule 12). Opened, it shows the chosen option.
   - **A press on the select opens it,** and focuses the select with no ring (section 6, rule 3). A press on the select while it is open closes it. The pointer moving over an option highlights it, and a press and release on an option chooses it and closes the list. A press outside closes it with no choice, and is taken (rule 14). The wheel over the list scrolls it, and over a closed select scrolls the panel, since scrolling over a control never changes its value ([panels](panels.md)).
   - **Focus stays on the select while the list is open** (section 6, rule 12). The highlight is the list's own, and the select's node points to it (section 7, rule 32).
   - **The list closes on its own, with no choice,** as a press outside closes it: when the select leaves the layout (a rebuild drops it, its panel goes, or it is turned off), when the select is scrolled out of view in its container, when focus leaves it by any path other than Tab, and when an overlay or a question opens over it, such as help on F1. In that last case it closes before the new overlay takes the focus, so the focus comes back to the select, closed (section 6, rule 4). It also closes when the app's options change while it is open, meaning their labels or their number, not a rebuild that gives the same ones. *Why close rather than keep the highlight:* a highlight clamped or moved to a changed list may rest on an option the user never aimed at, and the next Enter would choose it; opening again is one key. The APG is silent on all of these.
   - **The step's start** (plan 3.2, row 8, for Preferences' device lists). The app may name an option other than the chosen one where stepping starts: `Select::steps_from(index)`. The list then opens with that option highlighted, in place of the chosen one, and a screen reader's Increment and Decrement step from it. The select still shows the chosen option, and its node's value is still the chosen option's label. While a step's start is set, a step or a choice that lands on the chosen option is still reported to the app (`App::chose`), as going back to it, so the app can drop its mark of the failure and the next step goes on past it; with no start set, only a choice that differs from the chosen option is reported. *Why:* when a device fails to open, the chosen one stays the device that plays, and a step from it would land on the failed device again, so a keyboard or screen reader user could never reach the devices after it ([preferences](preferences.md#keys-and-focus)).
   - **One option, or none.** A select with one option opens as any other does, on that option. A select with no options is turned off: it opens nothing, is no focus stop (section 6, rule 2), and its node is disabled, with the app's description of why, as for any element turned off (section 7, rule 23).
   - **Its look:** the select is a box with its border and radius, the chosen label, and the mark at its right, from a `SelectStyle` the app fills from its tokens, as it fills `ScrollStyle`. The list is a box with the menu's fill, border, and shadow; the highlighted option has the hovered row's fill, and the chosen one a check mark before its label, so the two are told apart without colour (SC 1.4.1).
19. **A context menu is the app's, and the runtime opens it** (plan 3.2, row 5, 2026-11-24; for a library row in the module browser). An element that has one (`Element::context_menu`) hears a right press on it, and a screen reader's ShowContextMenu on its node, unless a layer above it takes the input (rules 2 and 3), as `App::context_menu(id, by_key)` on the next turn, as a click does. Its node offers ShowContextMenu, whatever order its builder set it in. A right press is `by_key` false and first focuses the stop there as any press does (section 6, rule 3); ShowContextMenu is `by_key` true, so the menu opens on its first item, as one opened by a key does (section 6, rule 8). A menu opened this way and placed under its element closes when the element scrolls out of view (rule 13). The menu key and Shift+F10 are the app's keys, not the runtime's: the app hears them through `App::panel_key` or its own shortcuts, since which element's menu they open depends on the view (a browser's highlighted row, not the focused field). *Why the app's:* the menu shows the app's items, and a menu opened by the pointer and by a screen reader must be one message, so neither path can show a different menu.

## 6. Focus and the keyboard

**Status:** Agreed. Rule 9 is built in plan 3.2, row 4a (`Element::radio_group`, `window/order.rs`, `Runtime::radio_key`); no view uses it yet. Rules 10 to 12 are built in plan 3.2, row 4b (`Runtime::slider_key`, a check box activated as a switch is, and `Runtime::select_key`); no view uses them yet. Rules 1, 3, and 5 for the canvas and the inspector in phase 1, and rule 8 for the menus over the canvas; the rest in phase 3, for every view. Rule 7 comes with the canvas accessibility spec's outline. For `loom-ui`'s own elements (plan step 3.1): rules 2, 3, and 5, rule 4's fallback when the focused element goes, and rule 7's Ctrl+Tab passing a focused element by are built (`focus.rs`, `window/order.rs`, `Runtime::focus_step`); no view uses them yet. The ring is data until drawing draws it (`Runtime::focus_ring`).

### Rules

1. **One element has keyboard focus at a time, across the whole window,** or none does. The canvas is one focus stop that manages focus among its tiles and controls itself (`FocusState` in `loom-canvas`). *Why:* two focus owners would both act on the same key.
   - **A selected tile is the canvas holding the keys** (Brylie's decision, 2026-11-19): with nothing open over the canvas and no field or element of either toolkit focused, a selected tile means the canvas has the keyboard, as a focused control does (`App::canvas_has_keys`, the one answer every rule reads). The canvas then takes Tab and Shift+Tab and walks its tiles, the arrow keys move the tile, and the runtime's stops are neither entered from it nor activated by Enter or Space. "Nothing focused" elsewhere in this section excludes a selected tile. To reach the runtime's stops from a selected tile, Escape lets the selection go, and Shift+Tab from nothing then enters the last stop. Changed from row 1, where Shift+Tab with a tile selected entered the bar's last stop. *Why:* a selected tile already takes the arrow keys, so it holds the keyboard in every other way; and Tab and Shift+Tab walking the tiles in both directions must not be cut off by a stop elsewhere in the window.
2. **Tab and Shift+Tab move through the focus order:** by layer from the top, then panel by panel in reading order, then elements in the order the panel builds them. A panel may set its own order. *Why:* NFR-UX-01, and an order a user can predict from what they see.
   - **Reading order is what the user sees, not what is drawn** (decided 2026-11-16). Inside a layer, root panels are read by where their first focus stop is: the higher one first, then the one further left, and the view's order where two are level in both. Two first stops are level when they overlap from top to bottom (Brylie's decision, 2026-11-17), so a stop one pixel lower does not read after one beside it. A panel in a slot is read at the slot's place in its parent's build order. A panel drawn later is not read earlier because it is on top.
   - **Tab passes over a turned-off element** (Brylie's decision, 2026-11-16), as macOS and Windows controls do: it is no focus stop, and a press on it focuses nothing. Its node stays in the tree with its description, which says why it is off (section 7, rule 23), so a screen reader still finds it, and it offers no action, not even Focus. An element turned off while it has focus is no stop any more, so focus falls back as for an element that went (rule 4): to the first stop of its panel. *Why:* the platforms' own convention, which keyboard users expect. One function in `loom-ui` decides what a stop is (`is_stop` in `layout.rs`).
   - **Except a menu item that asks to stay a stop** (`Element::focusable_while_off`, which `is_stop` honours for `Role::MenuItem` only), as the WAI-ARIA Authoring Practices keep a disabled menu item focusable (Developing a Keyboard Interface, Focusability of disabled controls). Its node says it is off and offers Focus alone; Enter, Space, and a pointer's click pick nothing: the runtime gives the app no click on a turned-off menu item, whatever the app would answer. The cable picker's "No ports to connect" is the one today (rule 8). *Why:* a screen reader hears that the item exists and why it can't be used, and a menu needs an item to hold the focus, so Escape and Tab still reach it.
   - **Past either end, focus leaves the runtime's elements.** Inside `loom-ui`, a step past the first or the last stop is `FocusStep::PastEnd`, so a router can hand focus to the elements a toolkit still draws. Coming in from outside, a step forward lands on the first stop and a step back on the last.
   - **From row 2: the top run** (Brylie's decisions of 2026-11-18; built in row 2). With the toolbar and the breadcrumb `loom-ui`'s, the runtime's stops are two runs with Iced's between them, in reading order: the top run (the toolbar, as one stop, then, inside a sub-patch, the breadcrumb's entries, one stop each), then the canvas, then patch info's fields, then the bar's stops. So one switch for which half reads first is not enough: at each end of each run, the next stop is worked out from where it is. In `loom-ui` the runtime asks the app at every Tab from one of its stops (`App::tab_from`, given the next stop in its own reading order, or none past either end), and the app answers a stop of the runtime's, `Leave` (the key goes on to the target, as with one run, the default), or `Send` with a message that moves the focus into the target, such as the canvas focus request, with the key taken. `InputState::target_first` still decides Tab from nothing.

     **Patch info's stops** (Brylie's decision, 2026-11-25; the APG's default, every control in the Tab sequence). From plan 3.2, row 4d, patch info is `loom-ui`'s, and every control in it is a stop, in the order it is laid out, top to bottom (WCAG 2.2, SC 2.4.3 and 1.3.2): Authors, the tags, the Tags field, Choose, and Keyboard shortcuts. The tags are one stop, a toolbar named "Tags", as in Your patches (the WAI-ARIA toolbar pattern): Tab lands on the tag last focused while it is there, or the first; Left and Right move between the tags' remove buttons and stop at the ends; Home and End go to the ends; Enter or Space removes the focused tag, and the focus goes to the next tag, or the previous at the end, or the Tags field once none are left. Each remove button keeps its name, "Remove tag" and the tag. Escape on any of them gives the keys back to the canvas, as from the toolbar, and from a field as before. Ctrl+Tab into the right column lands on the stop last focused there, or the first field, as before. From row 4d.2, a module's, an unknown module's, and a slot's rows are `loom-ui`'s too, and from row 4d.3 a sub-patch's: every part of them is a stop, walked by the runtime's reading order; Tab from a value field moves on and commits its draft (the decisions row of 2026-11-25).

     **The toolbar is one stop** (Brylie's decision, 2026-11-19, the WAI-ARIA toolbar pattern). Tab and Shift+Tab meet it once, and land on its remembered button: the one last focused in this level while it is still turned on, otherwise the first turned-on button. Inside it, Left and Right move to the previous and next turned-on button and stop at the ends, as main's toolbar region did (#849): the WAI-ARIA pattern allows wrapping or stopping, and we stop. Home and End go to the first and the last. Turned-off buttons are skipped, as rule 2 does for Tab. Enter and Space click the focused button, as on any button, and Escape returns to the canvas. An arrow, Home, End, or Escape move runs on a turn of its own (`App::post`), after every other message the same key sent: Escape also closes help, and that message must run while the focus is still where it was, or the app's copy of the focus would be a turn ahead of the runtime's. It is ordered on purpose, not a race. The breadcrumb stays one stop per entry: it is a list of links, not a toolbar. A screen reader's Focus still reaches every toolbar button, since the pattern changes only the keyboard's path. *Why:* the toolbar has more than a dozen buttons, and Tab through each of them on the way to the canvas is slow; desktop toolbars and the WAI-ARIA pattern both make it one stop.

     Changed from row 1: past the bar's last stop, Tab goes to the top run's first stop, where it left both toolkits before; and Shift+Tab from patch info's first field reaches the top run, where it reached the bar. A turned-off button is no stop (rule 2). With no stop of the runtime's at all, Tab moves as it did on main. An overlay keeps its loop, and the input layer keeps Tab from the runtime's stops while it is open, as below. *Why:* a keyboard user meets the stops in the order they see them, top to bottom, and the canvas is entered, not skipped, when Tab leaves the toolbar. Tab from nothing stays the canvas's, so the first Tab does what it did before.

     **Open for the plugin and web targets** (not decided; nothing is built for it): the wrap from the bar's last stop to the top run's first assumes the app owns its window, as the stand-alone app does. Inside a plugin's window in a host (CLAP, VST3), or embedded in a web page (wasm), Tab past the last stop, and Shift+Tab before the first, may need to hand focus back to the host or the page at some point, so a keyboard user can leave. The wrap is settled for the stand-alone app only; each of those targets decides this when it is built.
   - **Between the two toolkits, while both draw** (decided 2026-11-17, plan step 3.1; reading order, Brylie's decisions of 2026-11-17, plan 3.2, row 1). Iced's half is the canvas, with its own Tab among tiles and controls (rule 1), and the text fields of the view on top (`tab_fields`). The runtime's stops form the other half; while only the stats bar is the runtime's, they are its developer switches and its × buttons, below the canvas and the right column. So with no overlay open, Iced's half reads first (`InputState::target_first`): Tab with nothing focused is the canvas's, as it was before the bar moved, and Shift+Tab with nothing focused (no tile selected either, rule 1) enters the runtime's last stop, the last in reading order. Past patch info's last field, Tab enters the runtime's first stop, and Shift+Tab before its first field enters the runtime's last stop, so patch info's fields no longer loop by themselves while the bar has a stop. Past either end of the runtime's stops, focus leaves both toolkits, so the next Tab is the canvas's, as from nothing. With no stop of the runtime's (no error to dismiss and no developer switches), Tab moves exactly as before: patch info's fields loop. Any other Iced field moves as before: a value field closes on Tab, and the patches browser, an overlay, keeps its own loop. Tab moves only among the stops in the layers that take input now (`App::input`), so while the input layer is above the Panels layer (an overlay or a question is open), Tab never enters the runtime's stops below it; a focus already there stays where it is when no stop above takes Tab, and the key goes on to the target. The canvas keeps its own Tab while it has focus (rule 1). A Tab the runtime takes never reaches Iced (section 5, rule 10). Ctrl+Tab to a region that has moved to `loom-ui` lands on its first stop through a focus effect on that stop (rule 7). When the toolbar moves (row 2), the order is the one in the next item. As each region moves to `loom-ui`, its stops join the runtime's order, and this rule shrinks with Iced's half. *Why:* a keyboard user meets stops in the order they see them: the canvas before the bar at the bottom of the window, and patch info's fields, above the bar, before it. Iced's own field stepping is the app's code (`editing.rs`), so it can end at patch info's last field and hand the focus to the runtime. Tab from nothing stays the canvas's, so moving the bar changes nothing a keyboard user did before. An overlay keeps its loop, because the input layer keeps Tab from the runtime's stops while it is open. With no stop of the runtime's there is nothing to hand to, so the loop stays as it was.
   - **A focus effect on a UI ID no laid-out stop has yet** (a field in a panel opened in the same turn) reaches the toolkit as before, unless a panel of the runtime's already holds the ID. The next layout takes it if a stop has it then, and takes it from the toolkit; otherwise it is dropped. So when a panel opened in the same turn takes the focus, the toolkit holds it for one frame first, and a screen reader may announce that move. That is why the wait lasts one layout and no longer.
3. **Focus that came from the keyboard shows a visible ring.** Focus from a click does not, because the pointer is already there. *Why:* the canvas works this way today (`via_tab`).
   - **The runtime paints the ring** of its own elements: `RingStyle` from the app's tokens (`style::focus_ring`, through `PanelStyle`), an outline its width wide and its offset outside the focused element's bounds, with corners that follow the element's, in that element's layer after every panel of the layer, so a panel painted later does not cover it, and cut only by the window and by the scroll containers around the element (section 5, rule 12), so a part the wheel scrolled out of view leaves no ring over what is outside its container. Rows 1 and 2 kept the ring's state (`Runtime::focus_ring`) but painted nothing, so keyboard focus on the bar, the toolbar, and the breadcrumb could not be seen, which WCAG 2.2, SC 2.4.7 (Focus Visible) does not allow. Found 2026-11-20 in the running app, and painted since.
   - **No ring shows below the input layer** (section 5, rule 2): under an open question or panel, the element keeps its focus but shows no ring, as it shows no hover, so the only ring in the window is where the keys go. `Runtime::focus_ring` and painting read one answer (`shown_ring`).
   - **Its contrast.** The ring is the canvas's focus colour, 2 logical pixels wide and 2 outside the element, at 6.96:1 against the panel's colour (SC 1.4.11, 2.4.13). Against a filled button it is 1.1:1 to 2.3:1, but the offset leaves a strip of the panel's colour between the two, so the ring's neighbours on both sides are the panel's colour (`the_focus_ring_stands_out`). That holds only while the ring, its offset plus its width outside its element, reaches nothing else: no other filled button, and no text outside its own element, such as a "›" in the quiet text colour, which is 1.02:1 against the ring. So buttons side by side are at least `style::BUTTON_SPACING` (6 px) apart, the toolbar's in-group spacing, which the breadcrumb takes too (Brylie's decision, 2026-11-20; it was 2 px there), and `no_focus_ring_reaches_a_neighbour` checks every stop at the top level and two levels into a sub-patch.
   - **A focus moved by an effect can follow the latest input** (plan 3.2, row 6, built for help): `Effects::focus_as_input` shows the ring when the latest press was a key and none when it was the pointer's, as a browser decides `:focus-visible` when a script moves the focus. An overlay that a click or a key may open takes the focus into itself this way, so a keyboard user sees where it went and a pointer user sees no ring they did not ask for. `Effects::focus` keeps its ring. A screen reader's actions do not count as input here: a Click from VoiceOver leaves the mark at the last physical press, since the screen reader's own keys never reach the app. That is accepted until a screen reader action can say what it stands for.
   - **A button and a switch take no focus from a pointer press** (Brylie's decision, 2026-11-19): the press still shows the pressed look and clicks on release, but the focus stays where it was, in either toolkit. When one of the runtime's stops had it, that stop keeps it; when the canvas or an Iced field had the keys, nothing of the runtime's moves the focus, so the canvas behaves as it did with Iced's toolbar (a click takes the keys from a focused knob, and the arrows go back to the canvas). Tab and a screen reader's Focus still focus a button or a switch. A field, and any other stop, still takes focus from a press. It applies to the toolbar, the breadcrumb, and the bar's × and switches alike, and to a link in rich text (section 8, rule 10), which acts as a button does and takes no input of its own. *Why:* it is the convention for push buttons on macOS, and it is what the toolbar did before it moved, so a click on Undo does not take the arrow keys from the canvas. Windows differs: a click there focuses a push button. Brylie chose the macOS behaviour for every platform, the web and plugin targets included, so a click behaves the same everywhere the app runs. A focused button that then turns off still falls back as rule 4 says (Brylie's decision, 2026-11-16), which now happens only after keyboard focus.
   - **A press in a field's own list leaves the focus in the field** (plan 3.2, row 5, 2026-11-24): inside a container whose keys come from the focused stop (`Element::keys_from`), as a combobox's list box under its search field, a press moves no focus, as a press in a select's open list leaves it on the select (section 5, rule 18). The rows are no stops; the field's active descendant follows the highlight (section 7, rule 27). *Why:* in the WAI-ARIA combobox the focus stays in the field, so a right press that opens a row's menu, or a press that misses a row, must not leave typed keys with nowhere to go.
   - **An input widget takes focus from a press, with no ring** (Brylie's decision, 2026-11-20). A press on a slider focuses it, so the arrow keys then fine-tune the slider the pointer just set; the ring shows once the keyboard is used on it, from the first key it takes. A field, a select, and a radio button do the same, as any stop does: a press on a radio chooses it and focuses it with no ring, so the arrows then choose among that group's radios. This follows the input-widget rule, since a radio sets a value as a slider does, and Brylie's rule to defer to WAI-ARIA where in doubt: the APG's radio group example moves focus to the radio a click checks. A check box is pressed as a button is and takes no focus from a press, since a press sets its whole value and it has no arrow keys. *Why:* the platforms differ, macOS sliders taking no focus from a click and Windows sliders taking it, and the APG is silent; a press that leaves the arrows acting on something else would make a fine adjustment after a drag impossible. Iced's slider answered its arrow keys only while the pointer was over it, which neither the APG nor a platform does, and that goes.
   - **Over an overlay or a question, a press on no stop keeps the focus** (plan 3.2, row 8, built for Preferences). While the input layer is above the panels, a press that lands on no focus stop in it (a backdrop, the room between parts, a label) leaves the focus where it was, so a keyboard user keeps their place in the dialog, as a click on a part of a modal dialog that takes no focus does on the web (the WAI-ARIA dialog pattern). Below an overlay, such a press clears the focus as before. A focus that is gone falls back by rule 4. *Why:* found in Preferences, where a press beside the window dropped the focus and Tab then reached nothing.
4. **When an overlay opens, focus moves into it and stays there until it closes, then returns to where it was.** Built in `loom-ui` from row 3a: when the input layer rises to an overlay's layer, the runtime saves the focused element of its own, and the overlay's panel gives the focus its first place with a focus effect, as it opens; when the layer drops back, the saved element takes the focus again if it is still a stop, with the ring it had. A focus the target (Iced) held is the app's to give back, since the app's copy of the focus names it (`App::focus`), until the views that hold such focus move. Found on main 2026-11-20: nothing moved the focus, so a right-click that opened the probe menu left an inspector field taking typed text under it, and a screen reader's Click on Choose left patch info's Authors field taking typed text under the licence chooser. Rows 3b and 3c fix both by moving the focus in, each with a test. If that element is gone (a module deleted while the overlay was open), focus goes to the first focus stop of the panel that held it, or to the canvas if the panel is gone too. *Why:* a keyboard user must not be left behind the overlay, nor lose their place when it closes.
   - **A covered text field changes nothing** (2026-11-20). Until row 3 of plan 3.2 moves the focus into each overlay, a text field can keep its focus when an overlay opens over it without a left press: a right-click that opens the probe menu, or a screen reader's Click on Choose. Typing then reached it, and Enter in an inspector value field committed a value into the patch under the open menu. So a message only a focused text field sends (its typing, or Enter in it) is heard only while that field's view owns the input (`Message::field_view`, `InputOwner`); under any overlay it is dropped, as the question already drops it. Row 3 keeps this as the second guard.
5. **The accessibility tree reports the element with focus,** and changes it when focus moves. *Why:* otherwise a screen reader does not follow the keyboard. In the spike, focus was always on the window.
6. **A key goes to the focused element first,** then to its panel, then to the app's shortcuts. An element or a panel that takes a key stops it there. A focused text field takes every printable key, Space, Backspace, Delete, the arrows, and its editing shortcuts (select all, copy, cut, paste, undo, redo). It does not take Ctrl+Tab or Ctrl+Shift+Tab, which go on to the app's shortcuts (rule 7). As built in `loom-ui` (`FieldState::key`): editing shortcuts use the platform's shortcut key, Cmd on a Mac and Ctrl elsewhere, and redo is that key with Shift and Z, and also Ctrl+Y off a Mac. Moving and deleting by word use Option on a Mac and Ctrl elsewhere (`Modifiers::word_on`). In a single-line field, Cmd+Left and Cmd+Right go to the start and the end on a Mac, and Cmd+Backspace and Cmd+Delete delete to there, each an undo step of its own. Backspace and Delete with Shift alone delete one character, as without it, as the platforms' fields do. With any other modifiers they are taken and do nothing, so the app never deletes while a field has focus. Space types the text the platform gives with it, such as the no-break space of Option+Space on a Mac. A field in a layer below the one taking input (`App::input`), such as a panel under an open question, takes no key. In a single-line field, Up and Down, with or without Cmd, go to the start and the end on a Mac, as its own one-line fields do †; elsewhere the field takes them and does not move, since no other convention was checked. A multi-line field's arrow keys, with Cmd, Option, or Ctrl too, are section 8, rule 7's, on every platform. † Not checked against a document or by hand when this was written: it is the usual account of macOS single-line fields, to be checked on macOS before a view moves to the field. A field never takes Tab, Escape, or another shortcut such as Save. Paste is the field's own (plan step 3.3.2): it takes the key and asks the driver for the clipboard, and the text comes in on a later turn (section 8, rule 2). While the input method composes in the field, it takes every key, Tab and Escape too, and does nothing with them: the keys are the input method's then (section 8, rule 4). A key the field used goes no further: the runtime's panels take their keys before the field (step 2b), not after it as Iced's panels do (step 4).    - **Down and Right** move to the next radio and choose it; **Up and Left** to the one before. Both wrap at the ends.
   - **Space** chooses the focused radio if it is not chosen. Enter does nothing in the group: the pattern gives it no use, and in a dialog it would act on the dialog.
   - **A press** on a radio, its label, or its note chooses it and focuses it with no ring; the ring shows from the first key (rule 3).
   - **A choice reaches the app as `App::clicked(radio)`** on the next turn, from a press, a key, or a screen reader alike, so the app has one path for it. The app keeps which radio is chosen; the runtime never changes it.
   - **A note belongs to its radio:** a press on it chooses the radio, its bounds are inside the radio's, so the ring goes around both lines, and it is the radio's description (section 7, rule 29). Its text has a contrast of at least 4.5:1 against the panel, which a test checks.

   *Why:* the radio group pattern is what screen reader and keyboard users expect, and one stop keeps Tab from walking every answer. Radios are spaced so no ring touches a filled neighbour (rule 3).

10. **A slider's keys are the WAI-ARIA slider pattern's** (section 5, rule 16): Right and Up move it up by its key step, Left and Down down; Home goes to the minimum and End to the maximum, which the pattern requires; Page Up and Page Down move it by its page step, which the pattern allows. Shift with an arrow moves it by its fine step: an addition, since the pattern has no fine step. For a continuous parameter the key step is 1% of the travel and the fine step 0.1%, as on the tile knob ([panels](panels.md)), and a whole-number parameter steps one value; that is the 2026-11-11 decision, which waited for a slider whose keys step apart from its drag. *Changed:* the inspector's arrows moved 0.1% while Iced's slider shared one step with its drag. A vertical slider, when one comes, still goes up with Up, which the pattern allows. These are the keys it takes; a scroll key it does not take, such as Space, goes on to the scroll container around it (rule 6, step 3). *Why:* the slider pattern is what keyboard and screen reader users expect, and Iced's slider took no keyboard focus at all: its arrows worked only while the pointer was over it.
11. **A check box toggles with Space,** as the WAI-ARIA checkbox pattern says. Enter does nothing to a check box, since the pattern lists only Space; inside a grid, a cell may still take Enter for its check box, as the matrix's does ([modulation](modulation.md)). *Why:* the pattern, and Iced's check box had no keyboard at all.
12. **A select's keys are the WAI-ARIA select-only combobox pattern's** (section 5, rule 18). Focus stays on the select whether its list is open or not.
   - **Closed:** Down, Alt with Down, Enter, and Space open the list with the chosen option highlighted. Up and Home open it on the first option, and End on the last. A printable character opens it on the next option that starts with what has been typed (type-ahead, below).
   - **Open:** Down and Up move the highlight by one and stop at the ends, as the pattern says; Home and End go to the first and last; Page Down and Page Up move by ten options, stopping at the ends. Enter and Space choose the highlighted option and close the list, and so does Alt with Up. Escape closes it with no choice. Tab and Shift+Tab choose the highlighted option, close the list, and move the focus on, as the pattern says, though a native select does not: the pattern does it to match its other comboboxes. Moving the highlight never changes the choice; only these keys and a press on an option do.
   - **A departure from the pattern, with the reason:** in the pattern's example, focus leaving the select by any other path chooses the highlighted option. Here a press outside closes the list with no choice (section 5, rule 18), as a native select and our menus do, since the press is taken and the focus does not leave (rule 14).
   - **Type-ahead:** printable characters typed within 500 ms of each other build one string, and the highlight goes to the next option whose label starts with it, ignoring case; a single repeated character steps through the options that start with it. Closed, type-ahead opens the list. Space always opens or chooses, even while a string is building, so a label with a space in it is found by what comes before the space; a native select adds the space to the string instead, and the APG example does not say. *Why:* our options' labels are short and differ in their first word, and one meaning for Space is easier to learn.
   - **In a grid** (plan 3.2, row 4e, commit 3; the WAI-ARIA data grid pattern's widget in a cell): a select made with `Select::in_cell`, such as the matrix's Source, Target, and Polarity, opens only on Enter, F2, and Alt with Down while closed, on the chosen option. The arrows, Home, End, Page Up, Page Down, Space, and type-ahead go on to the grid around it (rule 6, step 2b), which moves the focus from cell to cell. Open, its keys are the ones above, and Escape closes it with the focus still on the cell. *Why:* the grid pattern's cell keys and the select's closed keys share the arrows; the grid keeps them, and Enter or F2 enters the cell, as the pattern says.
   - Any other key goes on, as it did before (rule 6). *Why:* the pattern is what keyboard and screen reader users expect, and Iced's pick list took no keys at all. The tile's choice lists are the canvas's and keep their own keys ([panels](panels.md)).

## 7. The accessibility tree

**Status:** Agreed, phase 1. The node of a text field (rule 10) is built in phase 3. `loom-ui`'s elements give their nodes from plan step 3.1 (`access.rs`, `Context::access_nodes`), checked against rule 2 when they are laid out. Rules 28 and 29 are built in plan 3.2, row 4a, rule 29's group of one in row 3c, and rules 30 to 32 in row 4b. The stats bar is the first view to give them (plan 3.2, row 1); the app still builds the whole tree and splices them in, until phase 4.

### Behaviour

In phases 1 and 2, the tree is built from the view models and the canvas scene, as in the spike. From phase 3, each `loom-ui` element gives its own node, from the same element that draws it. The canvas gives its nodes as a custom element (section 9) in every phase.

*Until phase 4:* the app still builds the tree and keeps the one table of node IDs. A panel that has moved to `loom-ui` gives its nodes through `Context::access_nodes`, with IDs from that table, and the app puts them in its tree where the panel is, hidden under a panel that owns the input as before (section 5, rule 3). A screen reader's action on one of them reaches the app as any other does, and the app turns it into a message by its UI ID (rule 6); a Focus action becomes a focus effect. The shell's adapter (`shell/access.rs`) is unchanged: the nodes reach it in the accessibility effect. In phase 4 the runtime builds the whole tree and keeps the table.

An element says what it is with an `Access` (`loom-ui/src/access.rs`): a role from the table below, its name, description, value, states, and actions. It is our own type, not AccessKit's node, so rule 2 can be checked against it and AccessKit's changes reach one file. Focus is never set by hand: every focus stop offers it, and nothing else does (rule 22). A focus stop must have an `Access`, since the tree's focus must name a node, and a slot must not, since the panel in it says what it is. A debug build panics on an element that breaks rule 2 or either of these when it is laid out, and `Layout::access_problems` lists them in a release build, which a test reads for every panel of the crate's examples (`tests/access_rules.rs`).

Each node has: a UI ID (section 4), a role, a name, a value where it has one, a description, a range and step for sliders, states (disabled, checked, selected, expanded), actions, and bounds.

The role follows the widget that is drawn, as widgets follow the kind of value (ADR-0024):

| Element drawn | Role | Value | Actions |
|---|---|---|---|
| Knob, fader, number | Slider | The number, in the parameter's range (rule 14) | Increment, Decrement, SetValue, Focus |
| Stepped parameter drawn as a knob (octave, note value) | Slider, stepping one option at a time | The option's index, with its name in the description | Increment, Decrement, SetValue, Focus |
| Stepped parameter drawn as radio or segmented buttons | Radio group, with one radio button per option | The chosen option | Click on an option, Focus |
| Toggle | Switch | On or off | Click, Focus |
| Button | Button | None | Click, Focus |
| Select (pick list) | Combo box | The chosen option | Increment, Decrement, Focus. Expand and Collapse on the runtime's select (rules 15 and 32) |

### Rules

1. **The tree and the screen come from one source.** Nothing writes accessibility names, values, or positions by hand beside what the view draws. *Why:* a tree that disagrees with the screen is worse for a screen reader user than no tree (ADR-0028).
2. **Every interactive element has a role that can be operated,** a non-empty name, and its value. A label and a status are not interactive: each is read by its text, which is its value and must not be empty, and needs no name of its own (the role table; decided 2026-11-17, plan 3.2, row 1, where the stats bar's warnings are the first statuses with no name). An element a user acts on offers an action, or is a focus stop; a list box option needs neither, since it is operated by being highlighted, as a field's active descendant (rule 27), so one that cannot be picked, such as a file in Your patches that does not read, is listed, enabled, with no Click (row 5b, 2026-11-24). A test checks every element kind in the table. *Why:* in the spike, radios and selects fell through to read-only labels, shown on screen but not operable. The snapshot tests did not notice.
3. **Names, values, and descriptions use our own words, the same ones the screen shows,** with units ("800 Hz", not "800"). *Why:* NFR-UX-06.
4. **A slider's value is a number, and its text with the unit goes in the description,** until AccessKit's macOS adapter can give a spoken value beside a number. Then the text moves to the value text, and this rule changes. *Why:* the spike found that with text in the value, VoiceOver can say the unit but cannot step the knob. Being able to change a control matters more than hearing its unit in the same phrase.
5. **A screen reader's SetValue is applied as sent,** clamped to the range. Increment and Decrement move one step, the same step as an arrow key on that control: 1% of the travel for a slider on a continuous parameter (rule 10), one value for a whole-number one; for a stepped parameter, one option. *Why:* VoiceOver speeds up while a key is held, and some screen reader users rely on that to cross a range quickly. Phase 1 records a listening test with VoiceOver in its pull request. If a held key cannot be used to set a value, this rule is changed before phase 1 merges.
6. **Every screen reader action becomes an ordinary message,** through the same path as the pointer or the keyboard. *Why:* undo, autosave, MIDI feedback, and the unsaved mark then work with no extra code, as the spike showed.

   **Screen reader edits group into undo steps** like a released arrow-key group ([undo spec](undo.md)). A screen reader sends no key-down or key-up, so each SetValue, Increment, or Decrement counts as one arrow step followed at once by its release. The app owns this group, beside `ArrowGroup` in `edits.rs`.
   - **Opens** on the first such action on a control.
   - **Joins** when the next one reaches the same control within 500 ms of the last.
   - **Closes** 500 ms after the last action. It closes sooner on an action on another control, a pointer press on the canvas, a key press other than a modifier alone, focus moving to another node, the window losing focus, an inspector edit, or Undo or Redo.
   - **Undo stays enabled** throughout, because no key is held. Undo or Redo closes the group first, then acts on it as one step.
   - **The wake that ends the group is one-shot, and it is the canvas's deadline.** The canvas is shown the app's open edit group with its deadline (`EditGroupView` in `loom-canvas`). It is not told who opened the group: a released arrow group and a screen reader's group look the same to it. It asks for one redraw at that time and reports the key or pointer press that ends the group sooner. With no group open, nothing wakes for it. *Why:* a timer that runs while a screen reader is attached would be idle work (NFR-PERF-04), and the canvas already wakes this way for arrow keys.
   - **The wake needs the canvas to be drawn and to have the input.** While a panel owns the input, the canvas ends any open group at its next event, so the group closes sooner, not later. While the window is not drawn at all (minimised, or fully covered), no wake comes. The group then closes at the next thing that closes it. An action that arrives after the deadline never joins: the app compares the action's time with the deadline, so the step is cut correctly even with no wake. Only the moment the step is recorded is late.
   - **A Click is not part of a group.** A Click on a toggle, a button, or an option ends an open group and is one undo step of its own, as a pointer click is. A Click that changes nothing, such as one on the option already chosen, still ends the group.
   - **An action waits while an arrow key is held.** The held key's group owns the edit in progress and may step again, so a screen reader's action does nothing then, as Undo does nothing then ([undo spec](undo.md)). *Why:* two owners of one edit would share an undo step.
   - **Hover text on Undo names the open group** "the screen reader edit".

   *Why:* one VoiceOver session in the spike made about 300 undo steps. `ArrowGroup` itself would never close, since its group waits for a key release that never comes. A group of its own, with the triggers of a released arrow group, gives a screen reader user what an arrow-key user gets once they let go of the key.
7. **The tree updates when what it reports changes, and sends only the nodes that changed:** after a message that changes a view model, and when widget state it reports changes without a message (keyboard focus, a text selection or caret, a scroll offset that moves bounds, an open or closed list), or the layout or scale factor changes. The runtime's own focus reaches the app through `App::focus_moved` (decided 2026-11-17): each change of the focused element is reported once, whatever moved it (Tab, a press, a focus effect, or a layout that settled it), and a ring shown or hidden on the same element is no change. When the report runs depends on what moved the focus: a move by an event is reported first in its turn; a move by an update's effects, right after that update, before the turn's next message; a move by a layout, on the next turn, through the waker, since a layout runs while the driver holds the runtime's parts. Only that last case leaves the tree one turn behind the runtime's focus. The app rebuilds its tree in that update. In `loom-app` the report is `FocusMoved`, the same message Iced's word on focus is, and the app's one copy of focus follows the runtime's element first, then Iced's field. For the runtime's own text fields, the runtime says so with `App::access_changed`: at most once a turn, asked after that turn's updates (field messages included) so its answer reads the new model, whenever a field's text, caret, selection, or scroll changed. A change a layout finds is told on the next turn. An app with no screen reader listening answers `None`, which costs nothing. A node that shows a live value (section 3, rule 7) is sent at most every 250 ms. While a screen reader is active, every live value node on screen is kept current at that rate, whether or not it has keyboard focus. A node off screen, or below a panel that owns the input (section 5, rule 3), keeps the value last sent. When the screen reader leaves (`deactivate_accessibility`), the runtime stops building the tree. *Why:*
   - **A screen reader can read any node without moving keyboard focus there,** so a node updated only on focus would show a stale value under the screen reader's cursor, against rule 1.
   - **AccessKit does not tell the app where that cursor is,** so the layer cannot update only the node under it. In `accesskit` 0.25.2 the app's only callbacks are activation, actions, and deactivation. `accesskit_macos` 0.27.2 answers VoiceOver's value reads from its own copy of the tree (`node.rs`, `accessibilityValue`), with no call to the app. A Focus action arrives only when the user has set keyboard focus to follow the VoiceOver cursor. The Windows and Linux adapters were not checked, so this rule holds on every platform. If a later AccessKit release reports the cursor on a platform, the rule narrows there to the node under it.
   - **The cap keeps a meter from flooding the screen reader.** `accesskit_macos` posts a value-changed notification for every node whose value changes (`event.rs`, `node_updated`). Whether VoiceOver speaks those for nodes it is not on is checked in the phase 1 listening test.
   - **No polling.** The spike rebuilt the whole tree every 500 ms (NFR-PERF-04). Here only changed live nodes are sent, and nothing is sent while no screen reader listens.

   How phase 1 does it, on Iced: after each message the app handles, other than the layer's own, it asks the window where the canvas is and builds the tree when the answer comes, one request at a time. It keeps the nodes it last sent and sends only those that differ. A message that only moves live values (lights, meters, traces, and the stats bar's load and dropout readings) asks for nothing: it marks them as waiting, and a 250 ms timer that runs only while they wait sends them. A timer or a watcher that only looks (the device and MIDI port checks, autosave, the pickup check, the audio load reading) asks for a build only when it changed something the tree reports, which the app tells from a small key taken before and after (`PollKey` in `a11y.rs`). So at rest no timer runs, and the last value is sent after a meter stops. `accesskit_macos` 0.27.2 has no callback for a screen reader that leaves, so on macOS the tree is still built after messages once one has listened; the app handles a deactivation event for the adapters that send one.

   Where the toolkit drew a part is read back from the window, never worked out a second time. Each part outside the canvas that has a UI ID is wrapped in a container whose widget ID is the UI ID's text. *Phase 1 bridge:* the named containers go when our own layout gives each element's bounds by UI ID (plan, step 3.1). The one widget operation that finds the canvas also collects every such container's bounds, and the bounds and offset of each scrolling area, so a part inside one is moved by the offset and knows what cuts it off (`places.rs`). The tree and the control channel's `locate` both read the result. A part scrolled out of view stays in the tree with its real bounds, inside a node marked as clipping, and offers no scroll-into-view action until phase 3. A scroll of Iced's inspector or matrix was a message only while a screen reader listened, which changed nothing and asked for a rebuild. *Phase 1 bridge, gone:* both are the runtime's since plan 3.2, rows 4d and 4e, and the runtime keeps their offsets as widget state (section 3, rule 4). Text parts are not named in the window in phase 1, so they have no bounds; every part that acts has them.

   While a panel or a menu is open, each tile's node is sent as hidden (rule 24), so a screen reader finds nothing below it, and what is inside a tile keeps the value last sent. A live value whose node lies outside the canvas's part of the window is not sent, and nothing waits for it, so the live timer does not run for a meter nobody can see. It is sent again when it comes back on screen.
8. **Bounds are sent in physical pixels,** converted from the logical layout with the window's current scale factor, as AccessKit expects. A scale factor change resends the bounds of every node. *Why:* layout and the control channel use logical pixels. Sending them unconverted would put VoiceOver's cursor at half the right place on a Retina display.
9. **Focus on a node never changes the patch.** Focus on a tile's node changes nothing: selecting a tile follows an explicit Click or Enter. A tile's node offers Click, which selects its module through the same message as a pointer click, so the inspector follows. Focus on a control selects that control's tile, as rule 20 says, because keyboard focus on the canvas lives only in the selected tile. Selection is not a patch edit and not an undo step. *Why:* an assistive tool that only inspects the window must not change the patch. The spike's tile selection on a tile's focus is removed.
10. **A text field gives its text as AccessKit text runs,** with the caret and the selection as positions in them, and handles SetTextSelection and ReplaceSelectedText. *Why:* with only SetValue, a screen reader cannot move its cursor through the text or read where the caret is.

    A tile's typed value field takes the place of the control's node while open. It takes keyboard focus, names the control and reports the draft text and selection. Closing it restores the control's node and its value.
    - *As built in `loom-ui`* (`field.rs`, `window/order.rs`): a character is one of Parley's clusters, the smallest piece the editor moves over and selects, so the screen reader's cursor stops where the caret does. A field's node holds its runs as children. Each run's UI ID is the field's, then `run`, then its index, so its node ID comes from the app's one table. AccessKit keeps a run's lengths and word starts as bytes, so a run holds at most 255 characters, and a longer text has several. A cluster longer than 255 bytes is split into pieces, each after the first at the cluster's trailing edge with no width, since no caret stands inside a cluster, so a caret after the last piece reports the cluster's end. A selection that ends inside one moves out to the whole cluster, since the editor selects whole clusters only, and a caret placed inside one goes to its start. A field's runs are one line, so each links to its neighbours (`next_on_line`, `previous_on_line`). A word starts where moving left by word stops; the space after a word belongs to it. Positions and widths are in physical pixels, from the run's left edge, and the run moves with the field's scroll. The field's node gives the selection as a run and a character in it, and offers SetValue, SetTextSelection, and ReplaceSelectedText beside Focus; a turned-off field offers none, and takes none that comes anyway. A selection end is checked against the run it names: past that run's length, or in a run the field does not have, the request is stale and changes nothing, not even the typing run. A selection's positions apply to the field's text as it is when the request arrives: AccessKit carries no version of the text a screen reader saw, so a request made against older text that still fits selects in the new text. The tree is sent again after every change (rule 7), which keeps that window short.
    - *Routing:* the runtime carries out those three actions itself when `App::access_target` says the node is one of its fields or a field's run. Each edit is one undo step, never joined to typing, and reaches the app as `FieldEvent::Edited`, so rule 6 holds. A screen reader's text is made one line first (section 8, rule 2). A field below the layer taking input, turned off, or taken out of its panel by a rebuild takes none of them (section 5, rule 3): the action changes nothing, gives no notice, and does not go on to the app. The runtime asks this with the same check a key does. SetTextSelection never moves focus (rule 9). Focus, and every other action, go to `App::accessibility_event` as before.
    - *Limit:* positions are in visual order along the line, and a run says left to right. AccessKit defines a run's positions in one direction, so in text that mixes in right-to-left a screen reader's positions are off there. The field still edits such text, since Parley's editor handles both directions.
11. **The adapter attaches before the window first shows.** The shell creates the window hidden, attaches `accesskit_winit`, then shows it. *Why:* AccessKit documents this order. The spike worked without it by luck. The shell owns the adapter on every platform, so any app on the shell has a screen reader (`loom_ui::shell`, `shell/access.rs`). The app hands it the tree as the accessibility effect: the whole tree and what changed. The shell keeps the whole tree and answers a screen reader that starts with it at once, on whatever thread the platform asks from. When none was given yet, the platform shows a placeholder, and the shell hands over the next whole tree rather than its changes. The screen reader's start, actions, and departure reach the app as `App::accessibility_event`, each run in a turn. macOS never says a screen reader left (`accesskit_winit` 0.34.2), so there the tree is kept up to date until the app quits.
12. **A tree is driven by the app.** The app handles Up, Down, Right, Left, Home, End, and type-ahead in a tree, and keeps which rows are expanded. From plan 3.2, row 4e, the Outline's rows are `loom-ui`'s: the current row is the tree's one focus stop, its scroll container takes the tree keys first (section 6, rule 6, step 2b) and hands them to the app, and each row's node says its level (`Access::level`). The app groups the rows' nodes under the Tree node, as it does the tab list, until the runtime builds the whole tree (the plan, [P6](../dev/leaving-iced-plan.md#p6-the-runtime-owns-the-whole-accessibility-tree)). The tree's visible rows are sent as direct children of the Tree node, in the order shown, and each still carries its level, its position in set, its size of set, and its expanded state. *Why:* `accesskit_macos` 0.27.2 has no expand or collapse action, reports no level, position, or size of set, and lists only a tree's direct items as its rows (`node.rs`, `accessibilityRows`). Rows nested as children of rows would not be listed there. The Windows adapter maps level, position, size, and expand state †, and the Linux adapter position and size †, so sending them costs nothing and helps where they are read. Keys the app handles work the same everywhere, with or without a screen reader.
13. **Elements may set `controls` relations to other nodes by UI ID,** inside or outside their own panel or custom element, and, on a field that keeps the focus while the keys act on a list, its active descendant (rule 27), and no other relation. The runtime turns each UI ID into its node ID when the tree is sent, and drops a relation whose target is gone. In `loom-ui`, an element sets its active descendant with `Access::active_descendant`, and a list box option its place with `Access::position_in_set` (from 0) and its list box the count with `Access::size_of_set`, as AccessKit puts them (plan 3.2, row 5): `accesskit` 0.25.2 counts a position from 0 and keeps the size on the container, and its Windows and AT-SPI adapters add 1 and read the size from the container, so the third row is heard as "3 of 10" (`focus/tests.rs`, `positions_count_from_zero_with_the_size_on_the_list`); `accesskit_macos` 0.27.2 reads neither; the target must be a laid-out element of the runtime's with a node, or the relation is left out. `controls` waits for the first view of the runtime's that needs it. *Why the active descendant:* the WAI-ARIA combobox pattern keeps focus in the field and names the highlighted option this way, and Windows and Linux read it; `accesskit_macos` 0.27.2 does not, and reads the option's selected state instead, so the option is marked selected too. *Why:* `controls` is the only AccessKit relation the three platform adapters map: on macOS to linked UI elements (`node.rs`, `accessibilityLinkedUIElements`), on Windows and Linux to "controller for" †. `flow_to`, `described_by`, and `details` are mapped by none †, so a relation of those kinds would reach no screen reader. The canvas uses it from each output port to the inputs its cables feed ([canvas accessibility](canvas-accessibility.md), rule 21).
14. **A slider's number is the parameter's own value, with the parameter's minimum and maximum,** not the control's travel from 0 to 1. A step size is declared only where equal steps of the control are equal steps of the value: a linear parameter, or a stepped one. A slider on a logarithmic or decibel parameter declares no step. Increment and Decrement still move it by what an arrow key moves it (rule 5). *Why:* "1000" on a control that reads "1000 Hz" is true, and "0.57" is not. One arrow key press on a logarithmic control is 1% of its travel, which is a different number of hertz at each place, so no one step would be true.
    Use the displayed decimal precision for a parameter slider’s number wherever its text is in parameter units, including each part of a composite control. Preserve exact bounds and positive linear steps using the shortest decimal representation of their single-precision values. A decibel control keeps its numeric value in the parameter’s linear units, using the same decimal conversion as the bounds. Its description gives the displayed decibels.

15. **A select says its chosen option and steps one option at a time,** with Increment and Decrement, on a tile, in the inspector, and in Preferences. It offers no Expand or Collapse until phase 3, when our own select can give its open list as nodes; from plan 3.2, row 4b, the runtime's select does (rule 32), and a view that moves onto it gains them. Nothing outside the canvas can open a tile's choice list. *Why:* a combo box that says it can expand, and then shows a screen reader nothing to walk, is worse than one that steps.
16. **An XY pad and a range are a named group holding one slider per value.** Each slider is named by its parameter and steps as an arrow key steps that value. A range's handles do not pass each other: a value set past the other handle stops at it, as a drag does. A handle stops from the side it is on: where a typed value has left low above high, low moves freely above and stops when it comes down to high. Where the two are together, low is the one below and high the one above, so each can move away. *Why:* AccessKit has no role for one control with two numbers, and two sliders are what the two values are.
17. **A readout is a label whose value is its name and the text it shows,** as "Cents: 12.5 cents", and it has no label of its own. An adapter gives a label node's label in place of its value (`accesskit_macos` 0.27.2, `label_is_exposed_in_value`), so a name set as the label would hide the reading. No label node has both. **A scope is an image** whose description says its trace's lowest and highest points in words, updated at most 4 times a second (rule 7). A light, and the other drawings a tile shows, are images named by what they are bound to, with the text the screen gives for them as the description. *Why:* a screen reader user should learn that a signal is there and roughly how large it is. A stream of numbers at the frame rate would be noise.
18. **A widget with no caption is named by what it is bound to,** the name its hover text shows. *Why:* most meters and scopes have no caption on the tile, and rule 2 needs every node to have a name.
19. **A tile gives no port nodes in phase 1.** Ports come with the canvas accessibility work ([canvas accessibility](canvas-accessibility.md)). *Why:* that spec designs how ports and cables are read, and nodes added before it would have to be redone.
20. **The Focus action on a control moves keyboard focus there,** and the tree reports focus on the control that has it, or on the window when none has. In phase 1 the app asks the canvas with a request that names the module and the widget, and the canvas reports each focus change once, whatever caused it. Focus on one value of an XY pad or a range, or on one option, focuses the control that holds it. Focus on a control also selects its tile, through the path a press or Tab on the control already takes, so arrow keys then act on it and the inspector follows. Focus on a tile does nothing, and no Focus action changes the patch (rule 9). A widget that only shows a value offers no Focus. A request waits while something else has the input, and is applied on the first redraw after the canvas has it again, so its events are never dropped. It is applied after a new level or patch is framed, which clears the focus, and waits while that framing waits for the canvas to have a width; a request made during that wait still lands once the width comes. The keys go with the focus, by the path a press on the canvas takes: the matrix lets go of them, and a text field that has them closes, its draft dropped as a press drops it. When the selection moves to another tile from outside the canvas, as on a screen reader's Click on that tile, focus left on the first tile is dropped and the tree reports focus on the window. While a choice's list is open, focus stays with it, and is dropped on the first redraw after the list closes. A valid request asks for a redraw through an effect. The canvas applies it on that frame, so an action that arrives alone still moves the focus. *Why:* VoiceOver can be set to move keyboard focus with its cursor, and a user who then presses an arrow key expects it to act on the control they hear. The request names a module and a widget, nothing of the toolkit, because the focus effect of phase 2 will carry the same.
21. **A meter reports the number its text shows,** not the level as stored. A level meter that reads "-6.0 dB" reports -6, from -60 to 0. A meter on a display value reports that value, with the display's range. The number is the one the text writes, digit for digit: it is read back from the text's one decimal, so "-12.0 dB" is -12 and never -12.04. Where the text says a value past the end of the range, the bounds reach out to it, so the number is never outside its own bounds. The code that writes the text makes the number, and the tree reads it from there (`Reading` in `loom-canvas`, `meter_reading` in `scene.rs`). When the text names no single number, the node has no number and says the text only: a stereo meter says two levels, and a level under the floor reads "below -60 dB". *Why:* a stored level of 0.9 means nothing to a listener, and working out decibels a second time in the tree would let the two drift apart. Decided 2026-11-11, the same answer as rule 14 gives for a knob.
    A meter whose own clip light is lit appends “clipped” to its description until that light is reset. It keeps the ordinary meter announcement policy. An invalid scope or XY scope window has the description “Not a number”.

22. **Outside the canvas, only a text field offers the Focus action until phase 3.** A toolbar button, a tab, a switch, and a slider offer what they do (Click, Increment, SetValue) and no Focus. *Why:* the toolkit's buttons and sliders cannot take keyboard focus, and an action that does nothing is worse than none. Our own widgets take focus from phase 3, and offer it then. A phase 1 limit. Each view's widgets offer Focus from the row that moves them (plan 3.2): from row 1, the stats bar's dismiss buttons and its developer switches; from row 2, the toolbar's turned-on buttons and the breadcrumb's entries. From row 4d, each part of the inspector's column that is a focus stop: patch info's, then a module's, an unknown module's, and a slot's. Focus on one of them takes the keyboard from the canvas too: the app sends the canvas a request that names no control, and the canvas lets go of its focus, so Enter and Space then reach the bar's stop.
23. **Hover text is the node's description,** on a toolbar button, a stats bar item, and the status line, unless the node sets a description of its own or the text only repeats its name or value: a screen reader would then read the same words twice. For a disabled button the hover text says why it is disabled, so the description does too. *Why:* the hover text is what a sighted user gets by pointing, and a screen reader user cannot point.
24. **The tree follows the pointer.** While a panel or a menu is open, a pointer press does not reach a tile, the toolbar, the right panel's tabs, or the stats bar: every panel puts a layer over the whole window, to close itself on a press outside or to hold the press. The small menus on the canvas do this too. The nodes of those parts are then hidden, and a screen reader's action on them does nothing. With nothing open they are reported and they act. One function says which it is (`App::pointer_reaches_window`), for tiles and for the rest alike, and a test presses Panic and drags a tile's knob under every panel and checks that the tree agrees. **Panic** is the case that matters: its button cannot be pressed under a panel, by a pointer or by a screen reader, so the panic shortcut is what works then, as section 6, rule 6 says it always does. What the panel or menu itself reports is rule 27. *Why:* rule 1. A node that a screen reader can press where a pointer cannot would make the tree say more than the screen.
25. **A panel the toolkit draws describes its parts as items,** built from the same model its view draws (`a11y/items.rs`; the inspector's in `inspector/access.rs`). An item says what the part is, what it says, and the messages each screen reader action sends, as a press, a key, or typing and Enter would. The tree turns items into nodes, and an action on a node into those messages, so a panel has no accessibility code beyond building its items. Every part that acts is named in the window, and a test checks that each one's item has the place the window drew. *Why:* rule 1, and one place for what an action does, beside the view that sends the same messages.
26. **What must be heard goes in a node's name or its value,** not its description, where the part offers the choice: a text part says its words as its value, and a modulation's depth and a stack's spread are numbers in percent, as the panel says them. A slider's value with its unit is in the description, on the inspector as on a tile's knob, so both change together if the listening check finds it is not heard. *Why:* on macOS a description is help text, which a screen reader may read late or not at all. Decided 2026-11-11, until the listening check.
27. **The overlay that owns the input is reported, and acts.** It is the one `Overlays::owner` names, the same answer that decides where a pointer press goes (section 5, rule 2). Everything it covers stays hidden and inert by rule 24, an overlay under another included: help over a menu, the licence chooser over Preferences. Its parts are items built from its own model (rule 25). Its root is a dialog, an alert dialog (the question), or a menu, marked as modal. A screen reader's action on its parts works as a press does, also while a question holds back most messages, since each message an action becomes is checked on its own. Focus is reported on, in order: the text field that has the keys; a menu's highlighted item, or the question's highlighted answer (section 6, rule 8), since the keys act on it; otherwise the overlay's root, which is where the tree says focus is, not a Focus action (rule 22). When the overlay closes, the tree reports what has the keys then: a canvas control's focus comes back on its own, since the canvas keeps it below the overlay. Giving a text field its focus back waits for phase 3, when the runtime owns focus (section 6). A link in help's text has bounds from row 6 of plan 3.2, when help moved to `loom-ui`: the rectangles of its words (section 8, rule 10). Slice 4a reports the menus, help, and the question; 4b the module browser and Your patches; 4c Preferences and the licence chooser. From plan 3.2, row 8, Preferences has the runtime's focus, on Close when it opens. The chooser is the runtime's from row 3c, so the part with the runtime's focus has it, from the first question as it opens. An overlay of the runtime's under another of its overlays, such as the chooser under help, is drawn but not reported at all, as a covered menu is not (rule 24), so its parts never read as part of the top one's dialog. Over Preferences, the chooser gives it back to Choose when it closes (section 6, rule 4; [preferences](preferences.md#keys-and-focus)). In Preferences a list steps from the option last asked for that could not be used, and the window says why under its lists, so a device that fails never blocks the ones after it, and a reader in the window hears the failure that the status line, hidden under it, also shows. In a browser the search field keeps the keys and the focus, and the highlighted row is the list box's selected option and the field's active descendant. While a library row's menu is open, its keys act on the menu (section 6, rule 8), so the field offers no Focus then and the menu's highlighted item, or the menu, has the focus. As Your patches reads its folder, each batch of rows rebuilds the tree with the focus where it was, so nothing new is announced, and the list says how many rows are shown so far. *Why:* rule 1, and a screen reader user must reach what has the keys.

28. **A scroll container is a scroll view,** named by its panel, with its offset, `scroll_y`, between 0 and its greatest, and the actions ScrollUp, ScrollDown, and SetScrollOffset; ScrollIntoView on a part inside it scrolls as a focus move does (section 5, rule 12). The bounds of its parts are cut by it, as drawn. The inspector's and the matrix's `Scrolled` messages, sent only while a screen reader listened so the tree heard Iced's offset, went when each moved (rows 4d and 4e): the runtime knows its own offset and updates the tree itself (rule 7). *Why:* AccessKit 0.25 gives a scroll view its offset and actions, so a screen reader can scroll without the keyboard.
29. **A radio group is a radio group of radio buttons** (section 6, rule 9): the group named by its label, each radio a radio button with its checked state, its label as its name, and its note as its description, offering Click, which chooses it, and Focus. Focus is reported on the radio that has it. *Why:* the WAI-ARIA radio group pattern, and AccessKit's roles of the same names.
   - **A group of one radio gives no node of its own** (Brylie's decision, 2026-11-22, plan 3.2, row 3c: the licence chooser's Other). Its radio's node sits where the group's would, under the group's parent, and the group's label is not used. The radio has no place in a set and no set size, since a set of one says nothing. The group stays a keyed element in the layout, so the radio's UI ID runs through the group's key as in any group. The layout check of rule 2 has nothing to report: the group has no `Access`, and a group is never a stop. *Why:* a group whose only radio has a name of its own would be heard twice, as "Other, radio group, Other, radio button, 1 of 1", which is noise, and inventing a hidden name for the group would give a screen reader words nobody sees.

30. **A slider is a slider** (section 5, rule 16): its value, minimum, and maximum are the parameter's own, and a step is declared only where steps are equal (rule 14). Increment and Decrement move it by its key step, the same as an arrow key (rule 5). The value with its unit goes in its description, not in its value text (rule 26): *a departure from the WAI-ARIA slider pattern,* which puts it in `aria-valuetext`, kept until the listening check, since on macOS a value text replaces the number. Its orientation is horizontal. Its steps in quick turn are one group, as keys are, and so one undo step (rule 6): Start and Move for the first, a Move for each step within 500 ms of the last, and End when the group closes, whatever has the focus, since a screen reader acts on a node without moving the focus there (`Sliding::step`, plan 3.2, row 4d; each step was its own Start, Move, and End before).
31. **A check box is a check box,** named by its label, with its checked state, offering Click, which toggles it, and Focus. *Why:* the WAI-ARIA checkbox pattern, and AccessKit's role of the same name.
32. **A select is a combo box, and its open list a list box** (section 5, rule 18; the WAI-ARIA select-only combobox pattern). The select's node is a combo box named by its parameter or its label, with the chosen option as its value, offering Expand while closed and Collapse while open, and Increment and Decrement, which step the chosen option by one as before (rule 15), and Focus. While open it says it is expanded, controls the list, and its active descendant is the highlighted option. The list is a list box with one option per row, each named by its label, the highlighted one selected, with its place in the list. Expand opens the list as Down does, Collapse closes it with no choice, and a screen reader's Click on an option chooses it. *Why:* a screen reader then walks the open list as a sighted user does, which rule 15 left for this row.

## 8. Text input and IME

**Status:** Agreed, phase 3. The text crate (rule 8) was chosen at plan step 2.4: Parley. Rich text (rule 10) is built in `loom-ui`; no view uses it yet. Canvas text is drawn with it since plan step 2.4b (rule 9). `loom-ui` has a single-line field since plan step 3.3.1 (`Element::field`, `crates/loom-ui/src/field.rs`): rules 2 and 3, and its keys (section 6, rule 6). The app hears its runtime fields from the shared groundwork for plan 3.2, rows 3c and 5 (`loom-app`'s `runtime_fields.rs`): each field's `Edited` and `Committed` become that field's own messages, routed by its UI ID to its view, and a field whose view maps no Enter ignores it; a refused paste is said in the status line; while one of the runtime's fields has focus, a question to the window about focus (Tab from a field, the clipboard keys, a script's typing) is answered with that field, from `Runtime::focused_field`, which follows the focus, so a field that is gone no longer counts; and a screen reader's text action reaches the field through the app's node table (`App::access_target`). Its text runs for a screen reader (rule 5) are in too, and since plan step 3.3.2 its own paste (rule 2) and IME composition (rule 4). No view uses it yet. A focus effect that asks for all of a field's text (`Effects::focus_and_select_all`) selects it in one of the runtime's fields too, as in Iced's, so the inspector's value field takes typing over its value (plan 3.2, row 4d). The multi-line field (rule 7, `Element::text_area`, row 4c) is used from plan 3.2, row 4d, by patch info's Authors box, whose node is a multi-line text input a screen reader can edit; from row 4d.3 a sub-patch's Authors box too, one undo step for each time it is edited until focus leaves.

### Rules

1. **Shaping, font fallback, line breaking, glyph rasterising, and the editing model come from existing crates.** We write the glue, not a text engine. The one exception is the glyph atlas: packing rasterised glyphs into a texture and drawing them, because no atlas crate takes Parley's glyph runs at our `wgpu` (rule 8). It stays small and replaceable, behind the `Painter` boundary: about 840 lines with its shader at step 2.4b, against an estimate of 680 and a stop point of 1,000. It lives in `loom-ui` since step 3.1 (`paint/atlas.rs`, `paint/plan.rs`, `paint/gpu.rs`, `paint/paint.wgsl`). *Why:* ADR-0041, decision part 3. An atlas is a cache and a shader, not text knowledge: rasterising, the part that knows about fonts, stays in `swash`.
2. **A single-line field supports:** caret, selection, word movement, Home and End, clipboard through effects, and undo inside the field. *Why:* users expect these in any text field, and their absence is noticed at once.
   - **The text is the app's.** A field element carries the text the app holds. The field edits in place and sends each change to the app as `FieldEvent::Edited`, through `App::field_event`; Enter sends `FieldEvent::Committed`. An app takes an edit into its model, so the next view shows it. Whenever a layout shows a text other than the field's, whatever the cause, the field takes that text: its selection is clamped to it, and its undo steps go, since they no longer apply. An edit the app does not take is one case of this: the field goes back to the app's text. *Why:* one owner for the text, as for every other value on screen (section 3), so the screen never shows what the app does not hold.
   - **Copy and cut with nothing selected do nothing,** and leave the clipboard as it was.
   - **The field's own paste reads the clipboard through the driver,** the same clipboard copy and cut write (`Driver::clipboard_paste`, answered with a `Paste`). Nothing waits on the system: the answer comes on a later turn, as the decisions row on reading the clipboard says, and goes in only if the field still has focus, focus has not moved since the paste was asked for (not even away and back), and the field takes input (`field_takes_input`), as one undo step. One that comes during a composition goes in after the preedit, which stays as text. Otherwise it is dropped, so a slow clipboard never types into another place.
   - **The clipboard is one backend, on a thread of its own** (plan step 3.3.4). `loom-ui`'s `clipboard` feature holds one long-lived system clipboard (`arboard`) on one thread, which does every read and write; the `shell` feature turns it on, and a plugin's driver can use it with no winit. The app's copy, cut, and paste, the field's, and Iced's widgets until phase 4 all go through it, so they never disagree. Nothing waits on it: a write sends and goes on, and a read answers on a later turn. One exception, until phase 4: Iced's widgets read the clipboard synchronously, so the bridge's read (`Clipboard::read_now`) waits on the UI thread at most 250 ms (`READ_NOW_LIMIT`), then answers `Refused`; drivers and the app's own effects always read asynchronously. A read the backend does not finish within a second (`BACKEND_READ_LIMIT`) answers `Refused`, and the thread goes on, so an owner that never answers holds no later read or write. The thread keeps two handles: one it writes through, which never leaves it, so a read that goes wrong never takes our copy, which on Linux the handle that wrote serves; and one it reads through, lent to a helper thread for each read. While a read is stuck, its helper keeps that handle, and reads answer `Refused` at once, with no new thread, until it comes back or three of them have (`READS_BEFORE_RETRY`). The next read then gives the stuck one up and tries again with a new handle, so a clipboard that answers again, such as after the app that held it quits, is not refused for good. A stuck read cannot be cancelled, so at most two may be stuck at once (`MAX_STUCK_READS`); past that, every read answers `Refused` until one ends. The limit counts reads, not time, since the crate never reads the clock. So a clipboard that stays stuck holds two helpers at most, never one per paste. How a read ends on each platform (#857): on Wayland, the clipboard reads the transfer itself through `wl-clipboard-rs`, since `arboard` reads it with no limit, so an owner that stopped would hold the read for good. The read waits on the owner's pipe and on a timer the system holds, armed once for 750 ms (`WAYLAND_READ_LIMIT`), so the deadline bounds the whole read, even one that trickles, and the crate still never reads the clock. At the deadline the read answers `Refused` and closes the pipe, which is a real cancel: no thread or file is left waiting. 750 ms is under the helper's second, so the read ends by itself and is never stuck. A timer or wait that fails answers `Refused` at once and never reads on with no deadline. A read takes at most 16 MiB (`MAX_TEXT`), far more than any patch or field text; an owner that sends more within the deadline is answered `Refused` and its pipe is closed, so a read never grows without bound. It reads Wayland exactly when `arboard` chose Wayland (a `WAYLAND_DISPLAY` and a compositor with data-control, `arboard`'s own check), decided once per handle, so reads and writes always use the same clipboard; writes still go through `arboard`. On X11 `arboard` waits 4 seconds and then answers as if the clipboard were empty, so the helper's second is what answers `Refused` there. On Windows and macOS the read is `arboard`'s. No backend holds a read for good now, so the cap on stuck reads is a safety net. Text only: the patch clipboard holds patch text (ADR-0008) and a field holds text, so nothing has use for an image or HTML.
   - **A read can be refused, and that is not an empty clipboard.** A driver answers a read with `ClipboardText`: `Text`, `Empty`, or `Refused`. `Refused` is any read that could not complete: one the browser or the system did not allow, and one the backend failed, such as a clipboard another app holds on Windows or no clipboard to reach on Linux. One answer serves all of them, since the app does the same for each and its message ("Couldn't read the clipboard") is true for each, so a failure never looks like an empty clipboard. The app's read effect and the field's `Paste` both carry it. A refused read never fails silently: the app shows a status message, which a screen reader announces (section 7, the status role), and a refused field paste reaches the app as `FieldEvent::PasteRefused` so it can do the same. An empty clipboard is not a refusal and adds no message of its own (Brylie's decision, 2026-11-19): a field's paste changes nothing and says nothing, and the app's patch paste says, as before, that the clipboard holds no LoomDSP modules, as it does for any text that is not modules.
   - **On each target.** Desktop: `arboard`, text only. On Linux the app that copied holds the text, so on quit it relies on the desktop's clipboard manager to keep it, and never waits; with no manager running, what was copied is lost on quit (Brylie's decision, 2026-11-19). On Wayland it uses the compositor's data-control protocol where the compositor has one, and X11 through XWayland where it does not (Brylie's decision, 2026-11-19); a data-control read ends at its 750 ms deadline (above); GNOME's compositor has no data-control protocol †, so there the clipboard goes through XWayland, and a session with no XWayland at all has no clipboard †. Web: the browser's asynchronous Clipboard API, which needs a secure context and allows a read only in answer to a user's key or click †, so a web driver starts the read in the same turn as the key that asked for it, as the runtime already does; a read the browser does not allow answers `Refused`. Plugins: CLAP and VST3 have no clipboard of their own †, so a plugin uses the system clipboard, with one clipboard thread per process shared by every instance; how a host passes the paste key to a plugin's window is for OQ-13.
   - **Text that comes in whole is made one line** (Brylie's decision for paste, 2026-11-17). Each line break, CRLF, LF, or CR, becomes one space, and a break at the end is dropped. Our extension of that decision: the line and paragraph separators U+2028 and U+2029, where the text engine also breaks, count as breaks; a tab becomes one space too, since a pasted tab usually separates words (as between spreadsheet cells), and other control characters go, as in typing. One function does this (`one_line` in `field.rs`) for a screen reader's SetValue and ReplaceSelectedText now, and for the field's own paste when it comes (plan step 3.3.2). *Why:* a field shows one line, and a break kept in its text would reach the app's model and draw as a second line the field has no room for.
   - **A placeholder** (plan 3.2, row 5, for the browsers' search fields). `Element::placeholder(text, colour)` shows a hint of what to type while the field's text is empty and nothing is being composed in it, painted before the field's own text, so the caret shows over it at the start. It is not the field's value: its node reports it as the placeholder (`aria-placeholder`), after the name, with an empty value. Its colour is the app's, at 4.5:1 or more against the field (WCAG 2.2, SC 1.4.3), since it is text to read; `loom-ui` holds no colour. The field's own state is not touched: drawing reads only whether its text is empty and whether it composes.
   - **The caret is steady** (Brylie's decision, 2026-11-17). It does not blink, so a still window draws nothing. A blink may come later; it would follow the system's setting for it, including off, and redraw as section 3, rule 6 says.
   - **A text wider than its box scrolls to keep the caret in view,** with 2 px to spare at either edge, and Home shows the start again (Brylie's decision, 2026-11-17). A text that fits never slides.
3. **Undo inside a field is separate from patch undo,** and ends when the field loses focus or commits. Losing focus means focus moving to another element, which the app hears as `FieldEvent::Left`; the window losing the keys is not that, since the field still has focus when they come back. In `loom-ui`, a typing run is one step, and a pause of 500 ms, a caret move, or a space typed after a letter ends it; a delete by word, a cut, and typing over a selection are each a step of their own. This changes today's behaviour, where Undo and Redo do nothing while a field has focus ([undo spec](undo.md)). The change arrives with each field as phase 3 moves it; until then the field keeps today's behaviour, and the parity checks expect it. *Why:* Cmd+Z while typing a name should undo the typing, not the last patch edit.
4. **IME composition goes to the focused field.** The shell sends preedit and commit events, shows the preedit text in the field, and reports the caret area so the candidate window appears beside it. An empty preedit ends the composition and removes only the preedit text. The commit that follows inserts the final text once, at the selection. *Why:* people who type Chinese, Japanese, or Korean need composition to type at all. *Until phase 3:* fields Iced still draws show the preedit text in a box at the input method's cursor area, not in the field (decided 2026-11-13, see the decisions).
   - *As built in `loom-ui`* (plan step 3.3.2, `field.rs`): the shell turns winit's IME events into `Event::Ime`, and the runtime gives them to the focused field when it takes input (`field_takes_input`); otherwise they go to the target, as with no field focused. A taken one is kept from the target (`Target::kept`), as a key is. A preedit with text is `set_compose`, an empty one `clear_compose`, and a commit `clear_compose` then the text at the selection, made one line, as one undo step.
   - **The preedit is not the field's text.** `FieldEvent::Edited`, undo, and the app's text taken at a layout read the text without it, so an unchanged app text never ends a composition. Drawing and a screen reader read the text with it (Brylie's decision, 2026-11-17, as macOS's own fields do): the node's value and runs say what the user sees. The preedit is underlined, one physical pixel in the text colour.
   - **A composition that starts over a selection replaces it,** as the platforms show it: the field deletes the selection first, as an undo step of its own that the app hears as `Edited`, then composes at the caret. So undo brings the selected text back even when the composition is cancelled.
   - **While composing, every key is the input method's.** The field takes each one and does nothing, before Tab or a button's Space can act.
   - **Focus leaving, the input method turning off, a screen reader's text action, or a paste in mid-composition keeps the preedit as text,** as one undo step, and the app hears it as `Edited`; on leaving, `Edited` comes before `Left`.
   - **The caret area:** `Runtime::ime` gives the focused field's `ime_cursor_area` in the window while it takes input. The shell sets that first; otherwise it sets what the layers last reported, and with none turns the input method off, so the window never keeps a field's area. When the runtime's field takes the input method over, the layers' last report is forgotten as Off, since taking the focus released their field and they report only a change. It calls the window only when the state changes.
   - **Targets.** What this assumes on each target, all first class: the stand-alone app on Windows, macOS, and Linux, a plugin exported as CLAP or VST3, and the web (wasm). The field's paste answer is asynchronous (`Paste`), which a browser needs, since its clipboard reads are asynchronous. `Runtime::ime` is a query that any driver can apply to the window it has, which suits a plugin inside a window the host owns; a host may own the input method itself, which [OQ-13](../product/open-questions.md#oq-13-embedding-iced-in-plugin-windows) is to confirm. The field reads whatever clipboard its driver has: `arboard` is desktop only, so it sits behind `loom-ui`'s `clipboard` feature (rule 2), which no web build turns on. Only the winit shell (`loom_ui::shell`) names winit's events; nothing else here assumes it owns the event loop.
5. **A text field reports its text, caret, and selection to the accessibility tree** (section 7, rule 10). *Why:* a screen reader reads and moves through text by these.
6. **Fonts keep today's face where today's face is the system font, and their widths change once per view.**
   - *Today:* Iced is built without its `fira-sans` feature, so `Font::DEFAULT` asks for the generic sans-serif, plus Iced's icon font (`iced_graphics` 0.14, `text.rs`). `cosmic-text` 0.15 names "Open Sans" as that family. Where it is not installed it falls back through a fixed list: `.SF NS` on macOS, Segoe UI on Windows, and Noto Sans, then DejaVu Sans, on Linux ([research](../research/2026-11-text-crate-choice.md#5-the-same-system-font-as-today)).
   - *Ours:* Parley's generic `system-ui` family: `.SF NS` on macOS, Segoe UI on Windows, and fontconfig's `system-ui` on Linux. So the face is today's on macOS and Windows where Open Sans is not installed. Two face changes are accepted: where Open Sans is installed, it becomes the system font (today's pick there is an accident of a default, not a choice), and on Linux, fontconfig's `system-ui` may name another face than Noto Sans or DejaVu Sans.
   - *Widths:* Parley applies the size-dependent tracking of Apple's fonts, as CoreText does, and Iced's text does not, so the same face sets from about 2% narrower to 5% wider: across the example patches' tile text, -1.7% to +5.3%, median +3.4% (labels at 9 px, median +3.5%; titles at 11 px, -1.6% to +1.4%). We keep the optical size axis at its default, as Iced does, so the change stays that small. Text that matches native macOS exactly (with the optical size set to the font size, 7% to 17% wider than today) is a visual change, so it is out of scope here, like embedding a font.
   - *The gate:* tile text changes at plan step 2.4b, and each view's text changes when phase 3 moves that view. At each such step, the `--screenshot-window` pixel diff is identical outside the bounds of the moved text and of any decided change the pull request lists (design goal 5) (masked from the union of each label's old and new text box, two physical pixels wider all round for ink past the advance; the tool is the ignored test `text_gate` in `crates/loom-app/src/screenshot/text_gate_tests.rs`), every `locate` answer is unchanged except those the plan's phase 3 layout gate lists, with their old and new rectangles, the pixels inside those bounds may differ, and the pull request records the change in width per label (least, greatest, and median). That screenshot is then the new baseline, and the pixel-identical gate resumes from that step on. Between 2.4b and the end of phase 3, the canvas and the panels set the same face two ways, and that is accepted.
   - System fonts fill in missing glyphs, as now.
   - *Why:* a different font measures differently, which moves `locate` answers, hit tests, and layout. A gate per view keeps every such move visible and small. Embedding a UI font of our own would make text the same on every platform, but it changes how the app looks, so it is out of scope here.
7. **The multi-line field, the Authors box, is built with plan row 4, the inspector,** which draws both Authors boxes: patch info's, shown when nothing is selected, and a selected sub-patch's. It stays on Iced's `text_editor` until that row. It is the single-line field's `FieldState` with a setting for one line or many, so the two keep one editing core. Its role and keys follow WAI-ARIA's `textbox` with `aria-multiline` set to true (ARIA 1.2, `#textbox` and `#aria-multiline`), which behaves as HTML's `textarea` does; the APG has no pattern of its own for a text box. Where ARIA says nothing, the platform's own text views decide, and each departure says why. Brylie chose these on 2026-11-19.
   - **Enter inserts a line break,** as ARIA's note on `textbox` says a multi-line text box does. One author per line is what the box is for. The field does not take Cmd+Enter on a Mac or Ctrl+Enter elsewhere: they go on to the app's shortcuts, which do nothing while a field has focus (section 6, rule 6, step 6). No key commits.
   - **Only focus leaving ends editing.** It ends the field's own undo (rule 3). What it puts in the patch's undo history is as today, and differs by box ([patch metadata](patch-metadata.md)): patch info's Authors box makes no patch undo step, since root patch info is not undoable ([undo](undo.md#what-is-not-undoable)); a sub-patch's Authors box makes one, at the moments patch metadata lists. Escape passes on to the app, as today.
   - **Tab moves focus and never inserts a tab,** as in an HTML `textarea` in a form, and as WCAG 2.1.2 (no keyboard trap) needs.
   - **While it has focus, the box keeps the text as typed,** empty and trailing lines included, so Enter after a name leaves room for the next. The app keeps that text as the field's draft and gives it back at each layout, so no layout while typing replaces it. The stored authors are still tidied on each edit, as today (trimmed, with empty lines and repeats dropped: [patch metadata](patch-metadata.md), rule 2). When focus leaves, the draft goes, and the box shows the stored list, so what it shows is what is saved.
   - **It wraps to its width and grows with its lines,** as today, so it has no scroll of its own. The panel scrolls to keep the caret in view.
   - **Up and Down move one visual line and keep the caret's horizontal place** (Parley's `move_up` and `move_down`). On the first line, Up goes to the start; on the last, Down goes to the end †. Shift extends the selection.
   - **On macOS, the platform's text views exactly** †:
     - Home and End scroll the panel so the box's start or end shows, and do not move the caret. *Departure from the single-line field,* where they move it: a macOS user meets this in every text view.
     - Ctrl+A and Ctrl+E go to the start and end of the line.
     - Cmd+Up and Cmd+Down go to the text's start and end, and Cmd+Left and Cmd+Right to the visual line's.
     - Option+Up and Option+Down go to the paragraph's start and end.
   - **On Windows and Linux** †: Home and End go to the visual line's start and end, Ctrl+Home and Ctrl+End to the text's, and Ctrl+Up and Ctrl+Down to the paragraph's. Page Up and Page Down move by the box's height in lines, and at the ends go to the start and end.
   - **Paste, the IME commit, and a screen reader's SetValue and ReplaceSelectedText keep line breaks,** through `multi_line`, beside `one_line`: CRLF, CR, U+2028, and U+2029 become LF, a tab becomes a space, and other control characters are dropped.
   - **Its node is `Role::MultilineTextInput`** (AccessKit 0.25), with the single-line field's actions: Focus, SetValue, SetTextSelection, and ReplaceSelectedText. Its value is the text with `\n`, and its text runs are one or more per visual line, linked along each line. Its label stays "Authors, one per line". This closes today's gap, where a screen reader can read the authors but not edit them.

   *Why:* it is the last of Iced's text widgets, so phase 4 waits for it, and building it with its one view gives it that view's parity gate at once. † From the platforms' descriptions, not checked by hand on each platform when this was written: check in the Manual QA round.
8. **The text crate is Parley** (decided 2026-11-11), with glyphs rasterised by `swash` into a `wgpu` atlas of our own. The comparison is in the [research note](../research/2026-11-text-crate-choice.md). It ranked the two candidates, `cosmic-text` and Parley, by these criteria in this order: IME composition in a single-line field; reporting text runs, caret, and selection to AccessKit; one font system for the canvas and the panels; how glyphs are drawn; the same system font as today; licences and versions. *Why:* Parley's editor composes for IME, the first criterion, and is a plain-text editor of the kind our fields are. Its word boundaries follow ICU. It is general-purpose text layout, which suits a UI layer meant for other audio tools too. `cosmic-text`'s lead on the font system, the glyph drawing, and the font match came from Iced being in the app, and ends with it. The costs accepted are an atlas of our own (about 680 lines; Vello can be weighed once our `wgpu` reaches 30), two font systems until phase 3, a change to text widths once for tile text at step 2.4b and once for each view as phase 3 moves it, with the canvas and the panels set two ways in between (rule 6), 35 crates, and Parley's faster pace of breaking releases, which we take by pinning a version and keeping Parley's types behind our own. Parley's `complex-scripts`, dictionary word breaking for Thai, Lao, Khmer, Burmese, Chinese, and Japanese, is on by default through `loom-ui`'s and `loom-app`'s features of that name, and a smaller build can leave it out (see the decisions).
9. **The canvas draws its own text** (plan step 2.4b). Iced draws only the canvas's background.
   - One `Typesetter` (`loom_ui::paint`, moved from the canvas at plan step 3.1) sets every run, with Parley's `system-ui`. Measuring and drawing read the same cached layout, so a box laid out by a measurement holds the text drawn in it. A layout is kept while frames use it and dropped one frame after the last one that did.
   - A text field's caret and selection come from its editor's layout, shaped with the same fonts and the same style properties as the run the typesetter draws (one function says what they are), and a test holds the two together at every cluster boundary (`the_caret_lines_up_with_the_drawn_text_at_every_boundary`).
   - Every run is shaped in full, with fallback fonts. There is no cheaper path to ask for: Parley has none, and layouts are cached.
   - The canvas paints into a list of layers. Inside a layer, a later piece is over an earlier one, text or box: a selection highlight goes before its text, and a caret after it. A layer is over every layer before it, and is cut to its clip.
   - The system's fonts are scanned once per process, and a canvas holds the font files it has used, so a new canvas on New or Open scans nothing and a font keeps its glyph images. On Linux, fontconfig is loaded when the app runs, not linked when it builds (fontique's `fontconfig-dlopen`), so a build needs no fontconfig headers.
   - The atlas never panics when full: it frees glyphs the frame did not use, then grows, and at its largest size leaves the rest out and counts them (`glyph_skips` in the bench report).
   - *Why:* drawing text inside the canvas's own primitive keeps a floating box over the tile text under it without Iced's layers, and is where phase 3 goes for every view. One layout for measuring and drawing rules out a box sized by one text system and filled by another.
10. **Rich text is one paragraph with spans over it** (plan 3.2, rows 5 and 6, built first for help's notes). `Element::rich` joins `Inline` pieces into one text that wraps, and each piece is a `Span` over its bytes: its weight, its face (the interface font, or the system's monospace for code), its colour, and an underline. The typesetter sets the whole paragraph in one Parley layout, so its lines break as one paragraph, and each span's index plus 1 is its glyphs' brush, so a painter finds each glyph run's colour and underline from its span; brush 0 is text past the last span, which takes the text's own style. Weight and face key the layout; colour and underline are painted, so they key none. An underline is drawn at the font's own underline place and thickness, after the glyphs, cut to the run's clip as its glyphs are. `TextStyle` names no face: a code block is a rich paragraph with one monospace span, so the face lives only on spans. A paragraph holds at most 65,534 spans, as many as a brush counts beside 0; a debug build panics past that, and a release build paints the rest as the last.
   - **A link is a part of its own.** An `Inline` made a link (`Inline::link`) is keyed under the paragraph's UI ID, or under the one around it when the paragraph has no key, and is a focus stop with its own node, held by the paragraph's node. It has no layout node: after layout, its place is asked of the text (`TextMeasure::span_rects`), one rectangle per line its words are on, each as tall as its line, at the width the paragraph is painted at. Its bounds hold them all, for its node and for `locate`; hit-testing tries each rectangle, so a link the width breaks is hit on both lines and not on the words between; and its focus ring goes around each rectangle. The paragraph paints the link's words; the link paints nothing. Its rectangles are measured from the paragraph's content corner, so a scroll container that moves the paragraph moves them too, with no new measure.
   - **Keys and the pointer** (WAI-ARIA's link pattern). Enter follows a focused link when it goes down; Space does not, since it is not a link's key, and goes on, as a page's Space scrolls. A press follows it on release and takes no focus, as a button's does (section 6, rule 3).
   - **Its look is the app's.** `loom-ui` gives a link no colour or underline of its own; the app sets them with the piece's colour and underline, so a link shows by more than its colour (WCAG 2.2, SC 1.4.1).
   - A measure that does not set text, such as a test's, may leave `measure_spans` and `span_rects` to their defaults: the spans are ignored, and a range is placed on one line by measuring the text before it.

   *Why:* a link inside a sentence must reflow with the sentence, and only the text knows where its words land. One layout for the paragraph, asked where a range lies, keeps the hit area, the ring, and the screen reader's bounds on the words the user sees (section 7, rule 1), with no text engine of our own (rule 1).

## 9. Custom elements

**Status:** Agreed, phase 1 for the canvas's input and drawing (plan steps 1.2 and 1.3), phase 2 for the full contract. The host contract for phase 4 (plan step P1), the items marked "Host" under rules 1 to 8: Agreed in what it covers (Brylie, 2026-11-25) and in its shape (Brylie, 2026-11-26). Built in `loom-ui` at plan step P1 (`custom.rs` and `custom/`): state kept by UI ID, the pointer with capture, keys, the home element, and focus on inner parts, the cursor, deadlines and animation frames, nodes and actions, the paint path, and the GPU path, with a frame's plan cut at each element (`Panels::frame_plan`, `prepare_gpu`, `draw_frame`). `examples/custom.rs` (a level meter, no GPU) and `examples/xy_pad` (an XY pad on the GPU) use it. No LoomDSP view uses it yet: the canvas moves onto it at plan step P4.

A custom element is the layer's supported escape hatch. The patch canvas is the first. Until phase 4 the canvas is an Iced widget at the window's root, and `loom-ui` has no way to host it. From P1, `loom-ui` hosts any custom element, with no patch words in its API (section 1, rule 1), and P4 moves the canvas onto it.

**The design point** (Agreed, Brylie, 2026-11-25). The host gets the app's model through the `App` trait or the view, never through a routing answer that comes later (the bridge's `Routed::Later`, section 5, rule 10). The canvas's input needs a model borrowed from the app (`CanvasModel`) while it handles an event, and today it gets one only because Iced's layers answer late, holding the app. It works when a plugin host drives the turn from its own callbacks, so the borrow assumes no `winit` loop and no thread of ours (section 9, A contract for every app, rule 3); the model is borrowed and not copied for each event, no `winit` type reaches the runtime or the trait (section 2, rule 9), and a headless test drives it with no GPU (section 10, rule 3).

**The model path: through the `App` trait.** **Agreed** (Brylie, 2026-11-26). The element's own trait gets `&App` on every call (each event, tick, paint, draw preparation, and node build), and the element builds its borrowed model there, inside the call. The app's glue type implements the trait; the runtime makes the element's state through an `App` method the first time a layout finds its UI ID (rule 1, its state lasts). Nothing is copied into the view, and there is no late answer. *Why not the view:* a model in the view must be owned and comparable, as a panel's is, so the canvas would copy its scene and selection every turn or wrap them in shared pointers, and it would lose the closure it holds. *Why not a method per element type on `App`:* `loom-ui` cannot name `CanvasModel`, and an app with a meter and a piano roll has two element types. *Why not app-owned state with a `&mut` hook:* that changes app state outside `update` (section 2, rule 1). This needs a new bound, `App: 'static`: the runtime keeps the elements as trait objects that it downcasts by type (rule 1, `update` reads its state), and a type that is downcast must be `'static`. `loom_app::App` and every example already meet it. The bound is on `loom_ui::App` from plan step P1. Because the host calls the element from inside whatever turn the driver starts, the same path holds under a plugin host's callbacks.

### Rules

1. **A custom element owns its own state, drawing, and input.** It gets pointer and key events inside its bounds, draws into a `wgpu` render pass with a viewport the runtime gives it, and keeps whatever retained data it needs (the canvas keeps its `Scene` and GPU buffers). Widened by the Host item "Two ways to draw" (Agreed, 2026-11-26): an element may also paint with no GPU.
   - **Host: layout bounds.** It is an element with a size, laid out with the panel around it (section 5, rule 5), and it reads its bounds, in logical pixels, from each layout. Layout, events, and its nodes need no GPU (section 10, rule 3).
   - **Host: pointer routing with capture.** It is a keyed, opaque leaf in the hit order (section 5, rules 1 and 7), and hears a pointer event inside its bounds at its layer's place in the route order. It answers that it left the event, took it, or took it and captures the pointer. While it holds a capture, it hears every pointer event first, in window coordinates, inside or outside its bounds, over any layer, and outside the window, until every button is up; no other element hovers or clicks meanwhile. The wheel is not captured. *Why:* a cable or a lasso is dragged across the right column and the window's edge today.
   - **Host: when a capture ends.** On the release of the last button. Otherwise it ends with a cancel, never a release, when: the window loses focus, is hidden, or is minimised, as a plugin host's DAW may do at any time; the driver reports the pointer lost (`PointerEvent::Lost`), as a web driver does on `lostpointercapture` or when the pointer comes back into the page with no button down; the app asks to release it (`Effects::release_pointer`); or the input layer rises above the element's layer, as when an overlay or a question opens mid-drag (Panic opening its question too). An overlay that opens mid-drag cancels the drag, so the gesture never finishes under a layer that now has the input (section 5, rule 1). An element that leaves the layout mid-drag is dropped, and hears nothing. The runtime cannot see which buttons are down, so a lost pointer is the driver's to report; the `winit` shell never needs to, since macOS, Windows, X11, and Wayland all deliver the release of a drag that left the window (corrected 2026-11-27 in P1: the Agreed text named the pointer coming back with no button down, which only a driver can see). *Why:* a cancel lets the canvas undo a half-made cable or move, where a release would complete it.
   - **Host: hover in and out.** It hears once that the pointer left it: the pointer moved off, a layer above took the pointer, or the pointer left the window. *Why:* the runtime passes each event to one owner, so an element can no longer learn this from events meant for others.
   - **Host: the wheel.** A wheel event goes to the element under the pointer first, as the innermost element. If the element leaves it, it goes to the nearest scroll container around the element, then outward (section 5, rule 12). *Why:* the canvas zooms with the wheel, and a piano roll in a scroll container may take Ctrl with the wheel and leave the plain wheel to scroll.
   - **Host: the cursor.** It says which `Cursor` it wants at the pointer. The runtime gives one cursor for the window: the captured element's, else the hovered element's, else the text cursor over a runtime field, else the default. The shell sets it (section 1).
   - **Host: its state lasts.** The host keeps the element's state by its UI ID across rebuilds and layouts, as other widget state (section 3, rule 4), and drops it, GPU data included, at the first layout that does not find that UI ID. So the app decides how long state lives by its choice of key: the canvas keeps one UI ID for every level, so a level change keeps its input state and GPU cache, as its place in Iced's tree does today (`the_camera_survives_opening_the_browser`), and a key that held the session's number would reset it on New or Open.
   - **Host: `update` reads its state in the same turn.** `update` can read an element's state by its UI ID through its `Context`, in the same turn as the event that changed it: the canvas's camera for `locate`, its focused control, its typed field.
   - **Host: its messages run in the same turn.** An element's messages run in the turn of the event that sent them, one update each, in order, before the turn's rebuild, as the routing target's do today. They do not wait for the next turn, as `App::clicked` does (section 2). *Why:* a drag's messages must change the model before the next pointer move is routed.
2. **It takes part in focus as one stop,** and manages focus inside itself (section 6, rule 1).
   - **Host: keys, in two cases.** It says whether it used each key, and a key it used is never handed on (section 6, rule 1).
     - *While the runtime's focus is on the element or inside it,* it is the focused element of section 6, rule 6, step 3. It hears a key after steps 1, 2, and 2b and before the runtime's Tab handling, so Tab and Shift+Tab move inside it until it lets them go, and the runtime then moves focus to the next stop. When Tab or Shift+Tab enters it, it hears which way it was entered, so it can start at its first or last part. *Why:* a piano roll or a second canvas is focused like any other stop.
     - *While nothing has focus,* the element the app names as the window's home hears the key at step 5, after the open overlay's keys. **Agreed** (Brylie, 2026-11-26, "Keep it, as today (Recommended)"): the patch canvas is the home element, so Delete, F, and the arrows work on the canvas with nothing focused, as `canvas_has_keys` does today. Under a question it hears nothing (step 2).
   - **Host: one Tab stop.** It is a stop when its builder makes it focusable, as for every element (section 6, rule 2), and the focus on it, or on a part inside it, is the runtime's focus. The focused part's UI ID is the element's UI ID followed by the path the element gives for that part.
3. **It gives accessibility nodes under its own UI ID,** one per inner part a user can reach (a tile, a control, a port), in its own focus order.
   - **Host: nodes in the tree.** The element adds its nodes, each with a path under its UI ID and a rectangle in window logical pixels. The runtime converts the rectangles to physical pixels (section 7, rule 8), cuts them by the element's clip, places the nodes under the element's own node, and gives them IDs from its one `IdTable` (phase 4, P6, section 7). A screen reader's action on one reaches the element, which turns it into messages that run in the same turn. Because `update` holds the app mutably, the runtime builds an element's nodes outside `update`, after a layout that moved the element or a turn that changed it, and keeps them until the next build; inside `update`, the nodes read are that kept copy, after the same wait for layout as panel nodes.
4. **It reports when it needs a redraw or animation frames.** That decides whether the runtime composes a frame, not which layers the frame holds: each composed frame draws every visible layer, the canvas included, from its retained GPU data. A panel change therefore redraws the canvas with no rebuild of its scene. Pan and zoom only update its uniforms (ADR-0010).
   - **Host: deadlines and animation frames.** It gives its next deadline, worked out from the moment the driver passes (section 2, rule 11), so the canvas's own clock goes, and asks for animation frames while it animates (section 3, rule 8). At a due deadline or a frame, it hears a tick with the driver's moment. A deadline's tick may send messages, which run in that turn. A frame's tick may change only the element's own state, and sends no message, because an animation frame draws and runs no update (section 2); a debug build panics on a message from a frame's tick.
   - **Host: two ways to draw.** An element may use either or both.
     - *Painting, with no GPU.* It paints boxes and text into the runtime's paint list, through the same `TextPainter` panels use, at its place in paint order. This shows in captures, in the headless recorder, and on the web without WebGPU. *Why:* a level meter or a piano roll's grid is boxes and text; twenty meters in one panel then cost one paint list and no extra pass. It also serves plugin hosts that limit a plugin's GPU use.
     - *The GPU callback.* Each composed frame, the host calls it with the `wgpu` device, the queue, a render pass on the frame's target, the element's viewport in physical pixels, the scale factor, and its scissor. The host owns the pass and the window (as `CanvasRenderer` expects today). Preparing GPU data happens only when the element's own data changed (rule 4). If the device or the target format changes (a plugin window reopened, a lost web context), the element drops its GPU data and keeps its input state.
   - **Host: draw order is paint order.** The runtime cuts a layer's paint list at each element that draws with the GPU. A frame draws what was painted before the element, then the element's GPU drawing, then its own painting and everything painted after it. So a parent's background is under the element and a sibling painted later is over it.
5. **It reports events to the app as messages,** and never edits app state itself. The canvas already works this way (`CanvasEvent`).
6. **It takes focus requests for its inner parts.** A focus effect whose UI ID names an inner part (a tile control on the canvas) is passed to the custom element, which focuses that part, and the tree reports it (section 6, rule 5). *Why:* a panel can then send focus into the canvas, as Enter on an outline row does, and the screen reader follows.
   - **Host:** a focus effect whose UI ID starts with the element's own is the element's. The host gives it the rest of the path and the element answers whether it found the part; one it did not find is dropped, as a focus effect on a missing element is (section 6, rule 2).
7. **Its nodes may set `controls` relations,** to its own nodes or to nodes outside it, by section 7, rule 13.
8. **Until the phase 4 cut-over (plan step P4), nothing in the window's base layer draws over the canvas.** From step 2.2c the app draws the canvas in a pass of its own, after clearing the frame and before Iced draws the window's layers (`iced_bridge/paint.rs`). Iced draws each layer's boxes before its shader primitives and its text after them, so this order matches what Iced drew only because the canvas is in the base layer and nothing else there draws over its bounds. Anything meant to show over the canvas (menus, the module browser, tooltips, the cable dragged across the window) goes in a later layer of the window's stack. The canvas draws its own background, which is not the window's. Its scissor is its bounds cut to the window only, not to the clip of any container around it, which Iced's primitive would have had; that holds while the canvas sits in no clipping container, such as a scrollable. *Why:* a box drawn in the base layer over the canvas would hide it, where Iced used to draw it below. The runtime's own panels in the Canvas and Panels layers draw after the canvas and before Iced, and those above after Iced (section 5, rule 10).
   - **From P4: the order with no Iced.** **Agreed** (Brylie, 2026-11-26). A frame clears, then draws each layer in paint order (rule 4, draw order is paint order): the Canvas and Panels layers, with the canvas element cut into the root panel's paint after its background; what an element draws above the panels; then the Overlays and Question layers. For today's window this gives the same pixels as drawing the canvas first, since nothing in its layer paints under it but the root's background. The dragged cable is drawn above the right column and below every overlay now too.
   - **Host: drawing above a layer.** An element may ask to draw a second time in a frame, after the panels of a layer it names (the Panels layer, for the canvas), for something that leaves its bounds while a gesture lasts: the cable dragged from a port to the inspector or the matrix. That drawing is cut to the window, not to the element's bounds, and asks for nothing else (no input, no nodes). *Why:* the cable is the canvas's, but it must show over the panels it is dragged to.
   - **The canvas's scissor** is its bounds cut to the window and to every clip around it, now that no Iced primitive decides it.

*Why:* a pure pipeline never covers everything. An editor or a canvas needs its own drawing and input. A hatch that is part of the contract keeps such elements inside focus, the accessibility tree, and the tests, rather than beside them.

### A contract for every app built on `loom-ui`

**Status:** Agreed (Brylie, 2026-11-26; plan step P0). It widens what Brylie decided by his scope note of 2026-11-25: `loom-ui` is the base for an ecosystem of accessible audio tools (effects, instruments, modular composition), so the host is written for them and not only for LoomDSP's window.

1. **The host is general.** Its API names no patch, canvas, module, or cable, and holds nothing the patch canvas needs that a meter, a waveform view, a spectrum, an XY pad, or a piano roll would not. The words above that name the canvas or the dragged cable are examples of use, not API. The meter and the piano roll below are the design cases the contract is checked against; P1's example program, with no LoomDSP crate, builds a meter and an XY pad, which are small and need no musical types:

   | Host part | Patch canvas | A plugin's level meter | A piano roll |
   |---|---|---|---|
   | Layout bounds | yes | yes | yes |
   | Pointer routing | yes | no: it takes no input | yes |
   | Capture during a drag | cables, lassos, tiles | no | notes, a selection box |
   | Keys, one Tab stop | yes, and the home element while nothing has focus | no: it is no stop | yes: arrows move the focused note |
   | Cursor shape | yes | no | resize at a note's edge |
   | Deadlines and animation frames | while something moves | frames while the level moves, none when silent (section 3, rule 8) | while playback moves the playhead |
   | Drawing | the GPU callback, and painting for its text | painting only, no GPU | painting for the grid and notes |
   | Nodes under its UI ID | tiles, controls, ports | one meter node, a live value (section 7, rule 7) | one per note, in time order |
   | Focus requests into inner parts | a tile control | no: it has none | a note |
   | Drawing above the panels | the dragged cable | no | a note dragged out of view, if ever |

   A part an element does not use costs it nothing: each is a method with a default, as `App`'s are (section 2). *Why:* a host shaped by one canvas would make the next app's element fight it, and every part the table needs is one a published UI crate is expected to have.

2. **Accessibility from day one, for custom elements too.** A custom element gives a node for every part a user can reach, under its UI ID, follows section 7's rules as built-in elements do (roles, names, values, actions, live values, hidden under the input layer), takes focus requests, and shows a ring for keyboard focus (section 6, rule 3). An element that draws pixels with no nodes is refused, by the same check built-in elements meet at layout (section 7, rule 2; `Layout::access_problems`): an element that takes input or focus and gives no node, or a node that breaks rule 2, panics in a debug build and is reported as an access problem in a release build, never a crash. A custom element that is a focus stop, or that gives nodes for its parts, has an `Access` of its own, so its parts sit in a node a screen reader can name. One that is purely for show, no focus stop and with no parts, may have none. A debug build also checks each turn that an element whose nodes it did not build again would have given the same nodes, so an element whose nodes follow the app's model but whose access version does not move is caught, not left stale. There is no "nodes later". *Why:* design goal 4; a hatch without this rule would be the one place a blind user meets a wall.

3. **Every target is first class** (design goal 3). Phase 4 builds only the desktop shell. The contract already holds for the others, so their drivers need no change to the runtime, the `App` trait, or the host (section 2, rule 9; OQ-13; OQ-23):

   | Host part | Desktop shell (`winit`) | Plugin window (CLAP, VST3) | Web (`wasm32`) |
   |---|---|---|---|
   | Events, routing, capture | from `winit`'s events | from the parent window the host gives us; capture through the platform's own call on that window | from the canvas element's DOM events; capture through pointer capture on it |
   | Keys | from `winit` | from the host, which may keep some for itself; a key it keeps never arrives, which is no change to the contract | from DOM key events, with `code` from `KeyboardEvent.code` (section 1, Keys) |
   | Deadlines and frames | the shell's loop | the host's idle or timer callback; we never own the loop, and the runtime never reads the clock (section 2, rule 11) | `requestAnimationFrame` and timers |
   | Drawing | painting, and a `wgpu` surface on our window | painting, and a `wgpu` surface on the parent window's handle | painting; a `wgpu` surface on the canvas element (WebGPU, or WebGL where `wgpu` offers it) for an element that uses the GPU |
   | Cursor | `winit` | the platform's call on the parent window | CSS `cursor` on the canvas element |
   | Nodes | `accesskit_winit` | an AccessKit platform adapter on the parent window | a DOM mirror of the same tree, by OQ-23's choice |

   What phase 4 guarantees for them: no `winit` type reaches the runtime, `App`, or the host; every answer from the system (clipboard, dialogs, capture) comes as a message on a later turn, never in the same call; the runtime never reads the clock or blocks. Known gaps, for the driver that meets them, not phase 4: a file dialog answers a `PathBuf`, which a web page cannot give (the first gap the web driver must solve), and the Tab wrap at the window's ends (section 6, rule 2).

4. **Which crates a sibling app uses.** An effect plugin or a mastering tool takes `loom-ui-core` (geometry, events, keys, UI IDs, text measuring), and `loom-ui`: with its `shell` feature for a stand-alone window, or without it, with `gpu` for painting (`loom_ui::paint`) and `clipboard` if it wants one, under a driver of its own for a plugin. Neither crate holds anything of LoomDSP's (section 1, rule 1), and P0 adds nothing to them. `loom-canvas` and `loom-app` are LoomDSP's and no sibling needs them. *Why:* the crates are candidates for publishing (FR-SDK-06), and a sibling that had to take LoomDSP's patch types to draw a meter would show the line was drawn wrong.

## 10. Test harness and control channel

**Status:** Agreed, phase 2. Rules 3 and 4 are built (step 2.3, items 2 to 4: `iced_bridge/measure.rs`, `ui_test/a11y.rs`); phase 1's tests in `a11y/tests.rs` still read the tree from `a11y/tree.rs` directly.

### Rules

1. **One runtime, two drivers.** The window and the headless `Ui` harness run the same code for events, layout, messages, and effects. Only the event source and the drawing target differ. *Why:* a test then checks what the app does, not what a copy of it does.
2. **The harness's event and query methods keep their meaning:** `headless`, `press`, `release`, `drag`, `move_to`, `hold`, `tap`, `tap_key`, `key_down`, `key_up`, `typewrite`, `click_text`, `control`, `control_bounds`, `field`, `value_field`, `text`, `focus`, `focused_field`, `output`, `input`, and the rest. Their call sites do not change. `run_task(Task<Message>)` becomes `run_effects(Effects<Message>) -> Vec<Message>`, with the same meaning: run until no messages are left, and return them all. Its call sites change mechanically in phase 2, in one commit with no other change. *Why:* every `loom-app` test (1,004 at commit `a781de4`) depends on the harness. Keeping the meaning fixed shows whether behaviour changed; renaming the one method tied to Iced is the only way to leave Iced.
   - **In phase 4, a type change at a call site is mechanical** (plan steps P2 and P4). **Agreed** (Brylie, 2026-11-26). Tests pass Iced's key, event, and geometry values to the harness today (`iced::keyboard`, `iced::Event`, `Rectangle`). Each such value becomes its `loom-ui-core` value, in its own commit with no other change, as `run_task` did in phase 2. The method names, what they do, and what each test asserts stay the same. A test that cannot keep its meaning (a bridge test that tests only the bridge) is deleted, and the pull request lists it with its reason; a bridge test that also tests behaviour is moved, not deleted. *Why:* the rule above keeps call sites fixed so a change in behaviour shows; a change of type alone changes no behaviour, and one commit of it is easy to check.
3. **Event tests need no GPU.** The harness lays the view out on a renderer that only measures: it lays text out with the same paragraphs the window's renderer draws, so every part lands where the window draws it, and it draws nothing. Drawing tests and captures render to an offscreen `wgpu` texture, and skip with `NO_GPU` where there is no adapter, or fail where one is required (`LOOM_REQUIRE_GPU=1`, as on every CI test job). *Why:* CI machines often have no GPU, and an event test should not depend on one.
4. **The harness can read and act on the accessibility tree:** `Ui::a11y_tree()` returns it, and `Ui::a11y_action(target, action)` performs an action on a node found by name. *Why:* a test can check the window the way a screen reader meets it.
   - A name is the node's accessible name, what a screen reader says. Names repeat (every filter tile has a Cutoff knob), so a target is one name, a path of names from the outside in (`["SVF", "Cutoff"]`), or a UI ID. `A11yTree::node(name)`, `path(names)`, and `node_by_id(id)` find nodes the same ways, and a node's own `node(name)` searches inside it.
   - A name that matches no shown node, or more than one, panics and lists what it found: the names there, or each match with the names above it. *Why:* a test never acts on the wrong node, and the panic shows how to scope the name.
   - Hidden nodes, and everything inside them, are not found, as a screen reader does not reach them. `node_by_id` finds a node whether it is shown or not.
   - `a11y_action` takes AccessKit's `Action`, for actions with no data. `Ui::a11y_set_value(target, value)` sends SetValue with text (`&str`) or a number (`f64`).
   - A request reaches the app as the adapter's does, an `a11y::Event::Action` message. It runs until no messages are left, and then the next frame is drawn, as in the window.
5. **A control channel command always gets its reply.** A command that waits for the window to be drawn asks for a message once the next frame is shown (section 2, the effects table), which also makes the runtime draw. So the two-frame wait of [control channel rule 5](control-channel.md#rules) completes even when the command changes nothing visible, with no animation frames and no update per frame. This replaces `ControlFrame`. *Why:* without a frame to wait for, a command that changes nothing would never be answered, and a script would hang.
6. **The control channel's protocol does not change.** `locate` finds targets from layout data and UI IDs, not from a toolkit's widget tree, and answers in logical pixels. Its replies are the same for every example in the [control channel spec](control-channel.md), except a reply a decided change alters (design goal 5): its pull request lists the example, the change, and the new reply, and updates the example in the control channel spec. *Why:* agents and scripts built on it keep working.
   - *Until the phase 4 cut-over (ruling, 2026-11-15; its end moved from phase 3 to P4 by Brylie, 2026-11-25):* the end state above lands one view at a time. `locate` already finds a module, a control, a port, a light, a meter, and a badge from the scene and the canvas's camera, and a canvas UI ID from the accessibility tree. Three things still come from Iced's widget tree, through the `Find` window question (section 2): the canvas's place in the window and its live camera, the parts Iced draws (their named containers, `places.rs`), and text shown in the window. Each comes from our layout when its view moves (plan, step 3.2), and the question goes with the last one, in P4 (Agreed, Brylie, 2026-11-25). A part that has moved (the stats bar, from row 1) is placed from the runtime's layout through the context (`Context::bounds`, and `Context::text_bounds`, which gives only the part of the text that shows, cut by the clips around it, and finds no text clipped away entirely), and the tree takes its nodes the same way (`Context::access_nodes`). Both wait for a current layout: when a turn rebuilt the view and no draw has laid it out yet (`Context::laid_out` is false), the answer is sent again after the next draw (`Effects::after_draw`), when the layout is current, so it waits once and never reads a layout half made. A `locate` that Iced or the canvas answers waits for nothing, since it reads none of the runtime's layout, so a search of Iced's parts is never replayed after a resize. A tree rebuild asked for while one waits starts no second one, but one more runs after it, so a change made during the wait (an autosave's warning in the bar) reaches the screen reader too. *Why:* until a view is ours, only Iced knows where it drew it, and working the place out a second time could disagree with the screen (section 7, rule 1). The app's copy of the camera is not used instead, because the canvas reports it when a pan ends, not on every move.
   - *From P4:* the canvas's place comes from the runtime's layout and its live camera from the custom element itself, read in the same turn; text from `Context::text_bounds`. `places.rs`, the `Find` question, and the pointer injector go: a control channel pointer command is a `DriverEvent`, routed as a real one. Every `locate` answer is recorded before and after P4, for every kind of target, and the pull request lists each one that moved. **Agreed** (Brylie, 2026-11-26).
7. **A view's layout changes once, when phase 3 moves it, apart from a decided change** (design goal 5), and the [plan's parity gates](../dev/leaving-iced-plan.md#parity-gates) say how that step is checked: what may differ, and what is recorded. *Why:* one place says it.
