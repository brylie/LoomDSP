# P1 UX Audit, Round 2: The App on Stage

- **Kind:** Research snapshot. Non-normative.
- **Date:** 2026-11-01, on `main` at fd6f938 (after #485).
- **Follows:** [the first P1 UX audit](2026-11-p1-ux-audit.md). All its issues (#453 to #460) are closed.
- **Used by:** issues #492 to #495 and #497, and comments on #463, #330, and #289. Decisions go in specs or ADRs.

The first audit asked for a new snapshot after its fixes. This one checks the app again, and covers what the first left out: MIDI learn mode, Preferences, keyboard focus, the probe and tile menus, screen readers, and contrast outside the module headers. It reads the app first as a live performer would (Tomas, use case UC3, the top use case in [personas and use cases](../product/personas-and-use-cases.md)). Where a learner needs something else, the finding says so. Do not update this snapshot later; write a new one after the fixes.

## Method

- Rendered `subtractive.ron`, `fm-feedback.ron`, and `examples/dev/test-widgets.ron` with `--screenshot-window`, with and without a module selected, after 4800 frames of the engine.
- Rendered the canvas with `--screenshot` at zoom 1 and zoom 2, scale 2, with a knob focused (`--focus 4:cutoff`).
- Read geometry from `--dump-ui`: port centres and the port hit radius.
- Computed WCAG contrast ratios from the colour tokens in `style.rs`, the app theme (`main.rs`), the canvas palette (`loom-canvas/src/theme.rs`), and the signal colours (`loom-core/src/signal.rs`).
- Read the view and input code for the toolbar, status bar, Preferences, MIDI learn, the canvas widgets, and the keyboard handling. Read the specs for panels, panel widgets, modulation, MIDI learn, panic, undo, files, preferences, help pages, the module browser, and control ranges, and the requirements and personas.

**Limits.** No live window was driven, so nothing here was heard or seen in motion. Hover states, pop-ups, and dialogs were judged from code. The window screenshots do not open the patch the way the app does (finding 18), so their canvas shows label bars where the app shows words; the zoom 1 canvas images were used for text.

Priority means: **High** blocks a task or misleads the user; **Medium** slows the user or looks broken; **Low** is polish.

## Summary

The first round's fixes hold. The toolbar is calm, button roles are clear, family colours are tested for contrast and colour blindness, patches open at a zoom where labels show, and the matrix fits its column. The type sizes now live in one module, and a test stops new inline sizes.

The weak parts are now about trust under pressure. A performer cannot tell an error from a success in the status bar, cannot see at a glance that learn mode is on, and can stop the transport with a stray Space. Several colours carry two meanings, and many canvas targets are smaller than a finger or a trackpad on a dark stage allows. The biggest gap is that performance mode, the view built for the stage, has no spec yet.

## Findings

### 1. Performance mode has no spec (High)

FR-PERF-01 (Must, M2) asks for a view that shows only the front panel, locks edits, and uses large controls. UC3 is the top use case. `panels.md` lists it as out of scope because it "has its own spec", but `docs/design/` has none. Findings 3, 6, and 10 all point here: a stage view with big controls, no cables, and a clear state line would answer them for the performer, while the canvas stays a place to build and learn.

Direction: write the spec before M2 work starts. It should settle what is shown, what is locked, how a performer leaves it, how MIDI learn and panic look in it, and what state is always on screen (audio, load, learn, transport).

### 2. Errors and successes look the same (High)

The status bar's right side is one line of `self.status`, set in over 100 places. An error ("Audio: "MOTU" was lost."), a warning, and a success ("Mapped CC 74 to SVF #4 Cutoff") have the same dim grey text, the line is cut to the width, and the next message replaces it. A message that matters on stage, such as the loss of the audio device, can be gone before anyone reads it.

`Settings::handle_audio_loss` (`crates/loom-app/src/settings.rs:1014`) takes a `_reason` and never shows it, so the user does not learn whether the device was unplugged or stopped calling back.

Direction: give status messages a severity (info, warning, error), with an icon or shape as well as a colour. Keep the latest error on screen until it is read or its cause is gone. Show the reason for an audio loss.

### 3. Nothing lasting says learn mode is on (High)

Turning learn mode on sets the status to "MIDI learn: click a control to map it" (`crates/loom-app/src/main.rs:1700`), but the next status message replaces it. After that, learn mode is shown only by the toolbar button's colour and the blue outlines on controls. In learn mode, screen controls do not change values ([midi-learn.md](../design/midi-learn.md)). A performer who forgets learn mode is on sees knobs that do nothing.

Direction: a lasting, labelled indicator while learn mode is on (for example a fixed "Learning" field in the status bar, or a banner over the canvas), shown with a word, not only a colour.

### 4. Space toggles Run while a knob is focused (Medium)

The keyboard table in [panels.md](../design/panels.md#keyboard-without-a-mouse) says a knob does not take Space, and a key with no use passes on to the next owner. So with a knob focused, Space reaches the global Run and starts or stops the transport. The rule is sound for most keys, but Space is the one key that stops the music.

Direction (needs a spec decision): either a focused knob takes Space and does nothing, or Run is never toggled while a panel control has focus. MIDI learn already gives Space a meaning on a focused control, which a single rule would cover.

### 5. Hold note is disabled with no reason (Medium)

With no audio or no MIDI, Hold note is greyed out with no hover text. The control channel already has the reason, "Hold note is disabled: no audio is playing the engine" (`crates/loom-app/src/control/resolve.rs:223`), but the window never shows it. Direction: show the reason as hover text on every disabled toolbar button.

### 6. Words or the whole patch, never both (Medium)

Opening a patch frames it at no less than the zoom where labels draw (`Camera::frame_readable`, `crates/loom-canvas/src/camera.rs:95`). This fixed the first audit's finding 2. The cost is that a wide patch shows only its left part, and zooming out to see it all turns every label into a bar. A performer wants the whole patch and the values that matter at once.

Direction: answer this in performance mode (finding 1). On the canvas, a zoomed-out level of detail could still draw the values of focused and MIDI-mapped controls. That idea would need its own spec change.

### 7. One orange means five things (Medium)

`#F5A623` is the selection outline, the value arcs on knobs, toggles and segments, the primary button, and the amber load warning in the status bar. The pitch signal colour `#F09A3E` is only 1.10:1 from it. A selected tile with a pitch cable on it reads as one orange mass, and an amber load warning looks like a value.

### 8. Red and yellow mean two things each (Medium)

The audio signal colour `#E04F4F` is the theme's danger colour, the canvas warning colour, and the top of the meter. The gate colour `#E8D24A` is the theme's warning colour. A red cable and a red warning share one meaning on screen that they do not share in fact.

### 9. Some cues are colour only (Medium)

Port shapes split signals into two groups (`signal_shape`, `crates/loom-app/src/scene.rs:29`): pitch and gate are square, and audio, modulation, and phase are round. Inside each group, only colour tells them apart. Pitch (orange) and gate (yellow) are close in hue and close further under protanopia and deuteranopia. The status bar's load severity, the meter zones, and the MIDI learn button state are also colour only. NFR-UX-03 says colour is never the only signal.

Direction for 7 to 9 (needs a visual-system spec change): give selection its own hue or a shape cue (a corner mark, a thicker outline); keep the signal colours apart from the danger and warning roles; add a third and fourth port shape, so each signal kind has its own; and add a word or icon to each severity colour.

### 10. Many canvas targets are under 24 px (Medium)

WCAG 2.5.8 asks for pointer targets of at least 24 by 24 px. At zoom 1:

| Target | Size | Where |
|---|---|---|
| Port hit area | 18 px across (radius 9) | `loom-canvas/src/scene.rs` |
| Toggle | 22 by 11 | `loom-canvas/src/controls.rs` |
| Select box | 9 high | `controls.rs` |
| Segment | 11 high | `controls.rs` |
| Modulation badge | 9 high, 7 px text | `loom-canvas/src/scene.rs` |
| Resize grip | 4.8 by 4.8 | `loom-canvas/src/widget/draw.rs` |
| Knob depth ring | about 4 px from the value ring | `controls.rs` |

Ports sit 16 world units apart, so their hit areas nearly touch. Everything shrinks further below zoom 1; only ports have a floor of 7 screen px. Port labels are 9 px at zoom 1. For a learner at a desk these sizes work; for a performer on a laptop trackpad in a dark room they are hard.

Direction: grow hit areas without growing the drawing where space allows (a hit area may be larger than its mark), keep the depth ring apart from the value ring, and let performance mode own large controls.

### 11. A focused knob's value runs into the next caption (Medium)

While a knob is focused or turned, its caption shows the value with its unit. On SVF, "300.0 Hz" in place of "Cutoff" runs straight into "Resonance", with no gap, at zoom 1 and zoom 2. Captions are fitted to their cell (`fit_label`, `crates/loom-canvas/src/scene.rs:881`), but the value text is not.

Direction: fit the value to the same cell, or let it use the gap to its neighbours and hide the neighbour's caption while it shows. Extend the `--dump-ui` `shown` check to value text so a test catches it.

### 12. Contrast failures outside the headers (Medium)

Ratios computed from the tokens:

| Pair | Ratio | Needed |
|---|---|---|
| Panic label: theme text `#E6E8EE` on `#E04F4F` | 3.17 | 4.5 |
| Panic label: white on `#E04F4F` | 3.89 | 4.5 |
| Panic label: `#22242A` on `#E04F4F` | 3.99 | 4.5 |
| Danger `#E04F4F` as text on the background | 3.99 | 4.5 |
| Tile border `#3C404A` on canvas `#1C1E23` | 1.61 | 3 (non-text) |
| Knob track `#454954` on control body `#3A3E47` | 1.19 | 3 |
| Unlit light `#353840` on tile `#2B2E35` | 1.16 | 3 |

None of the app's text colours reaches 4.5:1 on this red; only near-black text does (pure black is 5.4:1). A darker fill with light text is the likelier fix. The Panic button is the one control a performer must find without looking twice. In the window screenshots, disabled toolbar buttons (Hold note, Undo, Redo) are also hard to tell from enabled ones. These belong to the open [#463](https://github.com/brylie/LoomDSP/issues/463), which checks every colour pair.

### 13. The specs disagree on keys (Medium)

- **Tab with a module selected:** focus the next control (`panels.md:411`, `module-browser.md:106`), or select the next module (`panels.md:677`, the newer table, which the code follows).
- **Enter on a focused knob:** act on it (`panels.md:678`), open the type-a-value field (`panel-widgets.md:140`), or arm it in learn mode (`midi-learn.md:41`).
- **Double-click on a meter:** open the larger view (`panel-widgets.md:110`) or reset the clip light and peak (`panels.md:481`).
- **Arrow keys and undo:** presses within 500 ms join one step (`panels.md:686`, and the code), or each press is one step (`undo.md:192`).
- **Escape:** cancels a drag, hides pinned lines, clears focus, clears the selection, ends learn mode, closes overlays, and leaves matrix cells, across four specs, with no one order that includes learn mode.

The code's shortcuts are spread over about eight files (canvas input, panel input, `main.rs` in three places, `panic.rs`, `matrix.rs`, the browser). The shortcut list users see, `HELP` in `main.rs`, is kept in step by hand.

Direction: one keymap table in one spec that settles each conflict, and one table in code that both the key handling and the shortcut list read.

### 14. A and Cmd+A (Low)

A bare A opens the module browser; Cmd+A selects all. Both are common conventions, and nothing needs to change, but the keymap table in finding 13 should record it, so no third meaning lands on A.

### 15. Small panel and inspector issues (Low)

- **Envelope:** the Mode caption, the ADSR/AD segments, and the Level light stack above the Curve knob, so the light and the knob read as one control. The first audit's layout rule puts a light next to what it reports.
- **Resize grip:** a small blue square at the bottom right of resizable tiles (Scope, the test panels), with no hover state and no hover text. A learner cannot tell what it is.
- **Inspector:** "+ Add modulation" follows every parameter's slider, so the inspector is about twice as tall as its parameters. One button per module, or one shown on hover, would do.

### 16. Chrome tokens (Low)

- There are no spacing tokens: the app uses 12 spacing values and 14 paddings. There are no radius tokens: 3, 4, and 5 in the chrome, 5 and 7 on the canvas.
- The status bar's severity colours are hard-coded in `main.rs` (`severity_colour`), outside `style.rs`, and the alarm red `#EB6B6B` is not the theme's danger `#E04F4F`.
- The right column's width, 280, is written in two places.
- The window has no minimum size. The toolbar is one row that does not wrap, so a narrow window cuts it.
- The text sizes 11, 12, and 13 (SMALL, BODY, CONTROL) are hard to tell apart; the scale has little contrast at the small end.

### 17. Specs out of step with the code (Low)

- `panels.md` (Widgets) still uses the names slider, selector, and graph, which panel-widgets.md renamed fader, select list, and curve, and calls panel-widgets.md "Draft"; it is Agreed.
- `panels.md` says the mouse wheel always zooms. The code zooms on a wheel, but pans on a two-finger trackpad scroll and zooms only with Cmd or Ctrl (`crates/loom-canvas/src/widget/input.rs`). The code's rule is the better one for laptops; the spec should say it.
- The probe menu section of `panels.md` says right-clicking anything but an output or cable opens no menu, but right-clicking a tile opens a menu with Help ([help-pages.md](../design/help-pages.md)). The canvas context menu, [#330](https://github.com/brylie/LoomDSP/issues/330), is where these meet.
- The roadmap's M1 checklist is behind the specs: several features marked Implemented in their specs are unchecked there.

### 18. Window screenshots frame the patch differently (Medium)

The app frames a new patch with `Camera::frame_readable` (`crates/loom-canvas/src/widget/input.rs:135`). `--screenshot` and `--screenshot-window` use `Camera::frame` (`crates/loom-app/src/screenshot.rs`, `fn camera`), although its comment says "as when a patch opens". So every window screenshot shows label bars where a user sees words, and a review from screenshots will report a problem the app no longer has. This is a tooling bug, but it misleads the people who check the UI, so it is Medium.

Direction: frame with `frame_readable` and the canvas's readable zoom, and test that the screenshot camera matches the app's opening camera.

## What works well

- **One type scale, enforced.** Every text size is a named token in `style.rs`, and a test fails on an inline size.
- **Button roles.** One primary per view, quiet secondary buttons, and a red Panic. The first audit's "everything is orange" is gone.
- **Family colours** with tested contrast and colour-blind distance.
- **Focus ring only after keyboard use**, around the control and not its caption, so it never covers the value.
- **Shape previews** on Envelope, Ladder, and LFO, now drawn as smooth lines.
- **Hover text everywhere**, with label, description, and stable name, so a cut label is never a dead end.
- **The inspector's ranges** ("audio, -1 to 1") and units on every value.
- **Module browser:** search matches every word and ranks names that start with the query first.
- **Preferences:** every choice applies at once, and buffer sizes show their time in ms.
- **Panic** works in a text field and during a drag, and can be mapped to a MIDI control.
- **Undo names its step** in the toolbar hover text.

## Suggested order

1. The screenshot framing bug (18, #497). It is small, and later before and after images depend on it.
2. Status a performer can trust (2, 3, 5, #493). It is the cheapest change that makes the stage safer.
3. The focused knob value (11, #497). A visible bug on the most used filter.
4. The keymap spec (4, 13, 14, #494), then the colour spec (7 to 9, #495). Both need decisions first; the colour work also feeds #463.
5. The performance mode spec (1, #492). It decides how much of findings 6 and 10 the canvas must solve itself.
6. Pointer targets (10) and chrome tokens (15, 16), both in #495, and the spec drift (17, #497), beside the others.
