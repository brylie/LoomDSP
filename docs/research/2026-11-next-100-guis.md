## What the article says, in short

This is a paraphrase, not the article's own words.

- **The state of Rust GUI.** Shipping apps are often slow and bloated, and many cross-platform ones are built on Electron. Platform toolkits have stagnated. Rust UI is still adopted slowly. The author expects many new experiments, helped by AI-assisted development, with no settled consensus on the UI layer yet.
- **Shared layers are maturing.** Most new Rust toolkits now share Parley for text and AccessKit for accessibility. The author calls both solid, but says AccessKit integration quality varies, rich text editing still needs work, and accessibility can cost performance. His example is a toolkit that rebuilds and diffs its tree every frame.
- **Immediate mode is easy at first and hard to finish.** The last part of the work gets hard: stable widget identity for accessibility, cached text layout, and use of compositor layers. He also notes that mainline Iced lacks accessibility.
- **Keep design apart from execution, with a spec at the interface.** He sees a toolkit's core as an incremental computation engine. He argues that clearly scoped modules with specs suit LLM-assisted work.
- **Optimise by separating what's static from what changes.** Precompute the static parts. Use layers carefully, because each costs memory and too many slow things down.
- **Separate the reactive layer from the widget layer.** Xilem's reactive layer is kept apart from its widget layer, Masonry, so the same widgets can serve more than one front end.
- **Web standards: adapt them, don't follow them slavishly.** The DOM is heavy. A lighter tree and a curated CSS subset may fit apps better. Virtualised lists are a gap.
- **"Native" has no clear meaning on the desktop.** Matching each platform's gestures, scroll dynamics, and input methods is still not solved for cross-platform toolkits.
- **Advice.** Be bold, build on solid foundations, use well-defined specs where they exist, and work with upstream open source without flooding maintainers with low-quality pull requests.

## Where LoomDSP already agrees

| The article's point | What LoomDSP does |
|---|---|
| Reuse the shared layers | Text through Parley and accessibility through AccessKit (ADR-0041, decision part 3). The runtime, layout, and painting are our own (`loom-ui`), on top of them. |
| Retained mode with stable identity | Every element has a `UiId` from the app's model. A panel is rebuilt only when its model changes. Focus, hover, and the accessibility tree all key on the same IDs. |
| Accessibility must not cost every frame | The tree is sent only when something it reports changes, and only the nodes that changed. Live values are sent at most every 250 ms. With no screen reader active, nothing is built (UI layer spec, section 7, rule 7). |
| Separate static from dynamic | The canvas rebuilds GPU data only when the scene's generation changes. Panel control values have their own buffer. An unchanged paint list is not prepared again. Changes are measured: for example, the shadow's wider shape instance in row 3a, within noise on a 300-module patch. |
| Specs at the interface | Spec first (`docs/design/`), with design tokens (`visual-system.md`) and WAI-ARIA patterns cited for every widget's keys and roles. |
| Iced lacks accessibility | One of the reasons LoomDSP leaves Iced (#683). |

## What we might act on

1. **Accessibility for a UI drawn into a browser canvas.** The web is a first-class target (UI design goal 3). A UI drawn into a canvas is invisible to a browser's screen reader unless something mirrors it into the page's accessibility tree, usually through hidden DOM elements. `cargo search` on crates.io on 2026-11-22 found no AccessKit adapter for the web among its official crates. The ones listed are the core crate, `accesskit_winit`, and the platform adapters. This is the largest risk the article raises for LoomDSP. It is opened as [OQ-23](../product/open-questions.md#oq-23-accessibility-for-a-ui-drawn-in-a-browser-canvas).
2. **Contribute what we learn about AccessKit, carefully.** Our text fields hit the article's "rich text editing still needs work" directly. Examples: macOS ignores `aria_current`, positions in a set count from zero with the size on the container, and runs are bounded per line. Each upstream filing needs Brylie's approval (#683's pending item 1.5). It should be a single, well-evidenced report or fix, as the article asks, not a flood of small pull requests.
3. **Keep `loom-ui` free of LoomDSP's own models.** The article's reactive and widget split supports the plan to share UI layers with focused sibling apps, such as mastering or a piano roll. `loom-ui` already knows nothing of patches or modules. Keep it that way, and keep the app's view models on the app's side.
4. **Virtualised lists.** The module browser and Your patches draw every row in their scroll container (4a). That's fine for today's library sizes, but a large user library would lay out every row. Note it as a known limit of the scroll container. Measure before building virtualisation.
5. **Platform feel beyond the keyboard.** Our keys follow each platform's conventions. Trackpad scrolling has no spec yet, such as macOS momentum and elastic overscroll, and neither do gestures. Write that down as an open item for the scroll container, so the gap is known.
6. **The renderer's limits.** Our painter draws rounded boxes, glyphs, cable strips, and now shadows. That's enough for today's audio UI. The article judges another toolkit by its missing gradients, blending, and filters. If later visuals need them, such as spectrum fills, blurred overlays, or rich meters, a vector renderer such as Vello is the alternative to growing our own shaders. The [text crate choice](2026-11-text-crate-choice.md) noted that Vello needed a newer `wgpu` than Iced allowed, which no longer binds us once Iced is gone. Decide in an ADR when a view first needs it, not before.

## Not covered by the article

Plugin windows (OQ-13), desktop input methods, and `winit` are not discussed in it, so it gives no guidance on them.
