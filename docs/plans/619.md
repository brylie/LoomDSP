What "idle" means for #730's "Done when".** A new patch has a Transport, and it starts running (`clock.md`, rule 6), so its Beat light flashes twice a second at 120 BPM, about 4 frames a flash as it fades over 120 ms. That is a visible change, so the frames are correct (new rule in `panels.md`, Redraw). Today `FrameCause::Meters` counts `Message::Lights` too (`lib.rs:1421`), so with the transport running #730's check ("no frames caused by meters") cannot pass as written. That label is also what made #730 blame the meters.
  - **Recommended: (b)** split the cause into `meters` (meters and scopes: `Message::Meters`, `Message::Telemetry`) and `lights` (`Message::Lights`) in `--measure-idle`. Then #730's check passes as written, and the output names the true cause. The change: `FrameCause::Lights`, with a `FrameCause::is_live()` used at both places that list the live causes today (`lib.rs:1449` for the accessibility tree's `Touch::Live`, `lib.rs:1462` for the focus question), so a light message keeps today's handling there; the cause arrays in `loom-canvas/src/stats.rs:61,73,80` grow from 8 to 9; `bench.rs` prints `lights:N` between `meters` and `control`.
  - **(a)** read the check with the transport stopped, and edit the issue to say so.
  - The same reading applies to the UI layer's idle criterion (`ui-layer.md:496`, section 3, Agreed: "`--measure-idle` reports no redraws") and the #683 plan's note (`leaving-iced-plan.md:234`): both are measured on `subtractive.ron`, whose transport runs. A running transport also flashes the lights it drives (a Clock Divide's or a Phase Trigger's light, a sequencer's step), so hiding the Transport tile is not enough. **Recommended:** that criterion reads "with the transport stopped, or no light it drives on screen", linked to the new rule. Whether a new patch's transport should start running is a separate question, for a separate issue.
- **M2 (Q7). A trigger light coming into view.** The lights thread reads trigger cells with `swap(0)`, so a trigger that fired any time while the light was off screen flashes once when the light comes into view. Example: a /16 divider at 120 BPM fires every 8 s; pan away for 3 s and back, and its light flashes as if it had just fired, which misleads a player using it to find the bar.
  - **Recommended: start dark.** A trigger light new to the list throws away its first latched read. With the wake in #619's design (the thread reads a new list at once), the only trigger lost is one in the instant between the pan and the read, which the player could not have seen.
  - **Alternative:** keep today's flash on arrival (the architecture author's first reading), since it never loses a trigger.
- **M3 (Q9). A meter moved by a display's edge does not also grow that way.** `widget_bounds` applies both `display_push` and `meter_growth` (`loom-canvas/src/scene.rs:524-552`, `582-601`). So today a meter below the lowest trace display moves down and also grows taller, past the tile's bottom; the width rule would do the same to the right. **Recommended: yes.** It changes Implemented height behaviour, but no built-in panel has a meter below or beside a trace display, and today's result runs the meter off the tile.
- **M4 (Q2). Trace displays on the far edges share a wide tile (#637, #639).** This changes Implemented Resizable tiles behaviour, and it departs from #639's suggested direction (stop a display at a widget to its right, as `meter_growth` does).
  - **Recommended: the far-edge rule,** in both directions, with no tie-break: every trace display whose right edge is level with the furthest right edge takes the extra width, and every widget whose left edge is at or past that edge moves right by it; the same for height, with the lowest bottom edge. Each shift moves a whole half-plane, so it never moves one widget into another, and a display on the far edge grows into the band the shift frees. *Why not #639's direction:* stopping a display at a widget to its right means the left one of two side by side, or a display with a control beside it, never widens; the far-edge rule needs no tie-break and has no overlap by construction.
  - What follows: displays stacked in a column with level right edges all widen together; displays side by side with level bottoms all grow taller; the left one of two side by side keeps its width. No module in the registry changes. *The cost:* a row of controls below a narrower display splits at the display's right edge on a wide tile, as the height rule already splits columns.
  - **`test.panel` changes** (`crates/loom-modules/src/test_modules.rs:241-244`): its far right edge is 27 (the level history and the spectrum at x 18, 9 wide) and its lowest edge 18 (the XY scope at (18, 12), 6 × 6). So only the history and the spectrum widen. The scope at (0, 8) stops widening, which is #639's own fix: today it grows over the select at (9, 8), the fader at (15, 7), and the spectrum. The XY scope stops widening too, and its square frame then cannot grow. **Recommended:** accept the new look. The alternative moves `test.panel`'s XY scope to x 21, so its right edge is level and it keeps growing.

### Settled in review

- **Q1. Non-finite samples on a scope (#637).** Skip a NaN, as the XY scope does (`XyTrace::push`); a point at the centre would draw a false 0. Pin an infinity to the edge, as any value past the range is, also as the XY scope does (`panel-widgets.md`, XY scope). Today's code already pins it, and infinity equals itself, so it never caused the redraw bug; skipping it would make a runaway feedback trace vanish the moment it reaches infinity. The middle-zoom level ignores a NaN and shows infinity at full. The vertical range follows the peak, so an infinity in the window pushes it to its largest step (±10) and squashes the finite signal until the sample leaves; the spec says so, as a visible sign. Every point the canvas gets has a finite x and y: a trigger whose sub-sample fraction is not finite (an infinity next to the crossing) counts as no trigger, and the trace runs free.
- **Q2. Trace displays side by side (#637, #639).** Moved to the maintainer as M4.
- **Q3. Two meters on one output (#637, #640).** News per meter on the telemetry thread. #640 suggested keeping `Peaks` per probe and sending per-meter state from the UI side; per-meter news is simpler, since the reset that matters is the meter's own, and it meets the same "Done when". The PR says why it departs. The inspector's **Reset clip** button resets every meter on the module, as today; resetting one meter by keyboard comes with the panel editor (#76), which is the only way to place two meters on one output.
- **Q4. `--frames` counts its own drops (#637, folded in from #642).** The issue's direction: process the lead-in in blocks and drain the queues after each, including `take_pairs`. Its check: a test runs `--frames` for longer than the queues hold, with a scope and an XY scope on screen, and `telemetry_dropped` is 0. Measured on `main`: `--dump-ui --frames 480000` on `subtractive.ron` reports `telemetry_dropped: 31702`.
- **Q5. How far a scope trace must move to wake the UI (#730).** Half a pixel as drawn, measured as the distance from a point to the other trace's line (section 4). A fixed tolerance at the scope's declared size would let an enlarged or zoomed scope lag visibly.
- **Q8. Clips during `--frames`'s lead-in.** The lead-in now drains after each block anyway, so it feeds its meter readings to the peaks and throws away only the scope and pair chunks. A clip in the lead-in then lights, as a latched clip light should; an agent checking a patch for clipping with `--dump-ui --frames` gets a true answer.

## 4. The design

### What was measured for #730 (2026-11-16, `main` at `feed50b4`, release build, `--fake-audio --measure-idle --bench-seconds 6`)

| Patch | Frames | Meters cause | Trace uploads | Control uploads |
|---|---|---|---|---|
| `subtractive.ron` as shipped | 175 | 168 | 110 | 64 |
| scope removed | 74 | 62 | 1 | 63 |
| transport stopped (`run: 0`) | 122 | 110 | 111 | 1 |
| scope removed, transport stopped | 13 | 1 | 1 | 1 |

`FrameCause::Meters` counts `Message::Meters`, `Message::Telemetry`, and `Message::Lights` (`lib.rs:1421`), so the issue's "meters" is every live display. Two sources make the frames:

1. **The scope, about 18 frames a second.** `subtractive.ron`'s scope reads the filter's output (`4:lowpass`). The oscillator runs with no note, so the filter carries a steady saw while the output is silent (the amp envelope closes it later, at module 8). The trace is a still wave, but `Watcher::take` compares traces with `!=` (`monitor.rs`), and the sub-sample trigger offset and rounding make every drain a few bits different. The level history and the spectrum already have a tolerance for this reason (`moved`, from PR #609). The scope was left out.
2. **The Transport's Beat light, about 10 frames a second.** A real visible change (M1).

The meter readings send nothing on silence: `changed` already compares them in 256 steps. So #730's narrow fix is the scope's wake rule, plus M1's honest label. The 11 frames of cause `other` in 6 s are not live displays and are outside this batch (Risks).

### #619: the lights watcher lives as long as the engine

- **The key.** `lights::Watch` holds what the thread needs for its whole life: the `DisplayReader`, the generation, and the shared list of lights (an `Arc`), so a list is never read with another engine's reader. `DisplayTable::read` uses checked slice indexing (`loom-core/src/display.rs:44-46, 87`), so a list from another engine would either panic on a slot past the table, ending the thread, or pass the owner check for a module whose number the new engine reused (numbers restart at 1, the generation comment in `lights.rs`) and `swap(0)` the wrong trigger. Its `Hash` covers only the generation. Whether any light is shown is whether there is a watch at all: with no light on screen `watched_lights` gives `None`, `watcher::keep` drops the handle, and the thread stops, as the spec asks ("only while a module with lights is on screen", `panels.md`, Redraw, #68). A pan among lights changes only the list.
- **The shared list.** A small type in `watcher.rs` holds a watched value behind `Arc<(Mutex<_>, Condvar)>`. Under the mutex it keeps the value and a version number. It outlives any one watcher (a hide-and-show starts a new one on the same value), so it holds no closed flag of its own. `set` replaces the value only when it differs, bumps the version, and notifies; an equal `set` changes nothing, which a test reads from the version without timing. `get` clones the value out with the version it read. The compared values are finite (patch loading clamps or replaces non-finite parameters, `loom-patch/src/flatten.rs:1419`), so an equal `set` is never seen as a change; the type's doc says so. The monitor's `WatchList` moves onto the same type (`Monitor::watch` and `Monitor::watched`, `monitor.rs:396-405`), rather than a second copy. Locks use `unwrap_or_else(PoisonError::into_inner)`, as the monitor's do, and are held only to clone or replace, never across a read of the table or a sleep. The shared list lives in the session's engine with the lights watch, so a new engine starts with an empty one.
- **The wake.** The lights thread waits on the value's condvar for up to `INTERVAL` (33 ms) instead of `thread::sleep`, and only while the version is the one it last read and its own handle is not closed (the thread's own `Flow.closed`), both checked under the value's lock. So a `set` made while the thread is reading the table is not lost: the version has moved, and the next wait returns at once. `Watcher::start` registers the watched value, so `Watcher::drop` stores `Flow.closed`, then locks the value's mutex, notifies its condvar, and unlocks, as well as notifying `Flow.room` (`Drop for Watcher`, `watcher.rs:241-246`, notifies only `Flow.room` today). The closed flag is per handle, so a new watcher on the same value is never stopped by the old one's drop, and the old thread always ends. **Lock order:** `Watcher::drop` takes the value's lock and `Flow.room` one after the other, never one inside the other, and the thread never holds the value's lock while it sends (a send reaches the ledger and `Flow.room` locks), so no lock-order cycle can form. The loop order is wait, check closed, read, compare and send, so a stopped thread never reads the table again. A light coming into view is read in the same instant, and a dropped handle ends the thread at once, as #619 asked. The monitor's thread waits the same way, up to its own interval, so a clip reset, a scope setting change, or a zoom that changes a scope's drawn size drains early, which brings news back sooner and costs nothing.
- **Per-light state, kept by light.** The thread keeps each light's last step, fade, and readout hold in maps keyed by `Light` (module, widget), pruned to the current list at every read. A light that stays on screen across a pan keeps its fade and does not flash again. A light that comes into view has no last step, so its first reading is sent (a trigger light starts dark, M2). A light that leaves is forgotten. A light whose display source changes starts again.
- **The UI side of a leaving light.** `Message::Lights` only adds to `session.lights` today (`lib.rs:2041-2042`), so a trigger light panned away mid-fade keeps its brightness, and the pan's own frame would draw it lit on return before the first reading arrives. When a trigger light leaves the list, the app sets its kept value to dark. A level light keeps its last value, the best guess until the first read.
- `App::watched_lights` (`subscriptions.rs`) builds the list. `App::sync_watchers` (`watching.rs`) sets it on the shared list before `keep`.
- **`--frames` still reads the lights once** (`snapshot.rs:534-535`, `watched_lights().read()`). The split keeps a one-shot read of a list with its reader for that path. That read keeps the latch, so a trigger that fired during the run shows lit, unlike M2's start dark; the snapshot shows what the run left, and the spec says so.
- A side benefit for the PR: today a pan that changes the list starts a second lights thread while the old one may be mid-read, both calling `swap(0)` on trigger cells, which the spec forbids ("Two readers are not supported"). After this batch no pan starts a second reader. The same short overlap can still happen when every light is hidden and one is shown again, since that stops one thread and starts another.

### #637, part 1: a NaN never reaches a scope trace

- `ScopeTrace::canvas_trace` (`live.rs`) skips a NaN sample, in the full trace and in the min-max reduction of a long window. The reduction picks the lowest and highest sample of each group that is not NaN, and a group with none adds no point. An infinity is pinned to the edge by the clamp, as today.
- `find_trigger` (or `ScopeTrace::update`) treats a non-finite sub-sample fraction as no trigger: free run, offset 0. So no point gets a NaN x.
- The level already ignores a NaN through `f32::max` and shows infinity at full. A test pins both.
- The line-distance check below expects finite points. The `debug_assert` that says so is added in this commit, the one that makes the points finite, so a debug run with a NaN scope never panics between commits.

### #637, part 2: trace displays on the far edges share a wide tile (M4)

- `ModuleView::widget_bounds` (`loom-canvas/src/scene.rs`) gets the far-edge rule (M4) in both directions. `lowest_display` becomes the lowest bottom edge of the shown trace displays, and every display level with it takes the extra height; a new furthest-right edge does the same for width. `display_push` returns a shift in both directions: right by the extra width for a widget whose left edge is at or past the far right edge, and down by the extra height for one whose top edge is at or below the lowest bottom edge. Positions are compared as declared.
- A meter moved by a display's edge does not also grow in that direction (M3).
- The `lowest_display` comment that says side by side is not handled goes.

### #637, part 3: two meters on one output keep their own clips (Q3)

- `Peaks` (`clip.rs`) keeps its news per meter (module, widget). `WatchList::peak_resets` becomes a map from meter to (probe, its own reset count), filled by `App::peak_resets` (`lib.rs`) from `scene::meter_outputs`, with no sum.
- Each reading goes to every meter on its probe. A reset clears only that meter's news, so its neighbour on the same probe keeps a clip that is on its way.
- `Update::peaks` carries `(meter, PeakNews)`. `App::take_peaks` drops news that is stale for that meter, or for a meter no longer on screen, as it does today without being asked.
- `snapshot.rs` changes with `Update::peaks` in the same commit.

### #637, part 4: `--frames` drops nothing, and its lead-in clips count (Q4, Q8)

- `App::run_engine` (`snapshot.rs`) plays the lead-in block by block. After each block it drains `take_telemetry` and `take_pairs`, feeds the meter readings to the peaks, and throws away the scope and pair chunks. The last second works as today. The run never fills a queue, so `telemetry_dropped` counts only real drops.

### #730: a scope wakes the UI only when its line moves (Q5)

The spec is `panels.md`, Drawing the scope trace, Redraw (Draft, #730).

- **Why not point by point.** Each point is `x = (i - offset) / span` (`live.rs:449-450`), and the sub-sample offset changes on every drain when the period is not a whole number of samples (middle C at 48 kHz is 183.47 samples). The points slide along the same curve. A simulation of `subtractive.ron`'s case (261.63 Hz, 240-sample window, drawn 216 × 120 px) moved points by up to 1.7 px while the line moved under 0.01 px. Comparing y at fixed columns fails on steep edges instead, and a reduced trace can change its point count by one between drains.
- **The rule.** A new trace is sent when any of its points inside the frame (x from 0 to 1) lies more than half a pixel, as drawn, from the other trace's whole line, or the other way round. The middle-zoom level is sent on any change of its 256 steps. A scope-only function in `monitor.rs` does this; the level history and the spectrum keep `moved`.
- **The line reaches past both edges.** A triggered trace takes `window + 2` samples (`n.checked_sub(window + 2)?` in `find_trigger`, as it does today with `window + 1`, so a short history falls back to free run; the copy keeps its `.min(samples.len())`), so it reaches past x = 1 as it already reaches past x = 0. With `window + 1`, its last point falls short of the right edge by up to one sample, and that end moved by 0.72 px between drains in the simulation, over the tolerance at zoom 2. The `Data` line in the spec and the `ScopeTrace::trace` doc change with it. It also ends a visible jitter at the line's right end.
- **Bounded cost.** Both traces run left to right in x, so a window that moves along the other line keeps the check close to linear. The cap counts every segment tried for one point, the window included: 64. A point that reaches the cap counts as moved, so the worst case costs one redraw, never a stall of the telemetry thread, where meter and clip news also run. *Why 64:* full traces start at about zoom 0.81 (`loom-canvas/src/input.rs:991-999`), where a scope 9 grid units wide is about 87 px on a 1x screen. A window over about 21 ms reduces to about 1,022 points (`MAX_TRACE_POINTS`), so about 12 points a pixel, and the half-pixel window holds 12 to 14 segments. A small cap such as 8 would be hit at every point and bring #730 back for long windows; 64 leaves room, and the 1 × 1 worst case is 1024 × 64 segment tests. With no drawn size known yet, the trace is sent on any change, as today.
- **The limit.** A wave with corners sharper than a sample (a saw's jump) can still move its line by up to about 0.86 px and wake on some drains. That is a real change on screen.
- **The drawn size.** `ScopeWant` carries the scope's drawn size in physical pixels: the widget's bounds × zoom × the window's scale factor, rounded to whole pixels, at least 1. It is worked out again after any change that moves the scope's bounds: the camera, the window's scale, a tile resize, or a scene change such as a control shown or hidden above it. Plumbing: the `CanvasEvent::Camera` arm (`canvas_events.rs`) calls `publish_watch`, which it does not today; the drawn size reads the window's scale from each update's context (`cx.window().scale`) and republishes when it differs from the scale last used. A scale change arrives as a message (`Message::A11y(ScaleFactor)`), so an update runs. The watch list is updated in place, so no thread restarts. The accessibility layer keeps its own copy of the scale (`a11y.rs:258, 280`); sharing one kept value is a follow-up (section 9), since `a11y/` is where the #683 sessions work.
- **Two scopes on one probe** share one `ScopeWant` (`publish_watch` keys by probe, `lib.rs:1110-1121`). The size is the larger of the two, so neither lags by more than half a pixel. Only the panel editor (#76) can make this case.
- **The frame cause (M1, if (b)).** `FrameCause::Lights`, `FrameCause::is_live()` at `lib.rs:1449` and `:1462`, the arrays in `loom-canvas/src/stats.rs` from 8 to 9, and `lights:N` in `bench.rs`'s output.
- The meters and lights need no change for #730: both already wake only on a step that shows.
- The UI snapshot's `TraceShown.level` keeps the level last sent while the full trace is drawn, since only the points are compared then. The spec says so.

## 8. Risks

- **The scope tolerance hides a real change.** Half a pixel cannot be seen, and a trace that keeps drifting is sent once it has moved that far from what the UI last got. The moving-wave test checks it.
- **The drawn size changes the watch list on every zoom step.** The list is updated in place, and the size is rounded to whole pixels.
- **The far-edge rule moves a built-in widget.** The test that widens every built-in panel catches it.
- **The 11 `other` frames in 6 s** on the fake device are not live displays and are outside this batch. Retro candidate if they matter.
- **#683 phase 3** will replace the light and meter messages with draw-time reads. This batch's changes stay small, so that work can drop them without a fight. The shared watched-value type outlives it.
- **Drop first:** the far-edge rule (no built-in panel needs it until the panel editor, #76), then part 3 (no built-in module has two meters on one output).
