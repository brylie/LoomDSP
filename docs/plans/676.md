## 3. Questions to settle

Each has a recommended answer. Once agreed, it goes into `docs/design/polyphony.md` as Agreed.

**A. Voice assigner: what identifies a note?** Rule 22 identifies a note by its pitch, and on Note input by pitch and MIDI channel.
*Recommend:* the input voice index. `NoteId` is the input voice (0 to 15). One input voice carries one gate, so it holds at most one note at a time, and "expression follows the input voice it came from" is then exact. Two input voices on the same pitch are two notes, as two MPE member channels are. A rising edge on an input voice whose note still sounds cannot happen (a rise needs a fall first, which ended the note).

**B. Voice assigner: the input pitch moves while its gate stays high** (a legato mono source, a glide).
*Recommend:* the output voice's pitch follows, with no new note and no retrigger. This is what "follows the input voice while the note sounds" already says; the spec states it.

**C. Voice assigner: what `level` is indexed by, for Quietest.**
*Recommend:* by output voice. The player patches it back from the envelopes after the assigner, so voice *k* of `level` is the loudness of output voice *k*. With no cable on `level`, Quietest acts as Oldest (rule 20), checked with `!io.uses_default(LEVEL_IN)` as Note input does (rule 6's wording; same result as `is_connected` for one instance).

**D. Voice assigner: `unison` larger than `voices`.**
*Recommend:* the allocator's existing clamp: a note takes `min(unison, voices)` voices. With 8 voices and unison 3, two notes sound together and a third steals by the mode.

**E. Voice assigner: input bundle wider or narrower than `voices`.**
*Recommend (revised after the usability review):* the input width and the output count are independent, and **the number of input voices is the largest width among the five note inputs** (`pitch`, `gate`, `velocity`, `pressure`, `timbre`; not `level`, which is indexed by output voice). This is rule 4's "largest voice count" applied to the assigner's input side. `PortIo::voice_input` copies a one-voice cable to every voice, so reading all 16 input voices would start 16 notes on one mono edge; reading only `0..n` prevents that. Inside `n`, rule 6 applies: a mono cable feeds every input voice, a narrower one pads with its default. So a mono pitch and a mono gate give one note per edge; a 4-voice pitch with one mono gate gives a 4-note chord on each edge, as the same two cables into an oscillator give 4 voices; with no gate cable, nothing plays. A 16-voice input into 4 output voices steals by the mode. (The first draft used the gate cable's width alone; the usability review showed it breaks rules 4 and 6.)

**E2. Voice assigner: a note's output voice is stolen while its input gate stays high.** (Found by the product-owner author.)
*Recommend:* the stolen note stays silent; its later note-off changes nothing; it plays again on its input voice's next rising edge. This is what the allocator already does (`note_off` releases only voices that still hold that id), and it matches a keyboard, where a stolen held key does not come back.

**F. #793: what Voice merge's new output carries.**
*Recommend:* a new mono output, `gate` (signal type Gate, one voice).
- In Last, Lowest, and Highest: the gate value of the selected voice, its two stereo sides combined by maximum. When the selection moves to another held voice (the lowest key released while others are held), the output stays high and does not retrigger: legato, as Note input does at one voice. When every voice is low, it is low, and `out` keeps the last selection, as today.
- In Sum and Average: the largest gate value among the voices, so it is high while any voice is high.
- With `gate` unconnected: its normal of 1, so the output is 1 in every mode.
- A one-voice bundle passes its gate through.
A retrigger option on a selection change is out of scope.

**G. #794: a non-finite value in Lowest and Highest.**
*Recommend:* a voice whose `in` is NaN or infinite ranks below every voice with a finite value; for a stereo voice, if either side is non-finite. When every high voice is non-finite, the existing tie rule applies (lowest voice index), and its value passes through unchanged, because cables are never cleaned (ADR-0007). Sum, Average, and Last are unchanged.

**H. #787: what the "about 100 modules" are.** The polysynth benchmark record counts modules in the patch (12), not module runs.
*Recommend:* about 100 modules in the patch file, as a realistic layered 8-voice synth, not 100 copies of one module:
- Note input at 8 voices into a Voice assigner (so the new module is measured);
- per voice, about 55 modules: four oscillator layers (saw, pulse, triangle, sine), each with its own phase, Voice spread for detune, filter, filter envelope, amplitude envelope, amplifier, a per-voice LFO with slew, and the scale and multiply that set its depth (about 11 per layer); then a layer mixer, a noise layer with its own filter, a Clamp for saturation, a final filter, and an output amplifier;
- shared, about 40 modules: Note input, the Voice assigner, the Voice merge, global LFOs and macros, constants and math for modulation, and a stereo effect chain after the merge (Join, delays, all-pass diffusers, EQ, dynamics, a crossfade for wet and dry), plus Transport and Audio Out.
That is about 95 to 100 modules in the file and about 480 module runs per block (55 × 8 + 40). The per-voice share was miscounted in the first draft (found by the product-owner author). From the polysynth's 58 µs for 53 runs, a rough linear guess is 0.5 ms per block, about 20% of real time, so it may land near the 25% budget. If it goes over, the benchmark record says so: a result is a finding, and the patch is not trimmed to pass.
File: `examples/patches/polysynth-large.ron`, with a comment on what it is for.

**Settled by the architecture author against the code** (now in the spec): note-offs run before note-ons on one frame, in rising input voice; a gate bundle that narrows releases the notes it drops; each input voice's last finite values are held, so a NaN never sticks in a released voice; an output voice that never had a note writes Note input's values (pitch -0.5); a `unison` change applies from the next note; the large patch has no feedback loop and no `level` cable, so its number does not depend on #733.

**For the maintainer at sign-off** (recommendations in brackets):

## 4. The design

**`crates/loom-modules/src/voice.rs`, Voice assigner (`loom.voice.assign`, MT-VOICE-04).**
- `ASSIGN: ModuleDescriptor` as the spec's table: inputs `pitch`, `gate` (default 0), `velocity` (default 1), `pressure`, `timbre`, `level` (default 0), all `Channels::Voices`; outputs `pitch`, `gate`, `velocity`, `pressure`, `timbre`, all `Channels::Voices`; parameters `voices` (1 to 16, default 1, not modulatable, structural like Note input's), `mode` (rule 20, choices shown by count per ADR-0030), `unison` (1 to 4, default 1). Every port and parameter index is an associated constant from `ASSIGN.input_index(..)` and friends.
- State: one `loom_dsp::voice::Allocator` (it already has unison, `voices_for`, `update_note`, and `begin_frame(levels)`), and a fixed `[bool; 16]` of last gate states per input voice. No allocation after `new`.
- Per frame: `begin_frame` with the `level` values when connected; for each input voice below `n`, the largest width of the five note inputs (answer E), a rising gate edge is `note_on` with its pitch and velocity, a falling edge is `note_off`; for each held note, `update_note` with its pitch, velocity, pressure, and timbre; then each output voice is written from `voices()`.
- `reset`, `copy_state_from` (with `loom_core::copy_state`) implemented. The voice count reaches the outputs as on Note input (`crates/loom-modules/src/midi.rs`): capacity from `output_width(PITCH_OUT)`, `configure` once per frame. Note input's `voices` and `mode` `ParamSpec`s are written inline today, so the first build step pulls out a shared `const fn` for them, the value-to-`Mode` mapping, and a stereo-mean helper that Merge and Note input both compute. With the shared `mode` spec (`choices_by_count("voices", 2)`), the app's count-crossing mode switch in `crates/loom-app/src/modes.rs` needs no new code.
- Registered in the module registry beside the other voice modules; a help page from `mise run help-pages`.

**`Merge` in the same file.**
- #794: the comparison in the selection loop ranks a non-finite `value` last. A small helper, `better(mode, candidate, previous)`, keeps the three modes readable.
- **K, in `loom-core`:** a new `ModuleDescriptor::effective_value(index, values)` returns a count-filtered choice's stored value when it is inside `control_spec`'s filtered range, else the range's `min` (the allocator's `Mode::for_capacity` fallback). `is_shown` reads the controlling parameter through it. The inspector (`crates/loom-app/src/inspector.rs`, including the "Not used in" text, which today names the stored choice) and the canvas (`crates/loom-app/src/scene.rs`, `control_position`) apply this rule in their own copies today and switch to the shared function. Note input has no `shown_when`, so nothing it shows changes. Tested in `crates/loom-core/src/descriptor/tests.rs` and in the assigner's app test.
- #793: a `GATE_OUT` output. Written every frame from the selected voice's gate (selection modes) or the maximum over voices (Sum and Average).

**#787 files.** The new patch; a second summary line in `benches/engine.rs` printed beside the polysynth's in the same format; a reference render in `crates/loom-modules/tests/patches.rs`; `loom check` in `crates/loom-cli/tests/check.rs`; a benchmark record in `docs/benchmarks/`.

**Reused:** the allocator (#673), Note input's voice-count path (#674), the `loom-test` harness at block sizes 1, 77, and 512, the polysynth bench helpers (#677).
