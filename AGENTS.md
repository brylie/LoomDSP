# Agent Guide for LoomDSP

Context for AI coding agents (and new human contributors). Read this before changing code.

## What this project is

LoomDSP is an open-source modular audio environment in Rust, built for live performance. Users connect DSP modules in a graph, play it with MIDI controllers, and later export it as a plugin. Read [docs/product/vision.md](docs/product/vision.md) for goals and [docs/product/roadmap.md](docs/product/roadmap.md) for the current phase.

## Project stage: early alpha

Nothing is released yet. Until the architecture settles, expect breaking changes: module IDs, port and parameter names, the Rust API, and the patch format can all change. Prefer the clean design over a compatibility shim, a deprecated alias, or a migration.

- The patch format stays at version 1. A change may stop old patches from loading. Migrations (FR-FILE-02, ADR-0008) start with the first release.
- When a change breaks something, update every example patch, test, and reference render in the same pull request, and list the break in its description.
- The other hard rules still apply in full: real-time safety, block-size invariance, determinism, licences, portability, and clean room.

Why: the design is still being found. Keeping early mistakes compatible would freeze them before anyone depends on them.

## Architecture in one page

The longer version, with diagrams, is [docs/dev/architecture.md](docs/dev/architecture.md).

- **Two threads, two halves** (ADR-0001). `Controller` runs on a control thread, owns the editable `Graph`, compiles it, and sends commands. `Engine` runs on the audio thread and only executes. They talk through bounded SPSC queues (`rtrb`). Memory is allocated on the control thread, moved to the audio thread, and moved back for freeing.
- **Compilation** (ADR-0002, `crates/loom-core/src/compile.rs`). The graph is turned into a `Schedule`: every output port gets a buffer, Tarjan's algorithm finds feedback loops (SCCs), acyclic parts run a block at a time, and loops run one sample at a time. `loom.time.delay1` modules break loops. If a cycle has none, the compiler inserts one and reports it. Modules with no path to the audio output, a probe, a light or display value, or a modulated parameter are not scheduled (FR-GRAPH-09) but keep their state in their slots.
- **Schedule swap.** A new schedule replaces the old one at a buffer boundary. Module instances live in engine slots and keep their state across swaps. Unit delay state is carried over by key, and a new delay starts from its source's last value. An input whose cable or assignment changed holds its last value and ramps to the new signal over 5 ms (`crates/loom-core/src/cable_fade.rs`, `compile/fades.rs`); gate, trigger, and phase inputs switch ([live patching spec](docs/design/live-patching.md), rules 5 and 9).
- **Telemetry** (`crates/loom-core/src/telemetry.rs`). The UI probes an output port with `Controller::add_probe`; after each block the engine pushes meter readings, scope chunks, and chunks of paired samples into three bounded queues, read through `Telemetry`. When a queue is full, telemetry is dropped and counted, never waited for. Spec: [docs/design/telemetry.md](docs/design/telemetry.md).
- **Algorithms** (ADR-0035, `crates/loom-dsp`) are plain structs with no ports or graph: filters, equaliser sections, crossover, phase generator (`Phasor`), oscillator shapes, noise, a seeded random stream, Euclidean patterns, envelope, slew, delay line, all-pass, limiter, dynamics, and level match. A module is a thin wrapper that adds ports, parameter mapping, smoothing, and guards. An algorithm useful outside a patch goes there, with tests against its theory and cited sources. In phase-driven wave shapers (`poly_blep` / `poly_blamp`), use the shortest wrapped phase step `dt.min(1.0 - dt)` so descending phase ramps are also band-limited, track a separate phase step for any edge moved by a parameter (such as pulse width), and keep overlapping BLEP windows bounded to `[-1.0, 1.0]` under audio-rate modulation. Spec: [docs/design/dsp-algorithms.md](docs/design/dsp-algorithms.md).
- **Modules** implement `Module::process` over a `PortIo`. Their ports and parameters are described by a static `ModuleDescriptor`, as struct literals with a required `label` and one-sentence `description` (ADR-0016; these are not IDs and can be reworded). An unconnected input reads its `PortSpec` default: zeros, a fixed value, a transport signal, or the module's own phase. The engine fills every default except `PortDefault::OwnPhase`: for that one it feeds zeros, and the module runs its own phase while its phase input reads its default (`io.uses_default` on that input, including a voice beyond a narrower cable), through the shared code in `crates/loom-modules/src/own_phase.rs` (ADR-0042, [oscillators spec](docs/design/oscillators.md)). `tests/own_phase.rs` checks every module that declares it. Name every parameter and port index with an associated constant looked up from the descriptor at compile time, such as `const CUTOFF: usize = SVF.param_index("cutoff").unwrap();` (inputs end in `_IN`, outputs in `_OUT`), never a bare number: a wrong name fails the build, and reordering the descriptor cannot leave an index behind. `io.split` still binds ports by position, so reorder its patterns by hand when ports move. Use `io.is_connected(i)` to ask whether a cable exists. Use `!io.uses_default(i)` when a copy needs its own voice of an input, including alternate-source fallbacks such as a sidechain or the lane above. Value inputs keep their port default when padded. `reset()` clears state and snaps smoothing to its targets: the `Controller` calls it once after a new module's first values are set. A module that smooths a continuous parameter also implements `param_glide`, so the first assignment on that parameter does not step; `tests/param_glide.rs` checks every module. A module with state implements `copy_state_from` (ADR-0022), usually with `loom_core::copy_state`, so a stereo copy can take over the running state. Test each module with the `loom-test` harness (`crates/loom-modules/tests/reference.rs`): it checks block sizes 1, 77, and 512 and compares with a reference WAV file. Spec: [docs/design/module-test-harness.md](docs/design/module-test-harness.md).
- **Panels** (ADR-0013, `crates/loom-core/src/descriptor/panel.rs` and `descriptor/display.rs` for the descriptions, `crates/loom-core/src/display.rs` for the latest-value table). A `ModuleDescriptor` declares its tile's `Panel`: widgets on the grid, bound by name to parameters (controls) or display values (lights). The registry checks every panel. Modules publish up to 4 display values in `Module::displays`, once per block, into a latest-value table the UI reads with `Controller::display`. Spec: [docs/design/panels.md](docs/design/panels.md).
- **Transport** (ADR-0015, `crates/loom-core/src/transport.rs`). The engine owns one transport per patch: tempo, time signature, running, and position in `f64` beats. The `Controller` changes it; modules read it through `ProcessContext::transport`. Position is computed from an anchor, never by adding a step per block, so it is the same at any block size. Use `TransportInfo::position_at(i)` inside a call. Spec: [docs/design/clock.md](docs/design/clock.md).
- **MIDI mappings** (`crates/loom-core/src/midi_map.rs`). A mapping links a MIDI control (channel and controller number) to one parameter, and saves with the patch. The engine applies control changes itself and records each value in a feedback table of atomics, one entry per control. `Controller::sync_midi` copies those values into the graph, so the screen shows and saves what plays; an edit token orders them against screen edits still on their way to the engine. In the app, a watcher thread (`learn.rs`) wakes the UI when a control change arrives, and learn mode arms controls on tiles and in the inspector. Spec: [docs/design/midi-learn.md](docs/design/midi-learn.md).
- **Signals** (ADR-0007). Every cable is `f32` at the sample rate. Types are hints only. Pitch is 0.1 per octave, 0.0 = middle C. Gates are high above 0.5. A trigger output is high for one sample, and trigger inputs count rising edges (`signal::trigger`, `signal::EdgeDetector`). "1.0 = 10 V" for Eurorack users. Cables are never clipped. The engine clips only the final output, to -1 to 1, and turns NaN and infinity there into 0.
- **Output safety** (ADR-0019, `crates/loom-core/src/safety.rs`, with the DC blocker and limiter in `loom-dsp`). Before that clip, a DC blocker and a limiter at -1 dBFS protect speakers and ears, and audio fades in over 10 ms. Before a stream stops, `Controller::fade_out` fades it out, and `RunningAudio::stop` waits for the silence. `EngineConfig::output_safety` picks Low latency (default), Clean (2 ms lookahead), or Off. Tests that compare exact output values use Off and play past the fade-in. Spec: [docs/design/output-safety.md](docs/design/output-safety.md).
- **Patches** (ADR-0008) are RON files, loaded by `loom-patch`.
- **Visual system** (`crates/loom-app/src/style.rs`). Every app text size and switch size is a named token there, and every button has a role: primary (at most one per view), secondary (the default), danger (Panic), or plain. Never write `.size(N)` inline; a test checks. Spec: [docs/design/visual-system.md](docs/design/visual-system.md).
- **Accessibility tree** (ADR-0041, `crates/loom-app/src/a11y.rs`). A screen reader reads the window through an AccessKit tree built from the view models (`a11y/tree.rs`), and its requests become ordinary messages (`a11y/actions.rs`). The toolbar and the stats bar are drawn from plain-data models (`toolbar.rs`, `bars.rs`) that the tree reads too. A part the toolkit draws is wrapped in a container whose widget ID is its UI ID's text, and `places.rs` reads its bounds back from the window, for the tree and for `locate`. Neither file has platform code, so both are tested on every OS; `a11y/macos.rs` attaches the tree to the window until our own shell does. Every node is named by a `loom_ui_core::UiId`, a path of keys taken from what the element shows, never from its position, and `IdTable` gives each one a node ID that is never reused. Spec: [docs/design/ui-layer.md](docs/design/ui-layer.md), sections 4 and 7.
- **Canvas** (ADR-0010, `crates/loom-canvas`). Drawn with one set of wgpu pipelines (`canvas.wgsl`): instanced rounded rectangles and Bezier cable strips. The app builds a `Scene` from the graph; the canvas never edits it, it reports `CanvasEvent`s. Geometry and colours in the canvas and in the app's canvas code are `loom-ui-core` types (`Point`, `Vector`, `Size`, `Rect`, `Color`); convert with `loom_canvas::iced_convert` (`to_iced()`, `to_core()`) only where a value crosses into or out of an Iced call (ADR-0041). Input is plain code in `crates/loom-canvas/src/input`, with no Iced in it: `CanvasInput::handle` takes a `loom-ui-core` `Event` and the `Moment` it arrived in (pointer, bounds, time) and returns a `Reaction` (events to report, input used, redraw); `CanvasInput::next_deadline` says when it next needs to wake. `CanvasModel` is the canvas's view model for one frame. The handlers never read the clock or name an Iced type, and `crates/loom-canvas/tests/purity.rs` checks both that and where Iced is named; test them by calling `CanvasInput` directly. Drawing is plain code too. `CanvasRenderer` (`gpu.rs`) takes a wgpu device, queue, and render pass, a `CanvasFrame` from `CanvasInput::frame`, and a `Target`; the host owns the pass, its viewport, and the window. `CanvasInput::paint` hands text and the boxes of floating parts to a `TextPainter`, which also sizes text (`painter.rs`), so it names no text renderer. The canvas draws its own text (ADR-0041, spec section 8): `CanvasText` (`text.rs`) sets every run with Parley, one cached layout for measuring and drawing; `CanvasInput::paint_list` records the frame's boxes and glyphs in layers, in the order painted; and the renderer draws them last, from a glyph atlas rasterised with `swash` (`gpu/atlas.rs`, `gpu/text.rs`). The Iced widget (`widget.rs` and `widget/`) only converts events, applies the `Reaction`, schedules the deadline, and wraps the renderer as shader primitives. Iced is named only in `widget.rs`, files under `widget/`, and `iced_convert.rs`. GPU data is rebuilt only when the scene's generation changes, and pan or zoom only updates a uniform. Panel control values (`PanelValues`) have their own GPU buffer, so turning a knob never rebuilds tiles, ports, or cables. Keep it that way: do not rebuild GPU data every frame, and do not add shaders that run over the whole window for each shape.
- **UI runtime** (ADR-0041, `crates/loom-ui`, [spec](docs/design/ui-layer.md) section 2). `Runtime::handle` runs one turn per `DriverEvent`: one `update` per message, that update's `Effects` right after it, and messages those effects produce on the next turn. Effects are plain values (focus, scroll, clipboard, dialogs, questions, background work, capture, after draw, messages for the next turn, redraw, quit) that the runtime, the routing `Target`, or the `Driver` carries out. `update` reads the time, a `Waker`, the focus, and the window from its `Context`. A turn draws only when a panel's model changed, the target asks, or an effect asks. The crate names no window toolkit and never reads the clock (`tests/purity.rs`), except its window shell, `loom_ui::shell` (the `shell` feature, on by default): a `winit` loop that drives the runtime and hands each frame to the app's `shell::Layers` to draw (`examples/window.rs`). `mise run ui-no-toolkit` builds the crate without it. Test it with `headless::Harness`, which answers dialogs only as a test says and panics naming any other. `loom-app` runs on the shell.
- **App** (`crates/loom-app`). `App::update` returns `loom_ui::Effects`, and the app runs inside `loom_ui::Runtime` on the `winit` shell (`loom_ui::shell`). Until phase 3, Iced draws the views as the shell's `Layers` and is the routing target (`iced_bridge/window.rs`), and only `iced_bridge/`, or a file still listed in `tests/purity.rs`, may name Iced's `Task` or `rfd`. A native dialog is an effect whose answer comes on a later turn (`dialogs.rs`). There are no nested updates: a message the player sends through another part (a menu item's Enter, a screen reader's action, a control command) is posted for the next turn with `App::post`, which `update` returns as the next-turn effect, and what only Iced's widgets know (focus, where a part is) is asked with `App::ask_window` (`window_question.rs`). Tests apply a message with `App::send`, which routes input, answers dialogs from `files::fake`, and runs work inline. A `session::PatchSession` holds the open patch: the `Controller`, module positions, selection, edits, canvas caches, and the stream. New and Open replace it whole, so a new field goes either there or on `App`, by how long it lives, and a test makes it choose ([architecture](docs/dev/architecture.md#how-the-app-handles-a-message)). `overlays::Overlays` holds what is open over the canvas, one panel at a time. What belongs to the machine (the preferences file, devices, MIDI inputs) is a `settings::Rig` that outlives each engine; devices are reached through the `devices::Host` trait, which tests replace with a fake ([preferences spec](docs/design/preferences.md)). UI crates are desktop only; the engine crates never depend on them. To test what a pointer or key event does, use the headless `Ui` harness in `crates/loom-app/src/ui_test.rs`: it sends real events to `App::view`, runs them through the app's own bridge and runtime with a test driver (`iced_bridge/headless.rs`), and finds ports, controls, and text by name, not by pixel. To test what a screen reader meets, read `ui.a11y_tree()` and act with `ui.a11y_action` or `ui.a11y_set_value` (`ui_test/a11y.rs`). A test reads the app with `ui.app()` and sets up state with `ui.app_mut()`, never by setting the app's copy of focus. App tests check what the user sees with `App::ui_snapshot()`, built from the same data the view draws (the inspector rows come from a plain-data model in `inspector.rs`, and the module browser's and Your patches' rows from the model each browser keeps in `browser.rs` and `patches.rs`, and Preferences and the licence chooser from the models in `settings/model.rs` and `licence_chooser.rs`). Without an audio device the app keeps the engine idle, and tests run it with `App::process(frames)`. `--fake-audio` plays it from a timer instead (`AudioOutput::clock`), so live values and lights move with no device, and `--record out.wav` saves what it plays, across Open, New, and device changes, until the app quits. To test what the app plays, give the fake host a `Tape`: its devices become stepped outputs (`AudioOutput::stepped`) that play only when the test steps the tape and keep every sample, so a test can check clicks, peaks, and DC with `loom_analysis` (`crates/loom-app/src/qa_tests.rs`, [audio QA spec](docs/design/audio-qa.md)). To check a change in the running app, use the control channel (`--control SOCKET` or `--control-script FILE`, [spec](docs/design/control-channel.md)): commands by name go through the same messages as the UI, and replies give the UI snapshot, where a named control is in the window, and a screenshot of the whole window.

Tests live in their own files, never inline in a code module: unit tests for `foo.rs` go in `foo/tests.rs`, declared with `#[cfg(test)] mod tests;`, and test fakes follow the same rule. `mise run test-placement` enforces it (CONTRIBUTING.md, Where tests live).

Before finishing a change, add `///` doc comments to new structs, functions, and tests, then run `prek run --all-files` (fmt, clippy, typos, file checks) and `mise run check` (the checks CI runs, including tests with the 80% line coverage minimum). The tools come from `mise.toml`; in a new worktree, run `mise trust` and `mise install` first. Without the trust step mise refuses to read `mise.toml`, so `mise run check` and every hook that uses mise fail. CONTRIBUTING.md lists each check and the coverage gate. Never bypass the hooks with `--no-verify`; fix the cause instead.

For independent builds, run `scripts/setup-worktree-target.sh TARGET_ROOT` once in each worktree, with an existing directory on a drive with enough free space. It writes a local Cargo config that takes precedence over a shared global target directory and gives that worktree a stable folder under `TARGET_ROOT`. Keep that folder for incremental builds. Do not set `CARGO_TARGET_DIR` or pass `--target-dir` for individual commands: each new folder can use 5 GB or more. Use `cargo clean` from a live worktree to clear its target, then rerun setup to restore its ownership marker. Run `scripts/worktree-targets.sh TARGET_ROOT` to see target sizes and a dry-run of orphan cleanup, then add `--prune` to delete only marked targets of removed worktrees. Unmarked old targets need manual review.

## Hard rules

1. **Real-time safety.** Nothing reachable from `Engine::process` or `Module::process` may allocate, free, lock, wait, print, or do I/O. `tests/no_alloc.rs` enforces allocation rules.
2. **Block-size invariance.** A module must give identical output whether called with 1 frame or many. Feedback loops call modules one frame at a time.
3. **Determinism.** Same patch and input give bit-identical output. Random sources must be seeded.
4. **Licences.** Only permissive dependencies (ADR-0006). Never add GPL, LGPL, or AGPL code or crates. Check `deny.toml`.
5. **Stable IDs.** Never rename a released module ID, port name, or parameter name. Patch files depend on them. Nothing is released during the early alpha, so a rename that improves the design is allowed; update every patch and test that uses the name in the same change.
6. **Engine core stays portable.** `loom-core`, `loom-dsp`, `loom-modules`, `loom-patch`, and `loom-rt` must build for `wasm32-unknown-unknown`: no threads, files, or audio APIs there. `loom-dsp` also has no dependency that reaches users, no `unsafe`, and no allocation after `new`. `crates/loom-dsp/tests/purity.rs`, `crates/loom-dsp/tests/no_alloc.rs`, `crates/loom-dsp/clippy.toml`, and the lints in its `lib.rs` enforce this. The wasm build cannot catch a file, process, thread, or clock call, because `std` builds them there as stubs that fail when they run, so `mise run portable` (`scripts/check-portable.sh`) looks for them in the five crates' `src`. Test files (`tests.rs`, `*_tests.rs`, and files under a `tests` folder) are skipped, since test code never builds for wasm. Reading and saving patch files lives in `loom-app` (`patch_file.rs`).
7. **`unsafe` needs a `// SAFETY:` comment** that explains why it is sound.
8. **Clean room** (ADR-0018). Design modules from first principles and published theory (textbooks, papers, standards). Do not read the source code of other audio projects, whatever their licence, except dependencies accepted under ADR-0006. Do not copy or closely paraphrase other products' manuals, and do not copy their panel layouts, control names, parameter sets, or presets. If you are asked to make a module "like" another product's, build it from its purpose and the theory, and cite your references in the pull request.

## Spec first

Before writing code for a feature, read its specification in `docs/design/` (the issue links it).

- Build only what the spec says, from sections marked **Agreed**. Do not build what it lists as out of scope.
- If the spec does not answer a question about behaviour (a gesture, a default, what the user sees), do not guess. Ask, or propose a spec change first.
- If the code shows the spec is wrong, update the spec in the same pull request and say so in the description.
- Check every acceptance criterion: as a test where possible, otherwise as a manual check listed in the pull request.
- If the issue and the spec disagree, the spec wins. Say so in the pull request.
- No spec is needed for bug fixes, refactoring, tests, or changes that do not change behaviour.

Why: a gap in the spec gets filled with a guess, and a well-built guess is costly to undo. See [docs/design/README.md](docs/design/README.md#spec-first).

## Prior art

Other tools (Bitwig Grid, VCV Rack, Eurorack modules, Reaktor) inspire LoomDSP, but we do not copy them.

- Design from our own use cases, requirements, and module catalogue, not from another product's module list.
- Use our own words and names. Never copy text, module lists, parameter sets, or UI from another product or its documentation.
- Name another tool only to explain an idea or a convention, for example "like a range switch on a Eurorack module" or "1 V per octave".

Why: working through another product's catalogue makes it the outline of our design, and its selection, names, and wording slip in even by accident. LoomDSP should be original, both legally and in what it offers.

## Where documentation goes

- A **decision** (with its options and reasons) goes in an ADR. Keep it to the decision. An ADR merges into `main` only once it is decided (Accepted, Deferred, Rejected, or Superseded), never as Proposed: a Proposed ADR on `main` blocks the work that depends on it with nobody deciding. Once accepted, do not rewrite it; write a new ADR that supersedes it.
- **How a feature works** (modules, ports, rules, examples) goes in a specification in `docs/design/`, linked from the ADR. Update it in the same change as the code.
- **Who needs it and why** goes in use cases and requirements in `docs/product/`. **Tasks** go in GitHub issues.
- **Which modules to build** goes in the [module catalogue](docs/product/module-catalogue.md): one entry per module type, with a stable `MT-` ID. A new module starts from its catalogue entry. If it has none, add the entry first.
- **What we learned from other products** goes in a dated research snapshot in `docs/research/`. Only research snapshots, ADR "Prior art" sections, and explainers name other products' modules. Catalogue entries, specifications, descriptors, and help text use our own words (ADR-0018).
- **The theory behind it** (what the signal is, why the obvious approach fails, how Eurorack, VCV Rack, or Bitwig Grid do it) goes in an explainer in `docs/learn/`. Write or update one whenever a feature rests on an idea a newcomer would not know, or an edge case took real thought to settle. Link it from the spec and from the code. See [docs/learn/README.md](docs/learn/README.md).

Why: decisions stay trustworthy only if they do not move, while details must be free to change. Explainers exist because LoomDSP is also a way to learn modular sound design (product principle 11): the reasons behind our choices are part of what we ship. See [docs/README.md](docs/README.md).

## Writing style

Docs and comments use short, direct sentences and plain words, because many readers use English as a second language. Explain the reason behind a rule. Do not use em dashes. Avoid filler words such as "delve", "journey", "landscape", "realm", and "embark".

## Where things are

- Requirements with IDs: `docs/product/requirements.md`, `docs/product/non-functional-requirements.md`
- Planned module types, traits, and roles: `docs/product/module-catalogue.md`
- Research snapshots (evidence, not decisions): `docs/research/`
- Decisions: `docs/adr/` (one decision per ADR; frozen once accepted)
- Specifications: `docs/design/` (living; update with the code they describe)
- Benchmarks: `docs/benchmarks/`
- Example patches: `examples/patches/`
